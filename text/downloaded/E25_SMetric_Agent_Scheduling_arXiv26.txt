Abstract

1

LLM scheduling is critical to serving, yet how well existing
designs fit agentic serving—where agents, not humans, issue
the requests—remains unclear. Agents shift the workload in
two ways: they consume many more tokens than humans, so
the cluster must provide high throughput (tokens per second,
TPS) at low latency; and their requests reuse far more KV$
than chat.

Large language models (LLMs) now power agents like Claude
Code [6, 48] that accomplish complex tasks such as writing [5], debugging [16], and performance-tuning [54, 42]
code. An agent solves a task through a session of LLM requests, each of which requires generating many tokens. To
generate these tokens efficiently, providers deploy clusters
dedicated to serving agent requests; each cluster runs many
instances, each holding a full copy of the model. We term this
cluster-scale, agent-dedicated LLM serving agentic serving.
Agentic serving is still LLM serving: the provider serves each
request through the standard LLM API and neither runs the
agents nor sees their internal logic.
Request scheduling—how the cluster routes each request
to an instance—is a key pillar of LLM serving. Though recent
work studies it extensively [75, 82, 59, 74, 37, 2], we argue
that scheduling designs need to be revisited for agents, for
two reasons:
First, an agent consumes far more tokens per request than
a human user [9], so a cluster must provide high throughput
(tokens per second, TPS) to serve the load at low cost. Besides cost, the latency—the time to first token (TTFT) and
the time per output token (TPOT) [34]—cannot be compromised either. This is because the token generation latency
determines how fast agents finish their tasks, and a response
that is too slow makes the agent treat the request as failed [8].
Second, agentic serving exhibits a different workload pattern from chat: KV$ reuse dominates. The efficiency of
serving an LLM request depends heavily on KV$ reuse; the
KV$ is the intermediate state a cluster caches to avoid recomputation (§2). In chat workloads, this reuse is modest:
only 54–62 % of request tokens are reused from cache [63].
In agentic serving, it is far higher: our analysis of the production trace from a cluster at a representative model provider
(BAILIAN) reveals that the reuse exceeds 80 % (Finding 1
in §3). This shift requires revisiting how well scheduling
designs facilitate KV$ reuse, because the computation saved
by reuse becomes more dominant at a high reuse ratio: raising
it from 70 % to 80 % cuts the prompt tokens still to compute
by one third.
In this paper, we first conduct a systematic study of request scheduling for agents, using two recent large-scale realworld agentic serving traces (§3). We find that state-of-the-art

Existing schedulers still trade off load balance against KV$
reuse under the new workloads: cache-aware schedulers may
crowd requests onto the few instances caching the KV$, leaving the rest idle, while balanced schedulers may lose the
opportunity for reuse, which is costly, as the benefit of reuse
becomes more dominant at a high reuse ratio. We thus present
two key insights: (1) with a global-tier KV$ store, pursuing
load balance need not compromise KV$ reuse, though the
slower global tier must be used with care; and (2) given the
agent’s intra-session locality, routing requests by their sessions can balance the load with high KV$ reuse.
A key challenge in realizing session-centric scheduling is
that the scheduler must identify a request’s session statelessly,
which is difficult for model providers serving arbitrary agents.
SM ETRIC addresses this with differential scheduling based
on two indicators derived from the request itself, the session
turn and the local KV$ hit: it schedules first-turn requests
for load balance, as they mark the arrival of new sessions,
and sticks follow-ups to the instance with the highest local
hit for high KV$ reuse. As sessions differ widely in size,
SM ETRIC sticks a follow-up only if the instance can serve
it within its SLO, and otherwise migrates the session to the
least-loaded instance to prevent many long sessions from
eventually imbalancing the load. Evaluated on real-world
traces, SM ETRIC improves the peak TPS by 9–15 % under
prefill-decode colocation with a provisioned global tier and
the peak prefill TPS by 9 % under disaggregation over stateof-the-art schedulers, also with lower latency.

schedulers still suffer from the trade-off between KV$ reuse
and load balance [75]. Specifically, to achieve high reuse, the
current scheduler in BAILIAN prioritizes routing each request
to the instance holding its cached KV$ (cache-aware). This
trades away load balance: some instances overload while
others sit idle, capping the cluster’s throughput. On the other
hand, a balanced scheduler like LMetric [75] trades away
KV$ reuse, requiring more computation to serve the requests,
so the throughput gain from better load balancing is limited.
To address this dilemma, we draw two insights. First,
from the system’s perspective, pursuing load balance does
not have to compromise KV$ reuse: modern agentic serving
adopts a two-tier KV$ store—a local tier on each instance’s
GPU memory and a global tier on cluster-wide CPU memory
(§2). Even if the scheduled instance does not hold the KV$
locally, it can fetch it from the global tier. As long as the
global tier serves these KV$ fetches in time, TPS remains
high (§4.1). The global tier, however, must be used with
care: it is slower—waiting for the KV$ to be transferred adds
latency—and its capacity and bandwidth are limited. Routing
every request purely for balance—even with global-tier KV$
reuse—is thus still suboptimal.
Second, from the agent workload’s perspective, routing
requests by their sessions can balance the load with high
KV$ reuse. On the one hand, sessions are a natural unit for
balancing: though individual sessions have skewed token
usage, the token load can still be balanced across instances at
scale (Finding 6). On the other hand, sessions capture most
of the reuse, thanks to the workload’s intra-session locality:
follow-up requests mostly reuse the KV$ of earlier turns in
the same session (Finding 2). Keeping each session’s requests
on one instance thus preserves most of the KV$ reuse in its
local tier, while spreading sessions across instances balances
the cluster. At first glance, the KV$ reuse of first-turn requests
seems compromised. The impact is small: their reuse comes
mostly from the system prompt (Finding 3), which the global
tier serves efficiently.
One key challenge in realizing such session-centric
scheduling is that the scheduler must identify each request’s
session statelessly, which is difficult for model providers
serving arbitrary agents: the request carries no session information, as the LLM APIs are stateless, and its source may
further be anonymized by proxies. Inferring sessions from
records of past requests is typically impractical, as such persession state grows with active sessions, making a simple and
scalable router design challenging.
We address this challenge with SM ETRIC. The key observation is that the session turn and the local KV$ hit, both
derived from the request itself, identify sessions statelessly
and at zero cost. The turn, deduced from the number of historical messages in the request, tells the scheduler whether
the request starts a session: SM ETRIC thus schedules firstturn requests for load balance, spreading sessions across the
cluster (§4). Meanwhile, the local KV$ hit, which the router

already knows, helps identify the instance serving the session,
because intra-session reuse happens quickly (Finding 4), so
the instance with the highest hit is likely the one that executed
the session’s previous request. Therefore, SM ETRIC sticks
follow-up requests to it. This differential scheduling achieves
load balance and high local-tier reuse while keeping demand
on the global tier low, because in the ideal case only first-turn
requests fetch KV$ from it.
While such differential scheduling identifies sessions statelessly, we meet a second challenge: sticking every follow-up
request to its session’s instance still imbalances the load,
because sessions differ widely in size (§3.2) and the size
is unknown when the session is first routed, so an instance
overloads as multiple long sessions are scheduled onto it.
SM ETRIC thus sticks a follow-up request only if the instance
can finish it within its TTFT SLO, and otherwise migrates the
session by routing the request to the least-loaded instance,
with the global tier preserving its KV$ reuse (§4).
We have implemented SM ETRIC on vLLM [61] and LMCache [38], and extensively evaluated it against state-of-theart schedulers, including both the production scheduler used
in BAILIAN and recent research and open-source schedulers
(LMetric [75], llm-d [37], Preble [59], and Dynamo [45]),
with serving paradigms spanning both prefill-decode colocation and prefill-decode disaggregation. Against the bestperforming baseline, SM ETRIC serves 9–15 % more peak
TPS under colocation with a provisioned global tier, and 9 %
more peak prefill TPS under disaggregation; the gap widens
to 26–28 % as the load grows. It also achieves the lowest
median TTFT and the lowest P90 TPOT under colocation,
and the lowest tail TTFT under disaggregation (19 % lower at
P90 than the closest baseline).
In summary, this paper makes the following contributions:
• The first study of the workload patterns of LLM requests
served by an agent-dedicated cluster at scale (§3).
• The first analysis of how existing schedulers perform with
the two-tier KV$ store under agentic serving (§4.1).
• A session-centric scheduling design that identifies sessions
statelessly by the turn and the local KV$ hit, and migrates
overloaded sessions by their SLO, achieving both high
KV$ reuse and load-balanced serving (§4.2).
• An evaluation showing that SM ETRIC improves TPS and
latency over state-of-the-art schedulers (§5).
We will open-source SM ETRIC and the traces upon publication.

KV$ store hierarchy and the local vs. global tiers. Since
cross-request reuse is common in production workloads [63,
53], serving systems typically cache the KV$ of finished
requests for some time. Caching requires storage capacity
because each request’s KV$ is large: for example, a single
128K-token request consumes about 32 GB of KV$ on the
popular Qwen3-32B model. As a result, the KV$ store in
production systems follows a multi-tier architecture as shown
in Figure 1. The first tier is device (GPU) memory; when
it fills, KV$ cascades to the larger, global tiers below—host
(CPU) memory, then cloud storage (e.g., S3). A later KV$
hit on a lower tier must load the entry back up to the GPU.

LLM serving architecture in the wild. To serve LLM
requests at scale, providers typically deploy each model on
a cluster of GPUs1 . The smallest unit of deployment is a
model instance—one or more GPUs that together hold a full
copy of the model parameters. A global router dispatches
each incoming request to one instance using a routing algorithm [60, 59, 82, 75, 65]. Because a request runs in two
phases—prefill and decode—there are two mainstream serving architectures today:
PD colocation. PD colocation runs the prefill and decode of
a request to completion on the same instance (Figure 4 (b)).

agents such as Claude Code [6] solve a task through a session

written by the user, specifies the task to solve. The LLM

Agentic serving patterns in the wild

Analyzed traces. Existing production workload studies
characterize LLM serving in general [68, 53]. To understand
the workload characteristics of real-world agentic serving, we
collected two recent representative traces from two large-scale
clusters, both dedicated to serving agents for a commercial
coding-agent product (a paid subscription plan). Each cluster
is one of many supporting the product and contains at least
thousands of accelerators. Both traces cover the same peak
usage hours (10:00–12:00) on May 29, 2026: one cluster
serves a popular TB-level model (Trace 1) and the other a
roughly 280B-parameter model (Trace 2), covering agents
with different capabilities.

For each reuse, we track which session originally produced
the reused tokens. Figure 5 further breaks down the reuse on
this basis into intra-session reuse, when a request’s reused part
comes from a previous request in the same session, and intersession reuse, when it comes from a request in a different
session. Intra-session reuse contributes most of the reuse
(roughly 67 % in both traces), which is unsurprising: different
sessions tend to solve different problems, so cross-session
reuse is rare. Much of the remaining inter-session reuse stems
from multi-session workflows [4, 44], in which an agent forks
multiple sub-agents whose sessions share the parent session’s
context. Such attribution by the original producer also makes
67 % a lower bound on session locality: when a sub-agent’s
follow-up request reuses its own earlier turns, we count the
reuse as inter-session, though it could also be counted as
intra-session.

To study the workload in depth and to evaluate the serving
system under it, we collected as much information as possible
within BAILIAN’s privacy policy. For each LLM request,
each trace records (1) the hashed request content, which lets
us analyze how much the request can benefit from KV$ reuse,
(2) the arrival time, which captures request burstiness and
KV$ reuse intervals, and (3) the session information—the
session ID, the parent request ID, the turn number, and how
the request is triggered (e.g., by a human or by the agent).
Since requests carry no session identifier, we reconstruct the
session ID and the parent request ID offline during trace
collection (§A).

The KV$-awareness vs. load balance trade-off. Existing
schedulers still trade KV$ reuse for load balance. LMetric [75] reports KV$ reuse ratios comparable to those of
other KV$-aware schedulers while improving load balance,
on workloads with ideal KV$ reuse ratios typically around
50–70 %. Our agentic serving workload, with an ideal reuse
ratio of 82 % (Finding 1), shows that these two benefits do
not always hold together: without a global tier, LMetric’s
reuse ratio is only 45 %, compared with BAILIAN’s 74 %
(Figure 11 (b)). As a result, without a global tier, LMetric
serves only 920 TPS within SLO, 36 % below BAILIAN’s
1,437 TPS (Figure 11 (a)), even though LMetric achieves
better load balance than BAILIAN’s linear combination (Figure 11 (c)). We measure each instance’s load as its average
number of running requests within a 30 s window. Load imbalance is the ratio of the maximum load to the mean across
the 32 instances [51, 43].
Although the ideal reuse ratio of the agentic workload is
only about 10 percentage points above the high end of the
non-agentic ones (82 % vs. 70 %), the difference in prefill
computation is far larger: raising the reuse ratio from 70 % to
80 % cuts the prompt tokens that must still be computed by
one third.

The analysis methodology.
To understand how representative methods perform when serving agents, this section
compares the methods by replaying Trace 1 on a 32-instance
vLLM [61] cluster serving Qwen3-Coder-30B-A3B under
PD colocation, with Mooncake [53] and LMCache [38] as
the global KV$ store; §5.1 details the testbed, its tuning, and
how the replay keeps the KV$ reuse consistent with the trace.
We replay only Trace 1, since the two traces exhibit similar
patterns (§3); PD disaggregation shows similar results (§5.3).
We report each method’s TPS within SLO: the cluster-wide
output TPS (output tokens generated per second) contributed
only by requests that satisfy both the TTFT and TPOT SLOs.
The request-level SLO matters for agents: it determines the
task completion time, and a response that is too slow makes

Session-centric scheduling: challenges and our approach

Opportunity: session-centric scheduling can reconcile
load balance and KV$-awareness. Our insight is that
routing by session, rather than by request, can achieve both
objectives. Suppose the scheduler balances sessions across
the cluster and routes each follow-up request to the instance
serving its session. This strategy can balance the load without
losing reuse, because the token load can still be balanced at
scale despite the skew of sessions, as characterized in §3.2
(Finding 6). Note that placing sessions is coarser than placing
requests, which requires further care to balance the load (as
we describe in Challenge# 2 below in more detail). It also
keeps (local) KV$ reuse high: every request except the first
reuses the KV$ of earlier requests in the same session (Finding 2), and the reuse comes quickly (Finding 4), so the KV$
usually still resides in the local tier. The first-turn request is
the only exception, and it loses little performance because its
reusable KV$ is mostly the shared system prompt (Finding 3),
which the global tier serves. The load on the global tier also
stays low, because in the common case only first-turn requests
read from it.

Compared targets. We compare SM ETRIC with the stateof-the-art schedulers described in §4.1, as well as other schedulers from well-known open-source projects and research
work. llm-d (session) [37] routes requests by session ID; it is
the session-centric baseline described in §4.2. We supply the
session ID reconstructed offline. llm-d (SLO) routes by predicted latency: an online-trained model predicts the TTFT and
TPOT the request would see on each instance, and the request
goes to the instance with the least predicted headroom among
those meeting the SLOs we score against. Other non-opensource schedulers like the Mooncake scheduler [53] follow
a similar rationale. Preble [59] filters instances by KV$ hit
before scoring them: a request whose cached prefix covers
more than half of its prompt goes to the least loaded instance
holding that prefix, and any other request to the instance with
the least estimated work, a linear-combined (BAILIAN-like)
score. We use its implementation in AIBrix [2].

Sensitivity to the two routing hyperparameters

SM ETRIC uses two hyperparameters in Figure 13: SLACK
controls to what extent it can tolerate SLO violations and
HIT_RATIO determines when the local cache is treated as
evicted for the request. Figure 26 conducts a sensitivity analysis on these parameters. SM ETRIC is robust to both as long

by 1.0 % over SLACK from 0.5 to 2 and by 1.9 % over the
whole range of HIT_RATIO, except for the improper values,
e.g., setting SLACK to 0 disables session stickiness (every
follow-up request migrates), while setting it to ∞ completely
ignores the SLO checks.

Related Work

LLM request scheduling. Recent work schedules LLM
requests with KV$-aware, SLO-aware, load-balancing, fairness, and output-length-aware policies [59, 53, 60, 82, 11, 55,
65, 23, 58, 57]. SM ETRIC builds on these policies and derives
agent-session hints for the scheduler without requiring LLM
requests to provide session information. Unlike systems that
co-design serving with agent applications and require applications to expose inter-request structure [33, 39, 73, 13], SM ETRIC operates entirely on the provider side and treats agents as
unmodified clients, matching a typical serving scenario today.
AgentKV [77] also targets agentic serving but learns agent
execution to decide which KV$ to keep; SM ETRIC needs no
learning and infers the session from two indicators the router
already holds.

Conclusion

Agentic serving demands high cluster-wide TPS and makes
KV$ reuse dominant, requiring schedulers to be both loadbalanced and KV$-aware. SM ETRIC achieves the best of both
worlds by first routing requests by session, with session information deduced statelessly at the router, and further deriving
an SLO-aware migration scheme to prevent imbalance caused
by unpredictable session growth. It improves the peak cluster
TPS by 9–15 % under prefill-decode colocation and the peak
prefill TPS by 9 % under disaggregation over state-of-the-art
schedulers, at lower latency.

Figure 27 presents the pseudocode of SM ETRIC under PD colocation. Its high-level structure is similar to the PD-disaggregated
version in Figure 13, with two main PD-colocation-aware changes.
First, we further select the instances that meet the TPOT SLO

instance also executes decodes, which the prefill of the new request
delays. If no instance meets the TPOT SLO, the check is skipped
(line 6). Note that the check only considers the decodes in flight
at the instance, because the number of tokens the new request will
decode is unknown. Second, we adopt the multiplicative score
of LMetric [75] to select the target of load balancing and session
migration (lines 12–13), because in our setup it is the most effective
score that considers prefill and decode in a unified way.

To confirm that the PD-disaggregation results (§5.3) are not specific
to our trace, we repeat them on an open trace, the Codex agent
traces on SWE-Bench Pro [24], which record 610 sessions (20,230
requests) of the Codex coding agent. The trace carries every prompt
and response length but no timestamps, so we sample the think time
between turns from the inter-call delays reported with the dataset.
Its sessions are longer than ours (33 turns on average vs. 2.3) and
reuse more of their prompts (94 % of the prompt tokens are cache
hits, vs. about 80 % in ours). The setup is otherwise that of §5.3.
The results are consistent with §5.3. SM ETRIC achieves the
highest peak prefill TPS, 10 % above Dynamo, the best baseline
(Figure 29 (a)), and the most balanced load after LMetric, which
gives up KV$ reuse for balance (Figure 29 (b)): the busiest instance
holds 2.5× as many requests as the average instance, against 3.1×
or more under the other baselines. It matches or exceeds the best
baseline at every global-tier capacity (Figure 30) and across TTFT
budgets (Figure 32), and delivers the lowest TTFT at both the median
and the tail (Figure 31). LMetric and BAILIAN collapse at a lower
request rate than on our trace, for different reasons: LMetric serves
most follow-ups from the global tier (Figure 30 (b)), and the longer
prompts make each such transfer costlier; BAILIAN weighs KV$
hits far above load, so it keeps sending a session’s follow-ups to its
home even when the home is busy, and the long sessions keep it
busy.
