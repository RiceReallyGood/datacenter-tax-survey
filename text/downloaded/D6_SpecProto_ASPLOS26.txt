Protobuf is a widely used data serialization format, especially
in cloud environments. However, existing compilers generate
only serial decoders, limiting scalability for large datasets.
While parallel parsing has been studied for textual formats
(e.g., XML), parallel decoding of binary formats like Protobuf
remains unexplored, which present unique opportunities.
We propose two techniques to enable parallel Protobuf
decoding. First, we leverage the length-prefixed encoding of
Protobuf to “skim” the binary and identify decoding tasks. To
address inefficiencies caused by many small or imbalanced
fields, we further introduce speculative parallelization, which
partitions a binary into even segments and predicts decoding
states across boundaries. We implement these techniques in
SpecProto, a parallelizing compiler that generates parallel
decoders for a given Protobuf schema. Experiments on realworld and synthetic datasets show that SpecProto achieves
significant speedups by leveraging multiple CPU cores.

Introduction

Protocol Buffers (Protobuf) [7] is a language-neutral and
platform-neutral binary data format for serializing structured
data. It has been widely adopted in cloud environments for
inter-server communications [12] and data storage, such as
Google’s Dremel/BigQuery [20], and serves as the foundation
of gRPC, a leading standard for remote procedure calls.
Binary vs. Textural Serialization. Unlike textual data
formats, such as JSON and XML, that embed attribute names
in the serialized data (e.g., "name":"Alex"), Protobuf avoids
this overhead by enforcing a predefined schema—messages,
which are stored in a .proto file. As illustrated in Figure 1,
given a .proto file, the Protobuf compiler generates a pair
of encoder and decoder in a specified language, for data
serialization and deserialization. Study shows that Protobuf
messages can be up to 10× smaller than equivalent JSON
messages [28] and can perform up to 6× faster than JSON in
Java-to-Java server communications [15].
Besides Protobuf, some other binary serialization formats
include Apache Thrift [29], MessagePack [21], BSON [23],
and Apache Avro [3]. While this work focuses on Protobuf,
some of the issues and ideas could apply to other binary
formats.

Skimming-based Parallelization. Our first attempt is
to leverage the encoded lengths, which makes it possible to
“skip” a field value without examining its bytes and bits in
detail (impossible for JSON or XML). This feature allows us
to quickly skim the Protobuf binary to identify the top-level
fields without decoding them, such as name, age and address
in Figure 2. After that, the extracted fields are decoded in
parallel. With proper pre-memory allocation, their results
can be automatically merged. While reasonable in principle,
this approach has two significant drawbacks.

Parallelization Challenges. The main reason Protobuf
has traditionally adhered to a serial decoding design is the
inherent dependencies in data encoding. When encoding an
in-memory object, its fields are packed sequentially into a
contiguous memory block. Figure 2 shows the encoding of
a Person object according to the schema in Figure 1. Due to
the presence of variable-length fields (e.g., varint, string, or
submessages), determining the starting byte of any given
field (except for the first one) appears impossible without
decoding the entire message sequentially.
One may modify the encoding strategy to facilitate parallel
decoding [4]. However, this change comes with a significant
drawback: the loss of compatibility, which undermines the
viability of Protobuf for inter-server communication.
Prior studies have explored the parallelization of textual
data processing, including XML parsing and querying [10,
19, 24] and JSONPath querying [9]. While these studies offer
valuable insights, Protobuf, as a binary serialization format,
presents distinct opportunities and challenges.
Specifically, existing techniques for parallelizing textual
data rely on explicit structural characters (e.g., braces, brackets, or quotes) to recover parsing context or guide speculation [8, 9, 11]. Such characters are absent in Protobuf’s binary
format. Instead, Protobuf decoding must recover both field
boundaries and field types directly from raw bytes. Moreover,
due to Protobuf’s encoding scheme, the same binary tag may
correspond to multiple field types across different messages,
introducing type ambiguities that are unique to schemaenforced binary formats. As a result, prior approaches for
textual data cannot be directly applied.

• Serial bottleneck. The first phase—skimming, remains
serial and could become a performance bottleneck
when the message contains repeated fields—similar
to an array, it may include many field instances.
• Load imbalance. When the message contains only a
few fields or if their sizes vary significantly, decoding
them in parallel may suffer from load imbalance.
To address these limitations, we propose an alternative
parallelization strategy that removes the need of skimming.
by taking advantage of another property of Protobuf.
P2: Schema-Enforced Encoding. Unlike JSON and XML,
which are known to be “schemaless”, Protobuf (and some
other binary formats) strictly follows a schema for encoding
and decoding. As illustrated in Figure 1, the schema defines
the structures of messages, specifying the type and number
(ID) of each field within the message and its submessages.
Speculative Parallelization. Our second attempt aims to
speculatively start decoding at “intermediate points” within
the Protobuf binary. This may seem extremely challenging,
given that all information is encoded as raw bits (0s and 1s).
However, by leveraging the Protobuf schema specification,
we find it is possible to speculate the decoding state with high
accuracy, thus enabling effective speculative parallelism.
We break down the speculative decoding problem into
two subproblems: (1) tag speculation and (2) type speculation.

2.2 Protocol Buffer
Protobuf was originally developed by Google and became its
most widely used data format [7]. Figure 1 illustrates its basic
workflow. Users begin by defining a schema (i.e., messages) in
a .proto file. This schema is then compiled using the Proto
compiler, which produces an encoder and a decoder in a
specified language. For C++, the compiler generates a class
for each defined message, providing simple accessors for
its fields and methods to serialize the structure into a byte
sequence and deserialize it back into its original form.
Figure 2 illustrates a Person message with an embedded
Address message. A unique field number is assigned to each
field of a message for encoding the field. The field type
and number are encoded into a VARINT, called a tag, based

wire_type (see the table in Figure 2) dictates how to decode
the subsequent value. For example, when wire_type = 0, the
following value is of VARINT type; when wire_type = 2, the
next value has a variable length and the length is encoded

Skimming-based Parallelization

In this section, we present our first attempt to parallelize
Protobuf decoding, by taking advantages of the encoded field
lengths to quickly skim the binary message.
In practice, large Protobuf messages are often composed
of many repeated LEN-type fields. As discussed in Section 1,
LEN-type fields use length-prefix encoding. Based on this, we
propose a two-pass parallelization approach. In the first pass,
the binary data is quickly skimmed to locate the boundaries
of LEN-type fields in the message without decoding any field
values. In the second pass, the identified fields are decoded
in parallel. Figure 3 illustrates this parallel decoding process,
with more details explained in Algorithm 1.
Step 1: Skimming. The first pass is handled by the Skim()
function. Given the binary data, it begins by reading the tag
(Line 5) and then decodes it according to Protobuf’s field
encoding logic, resulting in the field number and wire type.
The function then calculates the length of the field value
based on the wire type (Lines 8-12). Next, it records the start
and end positions of the field value, which defines a decoding
task, and groups them by field number (Line 13). Then, it
jumps over the field value based on its length and proceeds
to the next tag, until it reaches the end of the binary.

Note that a similar skimming approach can also be applied
to parsing textual data formats, like XML and JSON, however,
the skimming overhead would be significantly higher, as
textual data lacks length encoding. Thus, skimming must
examine the text character by character, creating a serious
issue that may outweigh the parallelization benefits [19].
Limitations. Two critical assumptions must hold to make
skimming-based parallelization effective. First, the binary
message should contain a moderate number of fields—too
many fields can slow down skimming, exacerbating the serial
bottleneck, while too few may not yield enough decoding
tasks to fully utilize the CPU cores. Second, the field sizes
should be relatively balanced to prevent any single task from
disproportionately dominating the total parallel decoding
time. To address the above limitations, we next introduce an
alternative approach that offers more flexible parallelism.

Step 2: Memory Allocation. Once these decoding tasks
(field values) are collected, memory must be allocated to store
the results of the subsequent parallel decoding. To deal with
the memory allocation for repeated fields, we group tasks by
field such that the size of each field group corresponds to the
final size of the decoded list, and the order of tasks within a
field group determines their indices in the decoded list.
Step 3: Parallel Decoding. Finally, the whole collection
of decoding tasks is processed by ParallelDecode(), which
is a method of the Person class. ParallelDecode() sets the
fields of the class by calling each field’s corresponding (serial)
decoding function, such as ReadString() and address.Parse().

A Motivational Example. Figure 4 illustrates a binary
message split into two chunks. The first chunk starts with
byte “0A”, which, by tag encoding, denotes a LEN-type field
with field number 1. This corresponds to the top-level field
name, providing a clear initial decoding state.
However, initial decoding state for the second chunk is
less obvious: is its first byte (“05”) the start of a valid tag? If
so, to which field does it correspond? This ambiguity arises
because preceding fields might have variable lengths, causing
arbitrary partitioning boundaries to potentially fall in the
middle of a field. Moreover, correctly speculating the first tag
and type alone does not guarantee that the decoding state for
subsequent fields will become clear. As decoding proceeds
further into the chunk, similar ambiguities can repeatedly
occur, requiring ongoing speculation.
In the following, we will demonstrate that it is possible to
effectively speculate on the decoding state(s) by leveraging
structural information embedded in the .proto file. For better
illustration, we decouple the decoding-state speculation into
tag speculation and type speculation.

4.1.1 Tag Pool DFA. Deterministic finite automaton (DFA)
is a classic way for identifying string patterns in textual data.
In this work, we draw an analogy between binary tags and
words in textual content. Specifically, we treat each byte in
an encoded Protobuf message as a character in an alphabet,
allowing us to interpret tags from the tag pool as the “words”
to be matched within this byte stream. We refer to this DFA
for matching tags in a tag pool as the Tag Pool DFA.
Definition 4.2. Given a Protobuf schema S, its Tag Pool
DFA is a five-tuple 𝐷 = (𝑄, Σ, 𝛿, 𝑞 0, 𝐹 ) where:
• 𝑄 is a finite set of states, representing the matching
progress of valid tags defined in T (S).
• Σ is the input alphabet consisting of all possible values
of individual bytes (0x01 to 0xFF).
• 𝛿 : 𝑄 × Σ → 𝑄 is the deterministic transition function
mapping a state and an input byte to the next state.
• 𝑞 0 ∈ 𝑄 is the initial state—no input yet matched.
• 𝐹 ⊆ 𝑄 is the set of accepting states, each indicating a
complete match of a valid tag in T (S).

4.1 Tag Speculation
Recall the question in decoding the second chunk in Figure 4:
Could “05” represent a valid tag? In theory, any byte value
between 0x01 and 0xFF could appear as part of a valid tag.
However, given the schema defined in Figure 1, “05” cannot
be part of a valid tag. To systematically answer this question,
we need to find out what tags are possible for a given schema.
According to Protobuf encoding, each field has a unique
field number, which, combined with a wire type, forms a
binary-encoded identifier—a tag. Given a Protobuf schema,
we can infer all of its valid tags, referred to as its tag pool.

By transitioning through DFA states based on each input
byte, valid tags can be efficiently detected. For example, the
tag pool DFA in Figure 5-(b) can recognize “05” as an invalid
tag, while correctly identifying the next byte “1A” as valid.
Algorithm 2 outlines the process of generating a tag pool
DFA for a given Protobuf schema S. The construction starts
by first encoding each field’s valid tag (determined by its
field number and wire type) into VARINT format, and then
inserts each encoded tag into the DFA.

Definition 4.1. Given a Protobuf schema S, its tag pool
T (S) refers to the set of all unique tags that may appear in
the encoded message, as determined by the schema.

4.1.2 Fake Tags and Tag Speculation. It is critical to
note that the tags identified by the tag pool DFA are valid
tags but not necessarily actual tags because the field values
may contain bytes that resemble valid tags.

Considering the example in Figure 2, we have T (𝑃𝑒𝑟𝑠𝑜𝑛) =

4.2.2 Type Transition Automaton (TTA). The intuition
behind this automaton is to capture the “following relation”
between types in the encoded data. For example, given that
the last decoded field is an Address, the automaton is able
to determine which field types could validly follow next. A
formal definition is given below.
Definition 4.6. The type transition automaton (TTA) of a
schema S is defined as a 4-tuple 𝑀 = (𝑄, Σ, 𝛿, 𝑞 0 ) where:
• 𝑄 is a finite set of type states. Each type state, except
for 𝑞 0 , represents a unique field type specified in S.
• Σ is the input alphabet, consisting of all valid tags
derived from the schema, that is, the tag pool T (S).
• 𝛿 : 𝑄 × Σ → 2𝑄 is the transition function, which maps
a type and a tag to a set of possible successor types.
• 𝑞 0 ∈ 𝑄 is the initial state, representing cases where no
type information is yet known.

be added between the two type nodes.

4.2.4 Optimizations. We next discuss some opportunities
to boost the effectiveness of speculative decoding in practice.
O1: Type Prioritization. During type speculation phase,
if multiple candidate types are possible, we prioritize them
based on the following two heuristics:
• Prioritizing Submessage Types: Compared to more
generic types (such as string or uint64), submessages
impose stricter constraints on byte sequence structure.
Selecting them increases the likelihood of detecting
misspeculation earlier if the choice is incorrect.
• Prioritizing Self-Transitions: If the last recognized
field is a submessage T and T is among the candidate
types, we prioritize T. This is based on the observation
that repeated submessage fields often dominate the
data and occur contiguously in the input. Favoring the
same state improves speculation accuracy.
O2: Maximum-Cost Constraint. When a chunk begins
in the middle of a large string field or a field containing a
long sequence of raw bytes, the backtracking algorithm could
spend a large portion of its time speculating tags and trying
various candidate types. The speculation cost can accumulate
quickly, degrading the overall performance. To address this,
we impose an upper bound on the accumulated number of
bytes accessed during speculative decoding for each chunk
(e.g., 1.1× of the chunk size). Processing of the remaining
chunk bytes will be deferred until the merge phase.

Implementation

Based on our proposed techniques, we prototyped a proto
compiler in Python, called SpecProto. SpecProto generates
a parallel decoder in C++ for a standard Protobuf schema.
Given a Protobuf binary data file, the decoder returns an
in-memory object corresponding to the original message. It
supports two parallelization modes: the speculative mode
(see Section 4) and the non-speculative mode which uses the
skimming-based parallelization (see Section 3).
SpecProto uses Jinja [26] as its templating engine for code
generation. Given a schema and a parallelization mode, it
produces a header and an implementation file containing
the schema-specific parallel decoding logic. Each message
in the schema corresponds to a C++ class. Scalar fields are
stored using C++ primitive types, string fields are stored
as std::string, repeated fields are stored in std::vector,
and submessages are represented as pointers to instances
of their respective types. In practice, users may modify the
templates used in SpecProto to adopt custom data structures
to accommodate their specific use cases.

Evaluation

In this section, we evaluate the performance of the parallel
decoders generated by SpecProto. Note that their correctness
has also been thoroughly tested and verified.
6.1 Methodology
We evaluate both the speculative and non-speculative modes
of SpecProto and compare their performance against serial
decoding, which serves as our baseline. For reference, our
baseline runs about 2–4× faster than the standard protoc
compiler (Protocol Buffers v23.4, proto3) [7], which offers
more features, including arena allocation for memory management, unknown fields preservation, advanced language
features (e.g., map and oneof), UTF-8 validation, and has a
significantly larger codebase. We believe that most of these
features are orthogonal to our parallelization techniques.
One exception is unknown fields preservation in the speculative mode, since the speculative mode examines valids
tags during the decoding phase.
For the schemas under our evaluation, the encoders and
decoders (which share code) generated by protoc have an
average size of 13442 lines. In comparison, our sequential
decoder has an average size of 1574 lines, and our parallel
decoders have average sizes of 6503 lines (spec) and 2558
lines (non-spec).

When speculation mode is enabled, SpecProto generates
the tag-pool DFA and TTA, stored in the implementation file,
along with the speculative decoding workflow. The DFA and
TTA are shared among worker threads. For the root message,
a corresponding speculative decoding method is generated,
which executes the three steps described earlier: partitioning,
speculative decoding, and merging with validation. Each
message implements a merge method to combine the results
of speculative decoding. This is necessary because when a
submessage is partially truncated, its merge method must be
invoked to complete the partial decoding. For all messages,
a sequential parsing method is generated. In particular, the
first thread uses the sequential parsing method for the root
message to parse a partial message. All threads except for
the last one may use the sequential parsing method to parse
a partial message and cause the truncation point.
In non-speculative mode, a serial parser is generated for
each message, except for the root message, which employs
the two-pass parallelization approach.

6.2 Overall Performance
Execution time. Table 2 reports the end-to-end decoding
time of evaluated methods while Figure 11 visualizes the
speedups relative to the baseline. The results show that both
non-spec and spec modes of SpecProto exhibit significant
speedups over the baseline on almost all datasets, with the
only exception being non-spec on the TT dataset.
More specifically, SpecProto non-spec achieves speedups
ranging from 1× to 6.7× (3.8× on average), while SpecProto
spec achieves speedups from 3.7× to 6.2× (4.9× on average).
We will study the causes of speedup variations in Section 6.3.

Top-Level Fields. In MAP and SYN2 datasets, the number
of top-level fields is limited and their sizes are similar, in
which case spec and non-spec perform similarly. When there
are a large number of top-level fields (PROF, PRD, and SYN3),
non-spec quickly loses due to the serial bottleneck in the first
pass. Additionally, non-spec cannot achieve any speedup on
the TT dataset because this dataset has only one large field at
the top level, which means that during the parallel decoding
phase, only one thread can be used.
Based on the results of the experiments on two specially
synthesized datasets, SYN2 (𝑑 = 55) and SYN3 (#msg = 61), we
did not observe that the deep nesting depth or large number
of message definitions posed any unique challenges for the
two parallelization algorithms.

Memory Overhead. The memory cost is important when
parsing a single large message. Table 2 presents the memory
footprints of different methods in the parsing process, which
mainly consists of two parts: the binary data and the parsed
results. Due to the presence of the VARINT type, the memory
occupied by the parsed results is often greater than that of
the original binary data. For most of the datasets, there is no
significant difference in memory cost among the different
methods when using 1 to 16 threads. For the PROF dataset,
SpecProto consumes more memory than the baseline, especially for non-spec. This is because a very large number of
objects are allocated simultaneously by all threads, which increases memory retained in the allocator’s per-thread caches
and leads to a higher peak memory overhead.

Table 3 reports the number of bytes re-parsed during the

overlap substantially with submessage data, the chances of
misspeculation can increase significantly.

Related Work

In this section, we review prior work on parallel processing
of serialized data and discuss how our techniques may extend
to other binary serialization formats.
Parallel Processing of Textual Data. Extensive research
has explored parallel querying over raw textual data formats
such as JSON, XML, and CSV, with most solutions built on
formal querying models like NFAs or DFAs. For instance, to
enable parallel XPath querying, Ogden et al. [24] proposed
parallel pushdown transducers (PPT), which evaluate all
possible query states simultaneously when processing an
XML partition. Jiang and Zhao [10] improved PPT efficiency
by pruning infeasible states using the XML schema.
Prior works on accelerating JSON processing has largely
focused on exploiting bit-wise and byte-wise parallelism.
For example, Mison [17] builds bitmap index for large JSON
records, while Pison [8] improves the indexing scalability by
employing multiple cores. simdjson [16] employs bitwise and
SIMD operations to validate and tokenize JSON data prior
to building a parse tree. JPstream [9] leverages speculative
streaming to evaluate a JSONPath query in parallel. Finally,
JSONSki [11] utilizes bit-parallelism to fast-forward over
irrelevant data during streaming query matching.
While not directly applicable, the “divide and conquer” and
state speculation strategies from the above works inspired
the approaches proposed in this work.

Benefits of Type Prioritization. Figure 13 compares the
execution time with and without type prioritization. The
results indicate that this optimization is critical for most
datasets. Without the heuristics for candidate type selection,
it would take backtracking many more attempts to find the
correct type. Furthermore, in the merge phase, validation
failures led to expensive redos. A good type prioritization
heuristics can help determine a tag’s type more quickly and
reduce the likelihood of validation failure.

Acceleration of Protobuf. Existing research has explored
hardware-based approaches. Early efforts such as UDP target
ETL workloads by accelerating data transformation using

programmable hardware [2]. More recently, Optimus Prime
proposes a general-purpose accelerator for serialization and
deserialization by exploiting field-level parallelism within
message schemas [27]. One study proposes a near-core accelerator that combines specialized execution units with
optimized memory and layout representations [13]. Another
offloads Protobuf deserialization to SmartNICs, exploiting
message-level parallelism across NIC cores and pipelined
execution with host computation [1].
In software, Google’s µpb provides a high-performance C
decoding runtime that uses table-driven parsing and arenabased memory management to reduce per-field dispatch and
allocation overhead, but it remains largely single-message,
single-core in nature [6].
As far as we are aware, no previous research has explored
parallelizing the decoding of a single serialized binary.

Possible Extension to Other Binary Formats. Given the
similarities among binary data formats, some of our parallel
decoding ideas proposed for Protobuf could be extended
to other formats. For instance, Thrift is also schema-based,
like Protobuf, with explicit field types and identifiers. Our
speculative decoding method can be directly applied to Thrift
by identifying the type and field ID, speculatively decoding
fields, validating the speculation, and merging the correct
parses. Our skimming-based decoding cannot be applied to
Thrift, as it does not encode the byte length in the binary
data for types such as lists and structs.
For schema-less formats such as MessagePack and BSON,
our skimming-based decoding method is applicable, thanks
to the encoded length information. However, speculative
decoding requires strict schemas, which often times are not
available for such types of data formats.

Conclusion

This work tackles a fundamental issue in Protobuf decoding—
encoding-induced dependencies that limit parallelism. To
address this issue, it presents two methods: skimming-based
and speculative parallelization. Skimming exploits the lengthprefixing design of Protobuf to find independent decoding
tasks, while speculative parallelization cuts the binary into
even chunks and leverages schema constraints to infer the
decoding state for each chunk. Evaluation based on real and
synthetic datasets shows that both parallelization methods
deliver substantial speedups on multicore CPUs.

A.5 Experiment workflow
Clone the repository and move it to the desired directory.
Generate and build the code. Execute the compiled binaries
with the available datasets. README.md provides step-by-step
instructions for running the experiments.

A.3.3 Software dependencies. We recommend running
the artifact on Rocky Linux 8, though similar Linux systems
should also work. We provide a script to install the necessary
dependencies (e.g., Protobuf).
A.3.4 Datasets. We include links to the necessary datasets
in our artifact.

A.6 Evaluation and expected results
We provide the necessary commands to generate the figures
and tables presented in the evaluation section. The results
should be similar to those reported in our paper.

A.4 Installation
The artifact has been tested with G++ 9.2.1 and CMake 3.26.4.
Other compatible versions may also work. Compilation and
execution scripts are provided in the repository. Detailed
instructions can be found in README.md.

A.7 Experiment customization
Users can add new datasets and schemas and place them in
dataset/ and schema/, respectively. Then run the relevant
commands (see the examples in README.md).
