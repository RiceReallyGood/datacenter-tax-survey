Abstract—RDMA has been widely used in modern data centers
because it can provide low-latency and high-bandwidth network
communication for distributed applications. However, how to
build an efficient RDMA-based RPC framework is still challenging. We observe that existing work may have the following
problems: First, the lack of a serialization module makes the RPC
framework difficult to use, and cannot further be optimized by
overlapping serialization and network communication. Second,
CPU resources are ignored to scale out instead of focusing on QP
and memory resources, which may result in the RPC framework
not being scalable. In this paper, we propose LightRPC, which
provides users with easy-to-use and portable interfaces via a
new resource abstraction and achieves efficient performance
through co-design of serialization and communication, usage of
pre-registered memory, and adaptive polling mode. Compared to
bRPC’s IPoIB and RDMA modes, LightRPC improves throughput by about 2.5x and 1.5x, respectively, and has lower median
and tail latency.
Index Terms—RDMA, RPC, Scalability

I. I NTRODUCTION
As an important high-performance network technology,
RDMA has the features of kernel bypass and CPU offloading,
thereby enabling low-latency and high-throughput network
communication. Due to its excellent performance, RDMA
has been widely used in distributed applications such as
storage systems [1], transaction processing systems [2], and
deep learning systems [3]. At the same time, except for
scenarios where collective communication is required, most
distributed applications use an RPC runtime to achieve more
flexible point-to-point communication. The RPC programming
model abstracts data interaction into function calls, hiding the
underlying communication details so that users only need to
care about the data to be sent and received, so its semantics
are quite simple.
In fact, collective communication libraries such as OpenMPI
and NCCL already have provided mature RDMA functions.
However, there is still lacking of sophisticate RDMA-based
RPC framework in the industry. In the past time, there has been
a lot of research work on implementing RPC based on RDMA.
They achieve high performance by selecting appropriate transmission modes and RDMA operations, and some of them
make efforts to solve the non-scalability problem of RDMA.
We summarize some reasons why these frameworks are not
actually used: (1) Most frameworks do not have a serialization

module, such as eRPC [4] and Flock [5]. This will bring about
two problems: First, users may need to implement serialization
by themselves, leading to increasing the burden of program
refactoring. Second, collaboratively optimizing serialization
and communication can not be implemented. (2) Some work
ignores the management of CPU resources when reducing QP
or memory usage. For example, RFP [6] requires the client to
continuously use READ operations to obtain RPC responses,
resulting in a waste of client CPU resources. RFP will not be
available when there are multiple connections between client
and server. As another example, ScaleRPC [7] assigns a busy
polling thread to each client on the server side. When there
are many clients, the CPU resources of the server will be
exhausted.
Therefore, we design an efficient and easy-to-use RDMAbased RPC framework called LightRPC. We propose the following designs for resolving the existing problems: (1) Design
a serialization module and setup pre-registered memory for
message transmission. By serializing data objects directly
into pre-registered memory, we achieve zero copy of usermode memory. By implementing a lock-free queue to manage
memory blocks, we achieve efficient application and return in
high-concurrency scenarios. (2) We design an adaptive polling
mode for the server. When no RPC requests arrive, the polling
thread is in a blocked state, thus saving CPU resources. Once
an RPC request arrives, the polling thread switches to the busy
polling state to quickly sense the request and process it. (3)
We provide users with simple interfaces by a new resource
abstraction. Users can build RPC endpoints and make RPC
calls with only a few lines of code. In conclusion, this paper
mainly makes the following contributions:

II. BACKGROUND AND C HALLENGES
In this section, we first introduce RPC and RDMA, then
discuss the key points of implementing an easy-to-use and
efficient RDMA-based RPC framework.
A. Datacenter RPC
RPC allows the machine to call functions on the remote
machine just like calling local functions. Therefore, users only
need to complete the logical implementation of the function
body and do not need to pay attention to the underlying
communication details. This simple and flexible programming
semantics makes it widely used in modern distributed systems.
However, the mainstream open source RPC frameworks in
the industry are usually implemented based on the TCP/IP
protocol stack. For example, gRPC and Apache Thrift do not
have native RDMA support [8], which prevents them from
fully utilizing the performance of hardware such as high-speed
NIC in high-performance clusters.
A typical RPC framework mainly consists of a client, a
server, and their respective stubs, which serialize and deserialize RPC requests/responses. The serialization phase is to
convert the data object into a byte array, and the deserialization
phase is to restore the byte array into a data object [9].
Of course, the serialization module will add some system
overhead, especially when the data object itself is a byte array.
Therefore, some research focuses on designing communication
libraries based on application scenarios instead of directly using the RPC framework. However, the serialization module can
parse custom structured data, has cross-platform features and
good flexibility, so it is indispensable in common scenarios.

in advance. Each time the memory is registered, a pair of

access. Applications use various verbs operations by posting
work requests (WR) into the QP. Among them, SEND/RECV
are called two-sided operations. Before the sender posts a
SEND WR to SQ, the receiver needs to post a RECV WR
associated with a block of memory to RQ in advance. After
RNIC receives the message, it writes it into this memory.
WRITE/READ are called one-side operations. After the sender
obtains the address and rkey of the remote memory, it
can directly read and write the memory. Since each SQ and
RQ needs to be bound to a completion queue (CQ), when
the WR is executed by the RNIC, the RNIC will write a
completion event (CQE) to the CQ. The application can know
the execution status of the WR by obtaining the CQE.
RDMA provides three transmission modes: reliable connection (RC), unreliable connection (UC) and unreliable datagram
(UD). Their main differences are as follows: (1) RC guarantees
that data transmission is correct and reliable, but UC/UD
does not. (2) RC/UC needs to establish a connection before
communication and can only conduct one-to-one interaction.
UD does not need to establish a connection, and one QP can
interact with multiple QPs. (3) As shown in table I, these three

B. RDMA Programming Model
The use of RDMA is usually based on the InfiniBand
protocol or the RoCEv2 protocol. Since the latter is compatible
with Ethernet and requires lower hardware configuration, it
has been widely used in modern data centers. RDMA can
achieve hundreds of Gbps bandwidth and microsecond-level
communication latency mainly due to its following two features: (1) Kernel bypass: Bypassing the OS kernel during
data transmission avoids the overhead of data copying and
context switching between user mode and kernel mode, and
has very low latency. (2) CPU offloading: The local machine
can directly access the memory of the remote machine and
does not require the participation of the remote CPU, resulting
in higher throughput.
RDMA builds a series of abstractions and interfaces for
communication, which applications can use through user-mode
libraries such as ibverbs and rdmacm. Specifically, communicators establish connections and communicate through a
queue pair (QP). QP consists of a send queue (SQ) and a
receive queue (RQ). RDMA allows different QPs to share a

C. Design Challenges
How to better use the RDMA programming model in the
RPC framework, we need to pay attention to the following
questions: (1) How to choose the transmission mode and
RDMA operation? (2) How to reduce the overhead caused
by serialization? (3) How to obtain CQE? That is, sensing
the completion of the send operation and the arrival of the
remote message. (4) How to design a thread pool to handle
heterogeneous function calculations?

C. Thread model

A. Resource Abstraction
In terms of design, one of our main ideas is resource
abstraction. We define the following two resource types:
• UniqueResource (UR): A unique resource for client
use. It includes QP, SEND/RECV CQ, completion event
channel, and pre-registered memory.
• SharedResource (SR): A shared resource for server use.
Instead of a QP, it contains an SRQ and the rest of the
resource types are the same as the UR.
Among them, SR allows different connections within the
server process to share system resources. Taking the RDMA
queue resource as an example, as shown in Figure 1, all QPs
use the same RQ, that is, SRQ. Then, the SRQ is bound to
the RECV CQ. Each SQ has its own SEND CQ.
Through resource abstraction, LightRPC has very convenient user interfaces. As shown in the code shown in Figure
2, when the user creates a server or client object, it must be
bound to an already created resource object. In addition, users
can set parameters such as the size of pre-registered memory
and the number of worker threads.
B. Message Transmission
We implement two-side operations to build LightRPC. This
is because one-side operations often require additional information interaction. For example, the sender
needs to know the

address and rkey of the receiver’s memory, and bypassing
the CPU is sometimes not what the receiver wants, etc. These
problems may need to be solved through multiple round-trip
times (RTTs), resulting in higher latency.
We call the byte array obtained by serializing a data
object a message. We make an important observation about
how to efficiently transmit a message: Pre-registered memory
can improve the efficiency of message transmission. This is
because, in non-inline mode, the memory read by RNIC must
be registered. To meet this condition, we propose two methods:

In LightRPC, we mainly set up two types of threads, and
their functions and relationships are shown in the Figure 3.
Below we introduce them in detail.
Polling thread, used to obtain CQE from RECV CQ, that
is, to sense the arrival of remote messages. In fact, RDMA
provides two ways to obtain CQE: (1) Busy polling: The
polling thread quickly obtains CQE in CQ by continuously
calling ibv_poll_cq. This method has very low latency,
but when no CQE is generated, it will cause a waste of CPU.
(2) Event notification: After CQ is bound to a completion
event channel, the generation of CQE will generate an event
in the channel. The polling thread will obtain events through
the blocking interface ibv_get_cq_event. When no event
occurs, the polling thread enters the blocking state until it is
awakened when a CQE is generated. Therefore, this method
saves CPU resources, but the latency is relatively high. We
combine the advantages of both and design an adaptive polling
mode. First, at the client, due to the low latency of the RDMA
network, the client directly senses the arrival of the response
through busy polling after sending the RPC request. Secondly,
on the server side, since we do not know when client requests
will arrive, if we always use busy polling, it will cause a
waste of CPU. On the contrary, if we always use the event
notification mode, in the case of intensive requests, frequent
interruptions can lead to inefficiency. Therefore, we first let
the polling thread work in event notification mode. Once a
request arrives, it switches to busy polling mode. If the busy
polling does not get the request for a certain period of time,
it switches to event notification mode again to save CPU
resource. Note that for CQE in SEND CQ, the sending thread
calls ibv_poll_cq to obtain it after sending the request.
Worker thread pool, used for server-side RPC request processing. In terms of design, we allow each worker thread
to have an independent task queue to avoid excessive lock
competition caused by all worker threads sharing the task

D. Memory Management
Since memory registration is very time-consuming, if the
memory needs to be temporarily registered to send any message, the communication latency will be greatly increased,
so we provide pre-registered memory for the sending and
receiving of messages. Specifically, the client will pre-register
two memory blocks of size T, one for sending messages and
the other for receiving messages. The server will register a
memory pool and divide it into many blocks of T bytes. We
use a lock-free queue to store the address of each Block to
achieve high-concurrency application and return.
In terms of memory resource recycling, we use two methods
to handle it: (1) For the block that stores the received message,
the receiving thread actively returns it after acquiring the
message. (2) For the memory that stores sent messages, since
ibv_post_send is asynchronous, we need to sense that
the block has been used by polling the CQE in SEND CQ. In
fact, the address of the block where we store the message is
recorded in the wr_id field of ibv_send_wr, so that when
we obtain the CQE, we can easily obtain the memory address
through the wr_id field of ibv_wc and return it.

B. Experimental Results
Throughput: As shown in the figure4, as the number of
connections increases, the throughput gap between LightRPC
and bRPC gradually increases. This is mainly due to the fact
that LightRPC not only has better performance for single
connection, but also has better scalability. It is worth noting
that LightRPC reaches maximum throughput at 32 connections, and bRPC stabilizes at 80 connections. Finally, when
the message size is 64B, the throughput of LightRPC is 2.5x
and 1.4x that of bRPC-IPoIB and bRPC-RDMA respectively.
When the message size is 4KB, it is 4x and 1.2x respectively.
Latency: Figure 5 and Figure 6 show the changes in median
latency and P99 latency respectively. It can be seen that as the
number of connections increases, the median latency and P99
latency of bRPC continue to increase, and there is no stable
trend (except when the message size is 4KB, bRPC-IPoIB
finally reaches stability), but the latency of LightRPC increases
relatively slow and reaches stability after 32 threads. This is
mainly because in high concurrency situations, LightRPC’s
polling thread will automatically work in busy polling mode,
and message sensing is very fast, while bRPC always uses
event notification mode. Finally, taking the 64B message as an
example, the tail latency of LightRPC is only 13% of bRPCIPoIB and 28% of bRPC-RDMA.
