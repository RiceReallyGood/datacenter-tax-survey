## 0. 先把名词说清楚

下面这些词在后文反复出现。第一次读建议先过一遍，后面遇到再回来查。

**关于 Agent 本身**
- **Agent（智能体）**：一种程序，让大模型自己决定下一步做什么，并且能调用"工具"——运行命令、读写文件、上网搜索、操作浏览器——来完成一个任务，而不是只回答一句话。编码 Agent 的代表是 Anthropic 的 Claude Code 和 OpenAI 的 Codex，它们在开发者的终端里改代码、跑测试。
- **会话、请求、步**（TraceLab [56] 的定义，本文沿用）：用户打开 Claude Code 到关掉，是一个**会话**；用户在会话里每输入一句指令，是一次**请求**；Agent 处理一次请求要循环很多轮，每轮"调用一次模型 + 执行模型要求的工具"叫一**步**。一个请求里第一步是用户触发的，后面的步都是工具结果触发的，直到模型说"做完了"。
- **工具调用**：模型在输出里写"请运行这条命令 / 请读这个文件"，Agent 程序照做并把结果塞回给模型。Bash（运行 shell 命令）、Read（读文件）、Edit（改文件）都是工具。
- **沙箱**：把不可信代码（Agent 生成的命令）关在一个隔离环境里运行，防止它碰到不该碰的东西。有三个档次：**进程级隔离**——只是限制一个普通进程能访问哪些文件和网络（Linux 的 bubblewrap、seccomp、Landlock，macOS 的 Seatbelt），几乎没有启动开销；**容器**——Docker 这类，共用宿主机内核；**微虚拟机（microVM）**——Firecracker 这类，有独立内核，最安全也最重。**gVisor** 是一种特殊容器：它在用户态重新实现了一个内核来接管程序的系统调用，隔离好，但系统调用很慢。
- **系统调用（syscall）**：程序请操作系统办事的接口，比如打开文件、创建进程、读写网络。工具调用几乎全靠系统调用完成。
- **MCP**：Model Context Protocol，Agent 调用**外部**工具服务器的标准协议，消息格式是 JSON-RPC，本地服务器通过子进程的 stdin/stdout 传输、远程服务器走 HTTP。市面上有两万多个 MCP 服务器（比如 GitHub、文件系统、浏览器）。**注意：Claude Code、Codex 的内置工具（Bash、Read、Edit 等）不走 MCP**——模型在 API 响应里返回一个 tool_use JSON 块，Agent 进程自己解析、自己执行（起子进程、读文件），结果拼进下一次请求；主路径上没有任何进程间协议。
- **云开发机 / 云桌面 / CDE**：开发者的整套开发环境（操作系统、代码、工具链）跑在数据中心的一台虚拟机或容器里，本地电脑只显示画面或连编辑器。国内叫研发云桌面（华为云 Workspace、深信服等），国外叫 cloud development environment（GitHub Codespaces、Gitpod、Coder）。Agent 在这种环境里跑时，它的每次命令和文件操作都落在数据中心的 CPU 服务器上。
- **RL rollout**：强化学习后训练时，让模型批量跑成千上万个 Agent 任务来产生训练数据。它是 Agent 循环的"批量版"：没有人停顿，每个任务一个沙箱，用完即弃。

**关于大模型推理**
- **token**：模型处理文本的最小单位，大约是 3/4 个英文单词或 1–2 个汉字。本文按 **1 token ≈ 4 字节文本**换算（英文散文的经验值；代码略少）。
- **tokenize / tokenizer**：把文本切成 token 的过程 / 程序。切分规则由模型厂商定，同一段文本不同模型切出来不一样。**BPE** 是主流的切分算法（第 3.7 节解释）。
- **上下文**：每次调用模型时发给它的全部内容——系统提示、对话历史、工具返回的结果。Agent 的上下文通常十万 token 量级。
- **prefill 和 decode**：模型先把整个输入读一遍（prefill，算力密集），再一个 token 一个 token 地生成（decode，访存密集）。
- **KV 缓存**：模型读过的上下文会留下中间状态，叫 KV 缓存，占显存或内存。**前缀缓存**：同一会话下一次调用时，上下文前面没变的部分可以直接复用上次的 KV 缓存，不用重算；复用成功叫"命中"。命中率越高，NPU/GPU 省得越多。
- **TTFT（首 token 延迟）**：从发出请求到收到第一个字的时间。用户最敏感的指标之一。
- **RAG、embedding、向量检索**：把文档变成一串数字（向量，也叫 embedding），提问时也变成向量，用向量相似度找最相关的文档，再交给模型回答——这套流程叫 RAG。"向量检索"就是在几百万个向量里找最相似的几个，是 CPU 和内存带宽密集的活。

**关于硬件与库**
- **CPU:GPU 比**：一套服务器里 CPU 颗数比 GPU 颗数。传统 8 卡 GPU 服务器是 2 颗 CPU 配 8 颗 GPU，即 1:4；训练集群常见 1:8。
- **BOM**：整机物料清单，也就是一台服务器的成本由哪些部件构成、各占多少。
- **核时（core-time）**：一个 CPU 核忙碌的时间。8 个核同时忙 1 秒，是 8 核秒。文中"每请求 X 毫秒核时"指处理一个请求要占用一个核 X 毫秒。
- **NEON、SVE、SVE2**：Arm 的向量指令集。NEON 是固定 128 位宽的老指令；SVE 是可变宽度的新指令；SVE2 在 SVE 上又加了字符匹配、直方图等指令（`MATCH`、`HISTCNT`），对文本处理有用。鲲鹏 920 只有 NEON。
- **KAE**：鲲鹏片上的硬件加速引擎，做加解密（SEC/HPRE）和压缩解压（ZIP）。**KML**：鲲鹏数学库（BLAS、FFT、稀疏矩阵）。**zswap**：Linux 的一个机制，把不常用的内存页压缩后仍留在内存里，相当于把内存"变大"。
- **均值 vs 中位数**：Agent 数据的长尾非常重，均值常被少数极端值拉高。文中两者都给时，中位数更能代表"典型情况"。

### 1.2 大盘有多大

**IDC 的口径（硬件采购额）。** 2026 年第一季度，全球为 AI 负载采购的服务器和存储合计 **897 亿美元**，比去年同期增长 33.1%，和上一季度持平；其中服务器 876 亿（97.6%），存储 22 亿。IDC 把 2026 全年预测上调到 **4,970 亿美元**（比 2025 年增长 56%），2030 年 1.21 万亿，五年复合增速约 30%。地区上美国占 75.7%，中国 78 亿美元占 8.7%。平台上，带加速卡的服务器里 **Arm 平台 530 亿已经超过 x86 的 346 亿**（从 2025 年第四季度开始反超，原因是英伟达 GB200/GB300 机架自带 Arm 架构的 Grace CPU）。IDC 还特别提到一类**不带 GPU** 的 AI 需求在增长："AI 编排工具、数据流水线、CPU-only 推理集群"，但没有单独给金额 [81]。

**Gartner 的口径（所有 AI 相关支出）。** Gartner 说 2026 年全球 AI 支出 2.67 万亿美元，其中"AI 基础设施"1.48 万亿——这个数比 IDC 大三倍，因为它把云服务收入、网络设备、半导体都算进去了，不是同一个东西。对本文更有用的是它单列的 **"AI Agent 与助手"软件：2026 年 292 亿美元，比 2025 年增长 77%，2027 年 655 亿**。这是软件收入，不是硬件 [81]〔二手〕。

**TrendForce 的口径（出货台数）。** 2026 年 AI 服务器（带加速卡的）出货量增长 28%，全部服务器增长 12.8%；AI 服务器里 GPU 方案占 69.7%、定制 ASIC 方案占 27.8%。它还观察到：谷歌和微软在**增购普通服务器**来承担 Copilot、Gemini 推理流量的前处理、后处理和存储 [81]。

**中国。** 2025 年中国 AI 服务器市场 259 亿美元，增长 36%；按用途分，**推理服务器占 67%，训练占 33%**。2025 年上半年加速服务器 160 亿美元，同比翻倍，其中非 GPU 加速卡占 30% [81]〔二手〕。

### 1.3 Agent 占了多少推理流量

这个问题以前没有数据（`INSIGHT_AI_WORKLOAD.md` 2.3.6 承认"没有 fleet 级占比"）。现在 OpenRouter 给了一个可用的替代口径。

**OpenRouter 是什么、怎么统计。** 它是一个转发平台，开发者通过它调用 400 多个模型。它把 2025 年全年经手的 100 万亿 token 写成了论文 [79]。分类方法：用分类器给每条请求打"编程 / 角色扮演 / 翻译 / 科学…"标签（2025 年中才加的功能，所以分类数据只覆盖下半年）。"Agent 流量"的判定是按接入应用的类型（比如 Cline、Roo Code 这类编码 Agent 应用）。样本偏差：经它转发的多是开源模型和开发者流量，Anthropic、OpenAI 的第一方 API 调用不经过它。

**数字。**
- **编程类 token 从 2025 年初的约 11% 涨到年底的 50% 以上**（分母是平台全部 token）。
- 平均每次请求的输入从 1,500 token 涨到 6,000 以上（4 倍），输出从 150 涨到 400（3 倍）；编程类请求的输入是普通请求的 3–4 倍长。
- 论文原话："中位的 LLM 请求已经不是一个孤立的问题，而是一个结构化 Agent 循环的一部分。"
- 2026 年 8 月的周数据：**Agent 应用每周消耗 7.3 万亿 token，是人类直接聊天的约 5 倍**；从 2026 年 2 月到 8 月，Agent 流量涨了 14 倍，人类流量涨了 2.8 倍；**2026 年 2 月 6 日是人类 token 超过 Agent 的最后一天**。
- Agent token 里 **约 70% 是"缓存读"**——也就是前缀缓存命中、按折扣价计费的部分。所以 token 数涨 14 倍，钱远没有涨那么多。

**这些数字怎么用。** 结论是"Agent 已经是推理流量的多数"，但要说明是第三方路由平台的样本。它和本项目已有的三份 Agent trace 互相印证：TraceLab 命中率 95.7%（按 token 加权）[56]、TokTier 的 fleet 级命中率 94.1% [68]、阿里百炼生产 Agent 的 KV 复用率大于 80% [67]——四个独立来源都说 Agent 上下文的绝大部分是重复的。

### 1.4 Agent 为什么把 CPU 拉回来了

先解释逻辑：传统推理里 CPU 只是"喂 GPU 的"，一颗 CPU 配 4 到 8 颗 GPU 就够。Agent 循环里多了大量只能在 CPU 上做的事——运行命令、跑测试、读写文件、搜索、检索、把上下文切成 token——于是每颗 GPU 需要配更多 CPU。三个厂商各自给了数字，口径不同，列在一起看：

| 说法 | 数字 | 口径 | 来源 |
|---|---|---|---|
| Arm CEO 主题演讲（2026-03） | **每 GW 数据中心需要的 CPU 核数从 3,000 万涨到 1.2 亿（4 倍）** | "每 GW"指数据中心供电容量；这是 Arm 的估算，方法没公开，应理解为"CPU:GPU 比从 1:8 左右变到 1:2 左右"的另一种说法。同场发布 Arm 自研 AGI CPU（136 核，300 W），Meta 首发 | [81]〔二手〕 |
| Intel CFO 财报电话会（2026-04） | **客户部署里 CPU:GPU 已从 1:8 变成 1:4；转向推理和 Agent 后"可能收敛到 1:1 甚至更偏 CPU"** | 指 Intel 看到的客户订单结构；同一季度 Intel 数据中心收入增长 22%，说 Xeon 供不应求会持续到 2027 财年 | [81]〔二手〕 |
| TrendForce 分析（2026） | Agent 部署 CPU:GPU 从 1:4–1:8 变到 **1:1–1:2**；2026 年第一季度**服务器 CPU 平均售价上涨 27%** | 售价是供应链调研；CPU 承担的工作它列为：编排（任务调度、工具路由、子 Agent 间传数据）、工具处理（Python、爬虫、摘要、数据库查询）、RL 评估 | [81] |
| 分析师 Futurum | 服务器 CPU 市场 2029 年 766 亿美元，年复合 34.9% | 预测口径未披露 | [81]〔二手〕 |
| 学术论文 | 五种 Agent 负载里，CPU 上的工具处理最高占端到端时延 **90.6%**；大批量并发时 CPU 的动态能耗占 **44%** | 见 1.6 和 [78] | [78]〔公开〕 |
| 沙箱厂商 | Modal 融资 3.55 亿美元、估值 46.5 亿；E2B 累计启动沙箱超 10 亿个，按 0.05 美元/vCPU 小时计费；Daytona 每天 85 万次运行，月增 74% | 自报 | [81]〔二手〕 |

**对鲲鹏的直接含义**：CPU 在 AI 集群里从"配角"变成需要按 GPU 数量配比采购的部件，而且价格在涨。

### 1.5 占比拆法之一：按硬件构成看钱花在哪

**两类节点。** 一个 Agent 集群里有两种服务器：
1. **推理节点**：NPU/GPU 加一颗或几颗 host CPU 和大内存。CPU 负责把文本切成 token、调度批次、管理 KV 缓存池。
2. **CPU 节点**：没有加速卡，跑沙箱、执行工具、做网关和编排、跑向量数据库、停放空闲会话的状态。IDC 说的"CPU-only 推理集群 / 编排工具"、TrendForce 说的"增购普通服务器"都是这一类。

**成本构成的基线〔二手〕[81]。** 一台 8 卡 GPU 服务器里半导体占成本 90% 以上，GPU 自身占绝对大头（英伟达 GB200 NVL72 机架：GPU 成本约 46 万美元，内存 + 存储 + 机箱约 6.5 万）。一台普通双路服务器里半导体占 65–70%；内存的份额随 DRAM 价格波动很大——2023 年一台 1 TB 内存的双路机约 1.04 万美元，内存接近 40%；2025 年 1 月内存占服务器 BOM 约 18%，**到 2026 年 7 月涨到约 53%**，因为 DRAM 合约价 2026 年第一季度环比涨了 93–98%。

**CPU:GPU 比变化会让"CPU + 内存"的份额变成多少〔推算〕。** 假设：一台 8 卡 GPU 服务器 35 万美元；一个"CPU 单元" = 一颗高核数 CPU（8,000 美元）加 1 TB 内存（按 2026 年价格 8,000 美元），共 1.6 万美元；不算 CPU 节点自己的机箱和网络。分母是"GPU 服务器 + 配套 CPU 单元"的总价。

| CPU:GPU | 每 8 颗 GPU 配几个 CPU 单元 | CPU + 内存的钱 | 占总价 |
|---|---|---|---|
| 1:8（训练集群） | 1 | 1.6 万 | **4.4%** |
| 1:4（今天的推理，Intel 说法） | 2 | 3.2 万 | **8.4%** |
| 1:2（TrendForce 的下界） | 4 | 6.4 万 | **15.5%** |
| 1:1（Intel 和 Arm 说的 Agent 终点） | 8 | 12.8 万 | **26.8%** |

读法：如果 Intel 和 Arm 的判断成立，Agent 集群里 CPU 加内存会从"零头"变成总投资的四分之一。Arm 的"1.2 亿核/GW"换算一下：按每颗 136 核，是 88 万颗 CPU；按每台两颗，是 44 万台纯 CPU 服务器——这是每 GW 供电的量，不含推理节点里的 host CPU〔推算〕。

**这一节对加速库的意义**：CPU 节点的价值由三样东西决定——每台机器能同时跑多少沙箱（核数密度）、能停放多少个空闲会话的状态（内存容量）、内存变贵之后能不能把空闲状态压缩起来（压缩能力）。第 4 节会回到这三点。

### 1.6 占比拆法之二：按 Agent 工作的环节看时间和钱花在哪

下表每一行都注明数据来自哪份研究、样本是什么、分母是什么。

| 环节 | 占时间多少 | 占钱多少 | 占资源多少 |
|---|---|---|---|
| **模型生成**（在 NPU/GPU 上） | 编码 Agent 一次请求的响应时间里占 **41.0%**（TraceLab [56]：43 名开发者、8 个月、约 4,300 个会话的 Claude Code 和 Codex 日志；"响应时间"不含用户思考和打字的空闲）。如果把整个会话的时长当分母，模型生成只占 3.3%，把超过 1 小时的空闲截掉后是 14.5%。 | 模型 API 费用的构成：**59.5% 花在读取缓存的前缀、29.2% 花在新输入、11.2% 花在输出**（TraceLab 按各厂商公开价目表算）。生产编码 Agent 里，因为缓存 5 分钟就过期、用户一停顿就要重算，**重算占了 31.5% 的费用**（AgentSysBench [57]，35,037 个生产会话，24 小时）。 | 每个会话的 KV 缓存均值 2.2 GB、中位数 1.5 GB（AgentSysBench 在自己的 10 个应用上测的，模型从 7B 到阿里的 Max 级不等） |

| **检索、搜索、embedding**（CPU + 内存带宽） | RAG 问答里向量检索占 **84.5–90.6%**（三个问答基准各一个数；用 Meta 开源的向量检索库 faiss 做精确检索、C4 网页语料，48 核 Intel 服务器）[78]。生产搜索问答 Agent：141,376 个会话、373,678 次搜索，**搜索占会话时延的中位数 35%、均值 52%** [57]。向量库和模型放在同一台机器时向量库占 47%，分开部署、并发 10 时网络传输占 67.5% [57]。 | 搜索 API 按次收费；**27% 的不同查询词重复出现，贡献了 67.3% 的搜索调用**，加缓存能省 35.2% 的调用 [57]。 | 每个会话的向量库中位 7.4 MB、大会话超过 49 MB；一次深度研究请求要传输超过 20 MB 的向量（约 5,000 个 1,024 维 FP32 向量）[57] |

| **编排与协议**（CPU + 网络） | Codex 的执行器在"命令本身"之外还有 **18.6%** 的时间花在审批等待、调度、shell 启动、结果回传上（25.3 万次工具调用，端到端 418 小时里的 78 小时）[56]。链式 LLM 应用里 30–50% 的延迟发生在模型引擎之外 [66]。 | — | 内置工具（Bash/Read/Edit）由 Agent 进程直接执行，没有协议开销；只有用户配置的外部 MCP 工具走 JSON-RPC（本地服务器 stdio、远程服务器每条消息一次 HTTP）[74] |

| **CPU 能耗** | — | — | 五种 Agent 负载并发时，CPU 的动态能耗占 CPU + GPU 总动态能耗的 **20%（并发 1）到 44%（并发 128）**（64 核 AMD Threadripper + H200，减去空闲功耗后积分）[78] |

### 1.7 一次请求在 CPU 上花多少时间〔推算〕

以 TraceLab [56] 的典型请求为单位：8.8 次模型调用、10.8 次工具调用；每次调用模型时上下文中位数是 119K 个缓存前缀 token 加 875 个新增 token，合计约 120K token，按 4 字节/token 换算约 480 KB 文本。

| 项 | 每请求占用一个 CPU 核多久 | 怎么算的 |
|---|---|---|
| 把上下文全量重新 tokenize | **2.0 秒**（HuggingFace 实现）/ **118 毫秒**（Rust 实现）/ **20 毫秒**（增量修复） | 8.8 次 × 每次 228 / 13.4 / 2.3 毫秒（TokTier 表 8 [68]，平均上下文 117K token） |
| 把上下文转成 JSON 再解析 | 2 毫秒（simdjson，5 GB/s）到 85 毫秒（Python 自带 json，约 100 MB/s） | 480 KB × 客户端编码一次 + 网关解析一次 × 8.8 次 = 8.4 MB |
| 前缀缓存的块哈希 | 约 4 毫秒 | 120K token 按 16 token 一块是 7,500 块，每块 SHA-256 约 0.5 微秒；Mooncake 用 512 token 一块则只有 235 块 |
| 启动进程和 shell | 25–350 毫秒 | 一次请求里约 5–7 次 shell 类调用，每次启动 bash 或 Python 5–50 毫秒（bash 优化后约 40 毫秒，Python 解释器 10 毫秒起，带常用库导入几百毫秒 [81]） |
| 读写文件 | 约 10 毫秒 | 约 4 次读/改/写，每次 KB 到 MB |
| 工具本身（跑测试、编译、git） | 壁钟时间：命令内部平均 0.66 秒 × 10.8 ≈ 7 秒；执行器周边开销平均 1.26 秒 × 10.8 ≈ 14 秒 | Codex 表 10 [56]；工具本身用了几个核不知道（测试可能多核） |
| 创建沙箱（每个会话一次） | 27–125 毫秒，再加快照恢复后的缺页拖慢（执行慢 95%） | Daytona 容器 27–90 毫秒、Firecracker 微虚拟机 125 毫秒 [81][51]；REAP [64] |
| 空闲驻留（每个会话） | 0.8 GB 沙箱 + 1.5 GB KV 缓存，持续几小时 | [57] |

怎么读这张表：在**编码 Agent** 里，如果推理前端还在用 HuggingFace 那类 tokenizer，那么"把上下文重新切 token"是循环里最大的、加速库能碰的 CPU 项（2 秒/请求），比 JSON 高一到三个数量级；换成 Rust 实现或增量算法后降到几十毫秒，这时进程启动和工具执行成为主项——但工具本身（编译器、测试框架）不是加速库能碰的，**能碰的是它周围的隔离层、进程创建、文件系统和 git**。在 **RAG 或搜索型 Agent** 里，向量检索是绝对主项。

### 1.8 本地还是云端：沙箱到底在哪里跑，"云开发机上的 Agent"这个场景占多大

这一节回答一个容易混淆的问题：一个在自己电脑上用 Claude Code 的开发者，会觉得"沙箱"和自己无关——这是对的。下面把"谁会创建沙箱、沙箱跑在哪、占多少"拆开说。

**先说本地 Claude Code。** 每个工具调用都是 Claude Code 在开发者自己的机器上起的子进程。Claude Code 的"沙箱"是**进程级限制**：Linux 上用 bubblewrap 加 seccomp，macOS 上用 Seatbelt，只限制这个子进程能访问哪些目录、网络是否走代理白名单；它不创建容器或虚拟机，启动开销接近零；默认不开，要用 `/sandbox` 命令手动打开〔Anthropic 2025-10 博客，[74]〕。所以本文里"沙箱创建 27–125 毫秒""快照恢复慢 95%""gVisor 系统调用慢 2.2–216 倍"**对本地用法都不适用**；本地用法在数据中心里只留下推理那一侧的活（tokenize、KV 缓存、调度）。TraceLab 的"工具执行占 59.8%"测的就是本地机器上的时间。

**哪些 Agent 会真的创建沙箱、跑在哪。**

| 类型 | 例子 | 沙箱形态 | 跑在哪 | 规模线索 |
|---|---|---|---|---|
| 开发者的 Agent 跑在**云开发机 / 云桌面**上（每人一台常驻环境） | 企业研发云桌面（华为云 Workspace、深信服、中兴等）、云开发环境 CDE（GitHub Codespaces、Gitpod、Coder、Google Cloud Workstations、Microsoft Dev Box、华为云 CodeArts） | 每个开发者一台常驻虚拟机或容器；Agent 的 Bash/Read/Edit 全部落在这台机器上 | 企业数据中心或公有云的 CPU 服务器 | 华为研发自用桌面云用户 **19 万+**、Workspace 全球累计用户 350 万+〔华为云官网〕；中国桌面云 2025 年预计 673 万座席、100 亿元〔二手预测〕；Gitpod 累计 100 万+ 开发者 |
| 云端托管的编码 Agent（每任务一个短命环境） | Claude Code on the web、OpenAI Codex cloud、GitHub Copilot coding agent（跑在 GitHub Actions 的虚拟机里）、Devin、Cursor 后台 Agent、Google Jules | 每个任务或会话一个容器/虚拟机，可暂停、可恢复 | 厂商自己的云 | AgentSysBench 那 35,037 个会话的生产编码 Agent 属于这一类——论文说会话空闲时"沙箱、终端上下文、KV 缓存、对话历史必须保持可恢复"，所以"80% 空闲但沙箱一直占着"说的是云端 Agent；Copilot coding agent 上线 5 个月产出 100 万个 PR〔GitHub Octoverse 2025〕 |
| 让终端用户跑代码的 AI 产品 | ChatGPT 代码解释器/数据分析、Claude 的代码执行工具（API 侧）、Manus、Lovable/Bolt 这类 AI 建站、Perplexity | 每个用户会话一个微虚拟机或容器 | 云沙箱厂商（E2B 用 Firecracker、Modal 用 gVisor、Daytona 用 Docker）或大厂自有 | E2B 累计 10 亿个沙箱、Daytona 每天 85 万次 [81] |
| 浏览器 / 电脑操作 Agent | ChatGPT agent（Operator）、Anthropic computer use、AgentSysBench 的 GUIAgent | 云端浏览器或容器化桌面 | 云 | GUI 沙箱占该类应用时延 70% 以上 [57] |
| RL 后训练的 rollout | 蚂蚁 ASandbox、字节 SandboxFusion、SWE-MiniSandbox | 每条轨迹一个沙箱，用完即弃，万级并发 | 模型厂商训练集群旁的 CPU 节点 | 容器初始化占 rollout 时间 40–60% [76]；沙箱创建税最大的地方 |
| 企业多租户 Agent 平台、评测、远程 MCP | 阿里百炼、Coze 这类平台跑用户代码；SWE-bench 每题一个 Docker | 容器 | 云 | — |
| 云厂商的"Agent 沙箱"产品 | AWS Bedrock AgentCore（代码解释器/浏览器沙箱）、Azure Container Apps dynamic sessions、Google Vertex Agent Engine 代码执行、Cloudflare Sandboxes | 按秒计费的隔离运行时 | 公有云 | 说明这已经是一个卖 CPU 时间的产品品类 |

对服务器厂商来说，第一行（云开发机）和第二行（云端托管 Agent）都是数据中心负载，但形态不同：前者是**每人一台、长期常驻、80% 时间空闲**，后者是**每任务一个、短命、创建销毁频繁**。

**这个场景占多大：没有直接统计，只能拼。** 下面是能找到的间接数据和它们的口径。

|---|---|---|---|

|---|---|---|---|---|

| 3 | Kilo Code | 4,930 亿 | IDE 插件、CLI | 本地 |
| 4 | Cline | 4,120 亿 | IDE 插件、CLI | 本地 |
| 5 | pi | 3,050 亿 | CLI | 本地 |
| 6 | omp | 2,020 亿 | CLI | 本地 |

| 8 | Codex | 1,500 亿 | CLI | 本地 |

前 20 名合计约 4.45 万亿 token/天。其中明确在用户自己机器上执行工具的 CLI/IDE/个人 Agent（第 1–8 名）合计 3.67 万亿，占 **82%**；加上两可的 OpenHands 和 CodeGPT 是 86%。剩下 14–18% 里，大部分是角色扮演、游戏、聊天类，根本没有代码执行沙箱；真正可能在云端沙箱里跑代码的（Lemonade、ZCode、Framer 这类编程网页应用）合计不到 3%。

这个反推的口径要说清楚：(1) 单位是 token，不是工具调用次数；(2) OpenRouter 只看得见走第三方模型的流量，云端托管的第一方产品（Codex cloud、Claude Code on the web、Copilot coding agent、ChatGPT 代码解释器）用自家模型，**根本不经过 OpenRouter**，所以这里的"本地 82%"是 OpenRouter 用户群内的数，对全市场而言是本地份额的**上界**；(3) 但它和另一个独立锚点一致——Copilot 云端 Agent 只占 GitHub 每月 PR 的 0.5%。两个角度都说：**2026 年编码 Agent 的工具执行以本地为主，云端沙箱是少数**，与前面"云开发机场景是 1% 量级存量"的推算互相印证。

**推算：中国研发云桌面上跑 Agent 需要多少服务器。** 每一步的假设都写出来，便于替换。
1. 研发座席：673 万桌面云座席里研发占多少没有统计。研发是桌面云的核心场景之一（代码不落地、外包管理），头部企业可以做到研发全员上云（华为 19 万）。**假设 15–30%** → 100–200 万个研发云桌面座席。
2. 用 Agent 的比例：2026 年**假设 30–60%** → 30–120 万个跑着 Agent 的座席。
3. 每座席资源：研发云桌面常见 8 vCPU、16–32 GB；Agent 跑编译和测试时峰值 28 GB [57]；会话 80% 时间空闲 [57]，允许 2–3 倍超分。**假设**一台 2 路、128 核、1 TB 内存的服务器承载 24–40 个座席。
4. 结果：**0.75 万到 5 万台服务器**的存量，相当于中国 x86 服务器一年出货量的 0.2%–1.5%〔推算〕。

**结论。** 按今天的数据，"开发者 Agent 在云开发机上执行工具"这个场景在服务器市场里是**1% 量级**的存量，与 Copilot 云端 Agent 只占 0.5% PR 的现状一致——它现在小。但三个乘数都在往上走：Agent 使用率（2025 年问卷里已过半数开发者日常用 AI）、研发环境上云的比例（安全合规驱动，头部企业已全员）、每座席的资源需求（Agent 让编译和测试跑得更勤、峰值内存 28 GB）。另外两块云端负载——云端托管 Agent 的短命容器池和 RL rollout 的沙箱池——没有任何公开规模数据。

**怎么拿到更准的数。** 最直接的数据源在华为自己手里：19 万研发云桌面用户里开启了编码 Agent 的比例、开启前后每座席的 CPU 和内存利用率变化、峰值并发。这一个内部统计就能把上面 1–3 步的假设全部换成实测，而且客户（金融、运营商的研发云桌面）的形态和华为内部一样。

## 2. Agent 最常调用哪些工具

### 2.1 数据从哪来

**TraceLab [56]** 是目前唯一公开的、跨两家产品的真实使用记录：华盛顿大学的 43 名开发者自愿上传自己 8 个月里用 Claude Code 和 Codex 的日志，约 4,300 个会话、35 万次模型调用、43 万次工具调用（Claude 142,388 次 + Codex 290,122 次），覆盖 20 多个模型版本。**"占比"= 该工具的调用次数 ÷ 该产品全部工具调用次数**。它记录的是开发者自己的日常工作，不是 benchmark。局限：样本是一个实验室的人，任务偏研究代码。

**AgentSysBench [57]** 是港科大做的两部分工作：(a) 受控实验——10 个有代表性的 Agent 应用，每个跑一批标准任务（共 4,641 次请求、64,924 次模型调用、118,274 次工具调用），全部部署在一台英伟达 GPU 服务器上、每个组件一个 Docker 容器，模型多数走阿里百炼 API；(b) 三份 24 小时生产日志：一个编码 Agent 35,037 个会话、一个搜索问答 Agent 141,376 个会话、一个类 Openclaw 的办公 Agent 2,386 个会话（有 URL 抓取的那部分）。

**AgentSysBench 里的"沙箱"具体指什么、跑在哪（这决定它的沙箱数字适用于谁）。** 论文的视角自始至终是**服务提供方的云端**："agent-serving system"、"serving platform"。它的图 1 把编码 Agent 画成三部分：编排器、跑在 GPU 服务器上的模型（SGLang）、跑在**另一台物理服务器上的 Docker 沙箱**，两者之间走网络。受控实验里每个组件一个 Docker 容器；对 Codex、GUIAgent、Claude Code、Openclaw、Pi-AutoR 这些沙箱重的应用，用 SSH 连到远程沙箱去截获动作；做 CPU 敏感性实验时给 Codex 的沙箱分配 8 到 96 个核（图 19），做干扰实验时把 8 个沙箱各绑 16 个核或让它们共享（图 14c）。**费用估算的口径**：模型按各家 API 价目表，**沙箱按 E2B（云沙箱厂商）的价格**，搜索按 Firecrawl 的价格——所以"自动科研 Agent 的沙箱费用超过 99%"说的是"如果你租 E2B 那样的云沙箱（还要带 GPU 容器跑科学模拟）来运行它"。三份生产日志里的编码 Agent 没有说明是哪个产品，只说明它是"已部署的应用"、每个会话有一个"保存正确性状态的专属沙箱"、会话空闲时沙箱一直分配着——这是云端托管型编码 Agent 的形态（类似 Codex cloud），**不是开发者本地的 Claude Code，也没说是不是云开发机**。论文没有给出"这种部署形态占所有 Agent 使用的多少"。

**CPU-Centric [78]** 是 Georgia Tech 和 Intel 做的学术剖析：5 个用开源框架搭的 Agent 负载，在 48 核 Intel Emerald Rapids + B200 上逐个跑标准基准，记录每一步的时间。

**Inside the Scaffold [80]** 不测运行，而是读了 13 个开源编码 Agent 的源码，看它们给模型提供了哪些工具、怎么隔离。

### 2.3 工具的时间去哪了（TraceLab）

- **平均一次工具调用 16.8 秒，但分布极度不均。** Claude Code 里，不到 1 秒的调用占次数的 70%，却只占工具总时间的不到 1%；超过 1 分钟的调用占次数的 4.9%，占总时间的 92%。Codex 稍缓和：不到 10 秒的占次数 88%、占时间 12%；超过 1 分钟的占次数 3.1%、占时间 61%。超过 1 分钟的基本是编译、安装、跑整套测试。
- **"执行器残余"。** Codex 记录了两个时间：从模型发出工具调用到收到结果的端到端时间，和执行器自己报告的命令内部执行时间。两者之差就是命令之外的开销——审批等待、运行时调度、shell 启动、输出回传、客户端记账。对 253,391 次有两个时间戳的 Codex 调用（占 Codex 工具调用的 87.3%）：端到端 418.1 小时，内部执行 341.5 小时，**残余 77.8 小时，占 18.6%**。残余集中在 exec_command：它端到端 97.8 小时里内部只有 33.8 小时，**残余 64.1 小时，平均每次 1.26 秒（中位 0.16 秒，最慢 1% 达 8.6 秒）**——也就是说，对运行一条命令这个动作，**周边开销平均比命令本身（0.66 秒）还长**。审批等待是大头，但 shell 启动和输出回传也在里面。

### 2.5 学术负载里的热点（CPU-Centric）

五个负载在 48 核 Intel + B200 上单请求顺序执行的时间分解 [78]：RAG 问答里精确向量检索占 84.5–90.6%，模型推理只有 0.5 秒；数学问答里调 WolframAlpha 计算器 API 占 1.4–1.7 秒；化学研究 Agent 里 arXiv/PubMed 文献检索占 4–10 秒；网页问答里上网搜索最多 4.2 秒、CPU 上做的摘要最多 3.5 秒，两者合计超过一半；软件工程 Agent 里 Bash/Python 执行占 43.8%（DS-1000 基准）到 78.7%（BigCodeBench 基准）。

并发时的饱和点也在 CPU：网页问答和软件工程负载并发到 128 时因为**CPU 核被超额分配**而饱和（摘要任务从 2.9 秒拖到 6.3 秒）；RAG 并发到 32 就因为最后一级缓存（LLC）压力和磁盘争用饱和。

### 2.6 MCP 生态里的热点

MCP 是 Agent 调外部工具的协议。公开目录里有 2.1 万到 2.3 万个 MCP 服务器；2026 年 4 月本地 MCP 服务器被下载 6,700 万次（Pulse MCP 估算）。Bloomberry 分析了 1,400 个服务器共 4,126 个工具：每个服务器中位 5 个工具，**52% 是读操作、25% 是写操作**。最常用的服务器：Context7（查文档）、GitHub、Playwright（操作浏览器）、Filesystem（读写文件）、Exa（搜索）；企业侧 Slack、Zapier、Salesforce、Google Workspace 进入前 50 [81]。协议本身：每条消息 JSON-RPC，走 HTTP 时每条消息一次 POST，图片音频用 base64 编码（体积 +33%）[74]。

### 2.7 工具形态在收敛（Inside the Scaffold）

读 13 个开源编码 Agent 的源码 [80]：工具数量从 0 个（Aider，靠用户自己导航）到 37 个（Moatless）不等，但**所有让模型自主行动的 Agent 都收敛到四类能力：读文件、搜索、编辑、执行/测试**。13 个里 8 个把 grep/find/ripgrep 直接暴露给模型；编辑以"字符串替换"式为主流。隔离方式：3 个不做沙箱（Gemini CLI、Aider、OpenCode），1 个用进程级沙箱（Codex CLI：bubblewrap/Landlock/Seatbelt），5 个用 Docker（SWE-agent、OpenHands 等自动化 Agent），其余用 git 检查点或内存影子。这说明 2.2 的热点不是 Claude Code 一家的偶然，而是架构决定的。

## 3. 这些工具和 tokenizer 在 CPU 上忙的是什么

### 3.1 运行命令：进程密集、系统调用密集、被隔离层放大

**形态。** 大多数 Agent 每次调用启动一个子进程跑命令 [80]；Codex 还大量向长驻进程写输入。命令内容以 git、编译、测试、包管理、grep/find/ls/cat 为主——TraceLab 的原话是"运行命令和测试"，[80] 说 13 个 Agent 里 8 个把 grep/find 当工具。**公开文献里没有"Bash 里具体跑了什么命令、各占多少"的统计**，这是本文的一个缺口，建议用自家 Claude Code/Codex 日志补（见第 4.7 节）。

**一次调用的成本由四段组成。**
1. 创建进程：fork 加 exec 通常几百微秒；如果父进程很大、脏页很多，fork 要复制页表，比 posix_spawn/vfork 慢最多约 300 倍 [81]。
2. 启动 shell 或解释器：bash 优化后约 40 毫秒，没优化的 165 毫秒到 1.7 秒；Python 解释器本身 10 毫秒，加上常用库的 import 几百毫秒 [81]。
3. 命令本体：git status 要对仓库里每个文件做一次状态查询；git 的每个对象都用 zlib 压缩，读对象要解压、写对象要压缩，还要算 SHA 哈希；编译和测试是多核、长时间的。
4. 输出回传和截断。

Codex 的实测把 1、2、4 和审批等待合在一起叫"残余"：**平均 1.26 秒，比命令本体的 0.66 秒还长** [56]。

**长尾。** 超过 1 分钟的调用只占 4%（Claude Code 4.9%），却占工具时间的 85–92% [56]。这些是编译、安装、整套测试——多核、加速库碰不到，但它们决定了沙箱的峰值内存（28 GB）和需要配多少核。

**隔离层的放大** [64]。用 gVisor 这类用户态内核容器时，简单系统调用慢 2.2 倍以上，在外部 tmpfs 上打开关闭文件慢 216 倍，读小文件慢 11 倍，分配内存慢 2.5 倍，Python 的 import 明显变慢；普通 Docker（runc）比裸机慢 32%。从快照恢复的微虚拟机，恢复后的程序执行比一直常驻时慢 95%，因为内存页要一页一页从磁盘缺页载入，把工作集预取回来能把冷启动降 3.7 倍。业界的应对：本地 Agent（Claude Code、Codex）已经改用进程级沙箱，Anthropic 的博客说这样"避免了启动和管理容器的开销"[74]；云端仍然是容器或微虚拟机（Modal 用 gVisor，E2B 用 Firecracker，Daytona 用 Docker）[81]。

**RL 的批量版** [76]。软件工程类 RL 任务每条轨迹要一个独立仓库环境，SWE-MiniSandbox 论文测得**容器初始化占 rollout 时间的 40–60%**；它改用进程级隔离加 OverlayFS 文件系统快照。

**并发时 CPU 怎么饱和** [78]。Bash/Python 类工具并发到 128 时因为核被超额分配而饱和；Python 要用多进程绕过 GIL（解释器的全局锁，让多线程无法真正并行），多进程又比多线程更费内存和创建开销；并发从 1 到 128，CPU 动态能耗涨 86.7 倍，GPU 只涨 26.8 倍——CPU 并行的能效比 GPU 差得多。

### 3.2 读、改、写文件：小文件、单核、和文件长度成正比

Read 的流程是：打开文件、读入（或 mmap）、校验是不是合法 UTF-8、按行编号、超过限制就截断（Claude Code 默认最多 2,000 行）、转义成 JSON 字符串塞进上下文。Edit 是：读全文、找到那段唯一的旧文本、替换、写回。apply_patch 是应用 diff。每次 KB 到 MB，毫秒级。它们**占调用次数的 38%（Claude Code）和 30%（Codex）**，但占工具时间不到 1% [56]。

特征：数据几乎都在页缓存里，单核处理；UTF-8 校验用 NEON 指令的 simdutf 库已经能做到每秒 10 GB 以上，子串查找的 memmem 在 aarch64 上也有 NEON 版 [81]——**每字节已经很便宜，价值不在算得更快，而在别被放大**（gVisor 下小文件读慢 11 倍、打开关闭慢 216 倍）和**少往返**（AgentSysBench 建议"按需检索"而不是整文件塞给模型 [57]）。

另一个意义：文件系统是沙箱"正确性状态"的主体（[57]：文件、依赖、进程元数据都在里面），做快照、迁移、去重时对象就是它。

### 3.3 搜文本：ripgrep 那一套

ripgrep 的流程：遍历目录（要处理 .gitignore 规则、对每个文件 stat）、把文件 mmap 或读进来、用 memchr/memmem 找单字节或子串（NEON 加速）、多模式时用 Teddy 算法（SIMD）、复杂模式走正则引擎的自动机（DFA）。在 aarch64 上有 NEON 路径，**没有 SVE/SVE2 路径** [81]。一次仓库级搜索 10 毫秒到几秒。显式调用只占 2–3%，但 Bash 里的 grep/rg/find 没有被单独统计。搜索的变体还有 AST 感知搜索、embedding 语义搜索、知识图谱 [80]——后两种就变成了 3.5 节的向量检索。

### 3.4 上网搜索和抓取

时间主要花在网络往返上（搜索平均 1.35 秒、抓取 2.66 秒 [57]；文献检索 4–10 秒 [78]）。CPU 侧做的是：TLS 握手和加解密、gzip 或 brotli 解压、把 HTML 转成文本、解析 JSON、以及可能的摘要（CPU 上跑 LexRank 摘要 3.5 秒 [78]）。**最大的杠杆不是算得快，而是跨会话缓存**：27% 的查询词重复占 67.3% 的搜索、24% 的 URL 重复占 64% 的抓取 [57]。这是存储或缓存层的事，不是加速库的事。

### 3.5 向量检索、embedding、重排

精确检索（faiss 的 FLAT 索引，即不建索引、逐个比对）本质是一次大矩阵乘（查询向量 × 全部文档向量）再取前 k 个，占 RAG 端到端 84.5–90.6%，并发 32 以上被最后一级缓存压力和磁盘争用封顶 [78]。生产向量库与模型同机时占 47%，分开部署时一次请求要传 20 MB 以上的 FP32 向量，网络传输占 67.5% [57]。乘积量化（PQ）扫描每核 18 GB/s、能用到 80% 内存带宽 [52]。embedding 和重排模型是 CPU 上的小型 transformer 前向，本质是 bf16 或 int8 矩阵乘（Arm Neoverse V2 上 BF16 快 2.7 倍、INT8 快 4.8–6.2 倍 [74]）。

特征总结：**内存带宽型**，随机访问（HNSW：把向量组织成图、沿边跳着找）或流式扫描（IVF：先分簇再扫簇内；PQ：把向量压成短码查表算距离）。

### 3.6 沙箱层（隐式工具）

已知数字集中在这里：Firecracker 微虚拟机启动到能跑应用代码 125 毫秒以内、每台内存开销 5 MB 以内、单机每秒最多创建 150 台，其中内核解压占 40 毫秒 [51]；Daytona 的 Docker 沙箱创建 27–90 毫秒 [81]；gVisor 的系统调用放大 2.2 到 216 倍 [64]；快照恢复后执行慢 95%、预取工作集降 3.7 倍 [64]；沙箱内存工作集中位 0.8 GB、峰值 28 GB [57]；会话 80% 时间空闲但沙箱一直分配着 [57]；华为 virtCCA 机密虚拟机在鲲鹏 920 上对 I/O 密集负载的开销低于 29.7% [61]。

沙箱税的构成：创建（页表、内存清零、命名空间、cgroup）、镜像拉取和解压（压缩税）、系统调用拦截、快照保存和恢复（页拷贝、缺页）、空闲驻留（占内存）、销毁回收。

**"沙箱税"这个说法成立吗——分开判断。** 把它拆成三样东西，证据强度和适用范围各不相同：

| 分量 | 是什么 | 证据 | 强度 | 适用范围 | 对硬件的含义 |
|---|---|---|---|---|---|
| 创建 / 销毁开销 | 每个任务或轨迹起一个环境：建页表、清零内存、建命名空间、解压镜像、准备仓库 | RL 训练里环境初始化占 rollout 时间 40–60%（SWE-MiniSandbox 实测，一篇论文）[76]；单次创建 27–125 毫秒（厂商数据）[81][51] | 中：RL 场景有实测；交互式云端 Agent 每会话只创建一次、摊到几分钟到几小时里可忽略 | RL rollout、每任务一个环境的云端 Agent | 成立，但只在"高频创建"的场景 |
| 隔离层放大 | 系统调用被用户态内核或虚拟化拦截 | gVisor 系统调用慢 2.2–216 倍（2019 年微基准，无服务器场景）[64]；runc 慢 32%；Firecracker 是真内核，系统调用接近原生；进程级沙箱约等于零 | 弱：数字来自非 Agent 场景的微基准；而且**这项开销取决于技术选择，可以通过选更轻的隔离方式避开**，本地 Agent 已经这么做了 [74] | 只有选 gVisor 类隔离的部署（如 Modal） | 不像 Kanev 意义上"躲不掉"的税；硬件价值有限 |
| 空闲驻留 | 会话空闲时沙箱内存、KV 缓存、对话历史一直占着 | 生产编码 Agent 会话中位 80% 时间空闲、沙箱一直分配（35,037 会话实测）[57]；沙箱按存活计费 | 强：生产数据；但它占的是**内存容量和账单，不是 CPU 周期** | 云端托管 Agent、云开发机（每人一台常驻） | 成立，落在内存容量、分层、压缩上，不落在 CPU 核 |

按 `INSIGHT_AI_WORKLOAD.md` 第 0 节的三个判据（换模型换业务还在吗；是公共路径不是应用代码吗；不懂模型的硬件能吃掉吗），三个分量都过关。但按"税额"的标准——Kanev 那种 fleet 级"占 CPU 周期 X%"的测量——**没有任何来源测过 Agent 服务里沙箱生命周期占多少 CPU 周期**。本文能说的是：在云端和 RL 部署里它存在、在特定场景（RL 初始化、空闲驻留）里很大、在本地部署里为零；"沙箱税占 CPU 多少"是待测项，不是已知数。

由此对本文早先的表述做三处降级：(1) TraceLab 的"工具执行 59.8%"不是沙箱开销，是命令本身的时间，不能再作为沙箱税的证据；(2) `INSIGHT_AI_WORKLOAD.md` 税表第 11 项标的"已发生（实测）"应改为"云端/RL 场景有实测，fleet 级占比未知，本地为零"；(3) 4.6 表里 V1 从 P0 降为"按客户场景定"——目标客户是 RL 训练集群或云端 Agent 平台时是 P0，是云开发机时重点转到驻留（K1）而不是创建。

### 3.7 tokenizer：循环里最大的固定 CPU 项

**它是怎么算的。** 主流 tokenizer 分两步：
1. **预分词**：先用一条正则表达式把文本切成短片段（大致按单词、数字、标点、空格切）。GPT 系模型用的是"从左到右、多分支择一、允许回溯"的正则，本质是串行扫描。
2. **BPE 合并**：在每个片段内，反复找"合并优先级最高的相邻两个 token"合成一个，直到不能合并。查优先级用哈希表，找最高优先级用堆或链表。tiktoken 的实现最坏是 O(n²)，HuggingFace 用堆是 O(n log n)，GitHub 2024 年提出的新算法能做到线性 O(n) [81]。

整个过程**串行、分支多、哈希表随机访问**，向量指令只能帮第一步的字符分类。还有一个关键性质：tokenize(A) 接 tokenize(B) 不等于 tokenize(A 接 B)——在末尾追加文本会改变末尾几个 token 的切法。所以不能简单缓存上次的 token 序列然后往后拼，这就是为什么服务前端今天每次都把整个上下文重新切一遍 [68]。

**吞吐基线（口径要看清）。** TokTier [68] 的表 8：样本是两个 Agent 生态里采样的 153,529 次调用，平均上下文 117K token；数字是**"每次请求全量重新 tokenize 需要占用一个 CPU 核多少毫秒"**：

| 实现 | 每请求核时 | 折算每核吞吐（按 480 KB/请求） |
|---|---|---|
| HuggingFace fast tokenizer（Rust 实现，GPT 系正则） | **228.1 毫秒** | 约 2 MB/s |
| Rust 的 fastokens | **13.4 毫秒** | 约 35 MB/s |
| TokTier 增量修复（只重切追加的那一小段，再校验边界） | **2.3 毫秒** | — |
| GPU 全量（RTX PRO 6000） | 0.15 毫秒 GPU 时间 | 1M 字符 0.38 毫秒 |

所以"tokenizer 税"的大小强烈依赖部署用的是哪个库，两档差 17 倍。旁证：GitHub 的线性算法单线程比 tiktoken 快约 4 倍、比 HuggingFace 快约 10 倍（Apple M1 上）；quicktok 与 tiktoken 逐字节一致、快 3.5–11 倍；tiktoken 在 144 核 EPYC 上单进程 36 MB/s、HuggingFace 24.8 MB/s [81]。

**"每 1,000 颗 GPU 要几个前端核"是怎么算的。** TokTier 把每请求核时乘以请求率：如果每颗 GPU 每秒完成 0.5 次请求，1,000 颗 GPU 每秒 500 次请求，每次 13.4 毫秒核时，就要 6.7 个核一直忙着切 token；请求率 5 次/秒/GPU 时是 67 个核。换 HuggingFace 就是 114 和 1,140 个核 [68]。

**它在服务里的位置。** Agent 调用中位每次只往 86K–123K token 的上下文追加约 1.4K 字符，前端却全量重切 [68]；fleet 级前缀缓存命中率 94.1%；**命中率从 0.88 涨到 0.99 时，tokenize 占首 token 延迟的比例从 10% 涨到 64%**——因为 NPU 那边省掉了，CPU 这边没省 [68]；一个 16 核的无状态前端在每秒 40 个请求时就饱和 [68]。另一篇论文 [69] 在多 GPU 推理上测到：CPU 核数配得不够时首 token 延迟慢 1.47–7.11 倍，tokenize 线程和推理引擎抢核是原因之一，HuggingFace 默认开多线程反而更糟。三个趋势会把它继续放大：推理越来越快（每颗 GPU 每秒完成的请求更多）、上下文越来越长、命中率越来越高。业界的应对：vLLM V1 把 tokenize 挪到单独进程（整体吞吐提升 1.7 倍，归因于削减 CPU 开销）[74]；Blink 把 tokenize 放到网卡上的 Arm 核 [58]；TokTier 做有状态的增量修复加 GPU 精确 BPE [68]。

**和 JSON 对比，这是排优先级的依据。** JSON 解析在 Arm 上已经很快：simdjson 在 AWS Graviton 4（Neoverse V2）上第一阶段（找出所有结构字符）每核 4.8–5.5 GB/s，Graviton 5（Neoverse V3）6.3–7.1 GB/s；把 NEON 查表换成 SVE2 的 MATCH 指令后第一阶段再快 3–9%，整体只快 1–4%（Lemire 2026-09 的博客，单线程，需要 `-mcpu=native` 编译）[81]。同样 480 KB 的上下文，JSON 解析约 0.1 毫秒，tokenize 是 13 到 228 毫秒——**每字节 tokenize 比 JSON 贵 100 到 2,000 倍**。JSON 真正的问题在 Python：标准库 json 大约 100 MB/s，比 simdjson 慢 50 倍，而 Agent 框架大多是 Python 或 TypeScript 写的。所以 JSON 这条线的工作是"把快的库接进去"，不是发明新算法。

**SVE2 能帮多少。** 预分词的字符类判定可以用 SVE2 的 `MATCH`、`HISTCNT`、`TBL` 做（simdjson 的 SVE2 版本就是用 MATCH 替换查表；TokTier 把 GPT 系正则改写成按字符类分段的规则，正是为了并行化这一步）；BPE 合并那一步仍然是标量哈希。所以收益的上限来自算法（线性 BPE 加增量），SVE2 是第二位。

### 3.8 循环里其它的固定项

- **detokenize、流式回传、采样**：每生成一个 token 做一次；vLLM V1 已把它们挪出核心循环 [74]。Blink 测到 host 侧干扰下 GPU kernel 之间的间隙从 1 微秒涨到 40 微秒、页表遍历占最后一级缓存停顿的 85%，根因是 Python 栈的碎片化地址空间——和 malloc、大页有关 [58]。
- **前缀缓存的块哈希**：每次调用 7,500 次（16 token 一块）或 235 次（512 token 一块）哈希，毫秒级；Mooncake 和华为 EMS 的块哈希带前缀链 [44][45]。
- **JSON 和 base64**：主路径上的 JSON 是模型 API 的请求/响应体（messages 数组 + tool_use/tool_result 块）；内置工具调用没有额外协议；只有外部 MCP 工具走 JSON-RPC（本地 stdio 为主，远程才是每条消息一次 HTTP POST）；图片 base64 体积 +33%；每会话数十 MB 主要是向量和截图 [57][74]。
- **控制面**：辅助模型调用（35K 会话额外 2,684 次）、上下文压缩每次平均 156 秒、工具定义占上下文 16.3% [57][81]——这些烧的是 NPU，不进 CPU 的账。

## 4. 鲲鹏基础加速库能做什么

### 4.1 怎么排的序

每一项按五个因素打分：**每请求发生几次 × 每次占多少 CPU 时间 × 能加速多少倍 × 加速库能不能碰到 × 和竞争对手（x86、Graviton）差多远**。只列加速库及其带动的内核/虚拟化路径能落地的事；工具本体（编译器、测试框架、浏览器）不列。→950 表示在鲲鹏 920/950 上现在就能做的软件动作，→960 表示要等新硬件特性。

### 4.2 系统库与运行时

**S1〔P0〕有状态的增量 tokenizer 库。**
- 问题：每次调用模型都把十万 token 的上下文全量重切，HuggingFace 实现每次 228 毫秒核时；命中率越高这一项在首 token 延迟里越显眼（最高 64%）[68]。
- 做什么：一个 Rust/C 库，(a) 兼容 HuggingFace 的 tokenizer.json 和 tiktoken 格式（TokTier 覆盖了 17 个 tokenizer 家族）；(b) 用线性 BPE 算法（GitHub 的回溯/增量编码思路）；(c) 预分词用 SVE2 的 MATCH/HISTCNT/TBL 做字符类分段；(d) **保留会话的 token 状态，追加时只重切末尾一小段并校验边界**（TokTier 的契约：结果必须和参考实现逐位一致）；(e) 接进 MindIE、vLLM、SGLang 的前端进程。
- 预期收益：每 1,000 颗 GPU 的前端核从 114 降到约 7（换 Rust 实现）再到约 1（增量）[68]；命中率 0.99 时 tokenize 在首 token 延迟里的占比从 64% 降到 10% 以下；CPU 配少了导致的 GPU 空转（首 token 延迟慢 1.47–7.11 倍 [69]）消失。
- 对手：Rust 的 fastokens、quicktok、rs_bpe、GitHub bpe 都在 x86 和 Apple 上做，没有 SVE 路径。
- 先测：HuggingFace、tiktoken、fastokens 在鲲鹏 920/950 和 Graviton 4、EPYC 上对 117K token 上下文的核时；SVE2 预分词原型的收益上限。→950。

**S2〔P1；RL 客户 P0〕进程启动的用户态路径。**（2026-09-21 按"加速库 vs 内核团队"的口径重写：只保留用户态部分。）
- 问题：运行命令占工具调用的 47–65%，每次一个进程；Codex 实测命令周边开销（审批等待、shell 启动、结果回传）平均 1.26 秒，比命令本体 0.66 秒还长 [56]；RL rollout 每条轨迹一个环境，初始化占 40–60% [76]。
- 一次进程启动的成本按层拆：fork 时复制页表、写时复制缺页（内核）；用 posix_spawn/vfork 路径而不是 fork（glibc 自 2.24 起 posix_spawn 走 clone+CLONE_VFORK；CPython 3.8+、Node/libuv 都能走这条路，但要确认默认开启——库/运行时）；动态链接（glibc ld.so 的符号解析与重定位——库）；locale 初始化与 malloc 初始化（glibc——库）；解释器启动（CPython 的 site/import——运行时）；命名空间、cgroup、seccomp 安装、页清零、微虚拟机创建（内核/虚拟化）。
- 加速库做什么：posix_spawn/vfork 路径在 openEuler 的 Python、Node、Go 运行时默认化；动态链接加速（预链接、代码段用大页、ld.so 缓存、减依赖）；locale 与分配器初始化的成本；解释器启动（冻结模块、import 缓存）；作为运行时功能提供预先 fork 好的进程池。
- 明确不做、写成依赖项：fork 页表复制、命名空间/cgroup/seccomp、页清零、微虚拟机创建与快照恢复——内核与虚拟化团队。
- 预期收益：每请求 25–350 毫秒里的用户态大头（bash 165 ms → 40 ms 那类优化的主要成分就是用户态）〔推算〕；RL 场景的收益取决于内核侧是否同步跟进。→950。

**S2 的展开：一次进程创建的时间线与各段的发力点。** Agent 里一次 Bash 调用的真实链路是 Claude Code（Node 进程，几百 MB 堆）→ [bubblewrap 包装] → `bash -c` → 命令本身 → 命令再起的子进程，所以每一段在一次工具调用里发生 2–5 次。

**S6〔P1〕面向推理 host 的内存分配器：大页后端 + Arm 调优。**（推理 host 通用，Agent 的长上下文把它放大。）
- 问题：Blink 测到主流推理栈在 host 侧干扰下 kernel 之间的间隙从 1 微秒涨到 40 微秒、页表遍历占最后一级缓存停顿周期的 85%，根因是 Python 堆的碎片化虚拟地址空间 [58]；vLLM V1 把 tokenize/detokenize 挪出核心循环后整体吞吐 +1.7 倍，归因于削减 CPU 开销 [74]；Arm 上换 mimalloc 快 2.3 倍 [74]。
- 按层拆：内存分配器的 size class 与 arena 设计（用户态库）；分配器用大页做后端——`madvise(MADV_HUGEPAGE)` 或 hugetlbfs（用户态库，只要求内核透明大页处于 madvise 模式，不改内核）；框架缓冲区（KV 块表、元数据）的大页分配接口（库 + 框架适配）；透明大页策略、khugepaged、mTHP/contpte（内核）；TLB 容量与页表遍历器（硬件 →960）。
- 加速库做什么：Arm 调优的 mimalloc/jemalloc + 大页后端；给 MindIE/vLLM 的缓冲区提供大页分配接口；host 进程与前端进程分核的部署建议。
- 明确不做、写成依赖项：透明大页策略、mTHP——内核团队。
- 证据强度：中。Blink 测的是问题，它的解法是把 host 整个拿掉，不是换分配器；"分配器 + 大页能消掉多少"要先在 MindIE/vLLM on 鲲鹏上测 TLB 缺失和页表遍历占比。→950。

**S3〔P2〕SVE2 版字符串搜索和正则。**
- 做什么（2026-09-21 修正：grep、ripgrep、git grep 都不用 Hyperscan/Vectorscan，Vectorscan 从这条链里去掉，只对 ClickHouse、入侵检测类客户有意义）：① 给 Rust 的 memchr、aho-corasick（Teddy：用向量查表指令同时比对几十个短字符串的开头指纹，是 Hyperscan 思路的 Rust 重实现；ripgrep 和 regex 库靠它加速多关键词搜索）加 SVE2 路径——`MATCH` 指令天然适合"一个字节同时比对多个候选"，Claude Code 的 Grep 工具就是内置的 ripgrep，直接受益；② 确认 openEuler 的 glibc 用上了 Arm optimized-routines 里的 SVE 版 memchr/strlen 等字符串函数——GNU grep（自己的 DFA + kwset，底层大量调 memchr）和几乎所有程序都受益；③ PCRE2 的 aarch64 JIT（ripgrep -P、git grep -P 用它）目前是 NEON/标量，评估 SVE 收益。
- 为什么是 P2：显式调用只占 2–3%，但无处不在（Bash 里、日志过滤、MCP 文件系统服务器、代码索引），单次 10 毫秒到几秒。→950。

**S4〔P2〕JSON、base64、UTF-8 的启用和绑定。**
- 判断：simdjson、simdutf 在鲲鹏 920 的 NEON 上已经够快，950 如果有 SVE2 也只再快 1–4% [81]。真正的差距在 **Python/Node 绑定**（orjson、simdjson-py、Node 的 simdjson 绑定）和 MCP 传图片用的 base64。工作内容是"确认 openEuler 软件包里 NEON 路径默认打开、发布语言绑定"，不是新算法。→950。

**S5〔P2〕哈希。**
- 前缀缓存的块哈希（SHA-256、xxh3、blake3）、内容寻址存储、git 的 SHA-1。Armv8 自带 SHA-1/SHA-256/SHA-512 指令；xxh3、blake3 可以做 SVE 版。KAE 的加密引擎对 KB 级小块做同步调用不合算（Accelerometer [20] 的接口模型结论：卸载往返比省下的 CPU 时间还长）。每请求约 4 毫秒，低优先。→950。

### 4.3 KAE（加解密、压缩）

**K1〔P0〕把"活着但空闲"的会话状态压缩在内存里（zswap/zram 和 KV 缓存卸载压缩）。**
- 问题：会话 80% 时间空闲，但每个会话的 0.8 GB 沙箱内存和 1.5 GB KV 缓存一直占着 [57]；内存已经占服务器成本的一半左右 [81]。
- 依据：Intel 用自家 IAA 加速器做 zswap 的压缩，30 进程、64 KB 页的场景吞吐提升 62%、系统时间减少 28%，驱动从 Linux 6.8 进主线，2026 年又加了批量压缩补丁 [74]；AgentSysBench 把空闲会话的状态卸出高速内存省了 4.6 倍内存 [57]。
- 做什么：KAE ZIP 的 zswap/zram 后端（openEuler 内核驱动加批量压缩接口，对标 iaa-crypto）；沙箱的匿名内存页和 KV 缓存分开处理——fp16/bf16 张量直接压几乎没效果 [48]，要先做 TRACE 论文的位平面变换 [70]；和 UB 内存池分层配合（见 `INSIGHT_AI_WORKLOAD.md` 4.3）。
- 预期收益：每台机器能停放的会话数乘以匿名页的压缩比（2–3 倍）〔推算〕。
- 先测：KAE zswap 在 0.8 GB 沙箱工作集和 1.5 GB KV 上的压缩比、延迟、节省的 CPU。→950 软件；KV 专用变换加通用 codec →960。

**K2〔P1〕git 对象、容器镜像、沙箱快照的 zlib/zstd 和 SHA 走 KAE。**
- 问题：git 的每个对象都是 zlib 压缩的，clone、checkout、status、diff 都要大量解压，每个对象 KB 到 MB；容器镜像层是 gzip 或 zstd；Firecracker 启动时解压内核要 40 毫秒 [51]；RL rollout 每条轨迹都要 clone 或解包一个仓库 [76]。
- 已知和未知：KAE ZIP 公开的指标是大块吞吐（压缩 7 GB/s、解压 8 GB/s，见 REPORT 6.2），**对 KB 级小对象做同步调用的延迟没有公开数据**——这是 REPORT 里已经列出的待测项。
- 做什么：libz、zstd 的 KAE 后端在 git、containerd、StratoVirt 快照路径上默认启用，并设一个"多小的对象不值得卸载"的阈值。→950。

**K3〔P2〕TLS 和网关。** MCP 走 HTTPS、WebFetch、API 网关的握手可以用 KAE 的 HPRE/SEC；但连接复用之后加密占比很小（谷歌 fleet 不到 0.2% [02]），只在高并发的 Agent 网关或搜索代理上成立。→950。

**K4〔P2，→960〕KV 缓存的通用无损压缩。** TRACE 论文证明先做位平面变换再用通用压缩算法能把 KV 压掉 46.9% [70]，通用压缩这一步可以放 KAE；前提是变换部件放在内存侧还是核侧要先定。

### 4.4 KML（数学库）

**M1〔由搜索推荐团队负责，不列入基础加速库规划；此处仅保留分析〕向量检索的核心算子：矩阵乘、距离、乘积量化、取前 k。**
- 问题：精确检索占 RAG 端到端 84.5–90.6% [78]；生产向量库占 47% [57]。faiss 的 FLAT 索引本质是 BLAS 的 sgemm，IVF-PQ 是查表加累加（SVE2 的 TBL 指令合适），HNSW 是随机访问加 fp16/int8 点积。
- 做什么：让 faiss、Milvus 默认链接 KML BLAS；SVE 的 fp16/bf16/int8 距离核；PQ 扫描把内存带宽用到 80% 以上 [52]；HNSW 的预取和批处理。
- 优先级取决于客户组合：编码 Agent 几乎不用向量检索，企业 RAG、搜索、深度研究型 Agent 是主项。→950。

**M2〔P2〕CPU 上的小模型：embedding、重排、摘要。** AgentSysBench 里 embedding 组件比其它组件慢 32 倍 [57]，LexRank 摘要 3.5 秒 [78]。做 bf16/int8 矩阵乘（Neoverse V2 上 BF16 2.7 倍、INT8 4.8–6.2 倍的量级 [74]）和稀疏矩阵图算法；长期看要不要投 SME2 级矩阵扩展是 `INSIGHT_AI_WORKLOAD.md` 争议 5 →960。

### 4.5 存储、网络、虚拟化路径（2026-09-21 口径修正：这一节的大部分是内核与虚拟化团队的工作，加速库只保留用户态部分，其余写成依赖项）

**V1〔依赖项：内核 / 虚拟化团队；加速库不承担〕沙箱创建、恢复、隔离的 CPU 路径。**（成立条件见 3.6 的判断表：创建开销只在高频创建场景大；隔离放大取决于技术选择，可避开。命名空间/cgroup/seccomp、二级页表、页清零、快照恢复缺页都在内核或 KVM 里；StratoVirt 的 VMM 虽在用户态，但属虚拟化团队。加速库能做的只有 S2 里的用户态进程启动部分。以下保留原分析供内核团队参考。）
- 两档要分开做：
  - 进程级（bubblewrap/seccomp/Landlock，本地和一部分云端）：namespace 和 cgroup 创建、seccomp 过滤的开销、文件系统视图（bind mount、overlayfs）。
  - 微虚拟机（StratoVirt/Kata/Firecracker）：二级页表和大页、内存清零（Arm 的 DC ZVA 整行清零指令或 SVE 版 memset）、快照恢复时预取工作集（REAP 降 3.7 倍 [64]）、virtio-fs/DAX 文件路径、用 KSM（内核的相同内存页合并机制）对同镜像的沙箱做内存去重。
- 目标：进程级创建 30 毫秒以内、微虚拟机 125 毫秒以内、系统调用放大不超过 1.3 倍（gVisor 是 2.2 倍 [64]）、快照恢复后执行退化不超过 20%（现在 95%）。
- 预期收益：RL rollout 里 40–60% 的初始化开销 [76]；云端 Agent 平台每核能装几个沙箱。
- 先测：用 TraceLab 的工具混合（Bash 47%、Read 23%、Edit 13%）做一个微基准，在 920/950 上跑裸机、bubblewrap+seccomp、runc、gVisor、StratoVirt、Kata 各档，量放大倍数。→950 软件；硬件辅助的创建/清零/快照 →960（`INSIGHT_AI_WORKLOAD.md` 税表 #11）。

**V2〔依赖项：内核团队；加速库只保留 io_uring 的用户态封装〕文件系统和 I/O 路径。** Read/Edit/Grep 的 open/stat/read（io_uring、页缓存亲和）、overlayfs 快照（SWE-MiniSandbox 的做法 [76]）、git 的大量 lstat。沙箱里 tmpfs 和外部文件系统差 216 倍 [64]，说明"把工作目录放对地方"比任何库优化都大。→950。

**V3〔P2〕网关和状态层的网络。** MCP 每条消息一次 HTTP POST [74]，网关可以做 HTTP/2 复用和用户态协议栈；会话状态和 KV 缓存的停靠层走 UB 内存池（`INSIGHT_AI_WORKLOAD.md` 4.3 的 U1–U10）；搜索和抓取结果的跨会话缓存（67.3%、64% 的重复 [57]）是存储层功能。→950。

## 附录 A：tokenizer 是什么、各模型一样吗、加速库该做通用的还是按模型做

（2026-09-21 补，回答团队内的概念问题；配合 4.2 节的 S1。）

### A.1 tokenize 是什么

模型不认识文字，只认识整数。tokenize 就是把一段文本变成一串整数的过程：先把文本切成一个个片段（token），再把每个片段换成它在"词表"里的编号（token ID）。反过来，模型生成的整数串换回文本，叫 detokenize。词表是一张固定的表，一个模型训练时定下来就不再变；今天主流大模型的词表有 10 万到 25 万个条目。

之所以不按"字"或"词"切，是因为要同时满足三件事：词表不能太大（每个条目对应模型里的一行参数）、任何输入都得能表示（生僻词、代码、表情符号、乱码）、常见的词最好一个 token 就能表示（省长度）。子词切分（把 "tokenization" 切成 "token" + "ization"）是这三者的折中。

### A.2 流程：四步

以今天最常见的"字节级 BPE"为例（GPT 系、Llama 3、Qwen、DeepSeek 都是这一类）：

1. **规范化**（可选）。有些 tokenizer 会先做 Unicode 归一化或大小写处理；大模型多数不做，或只做很少的处理。
2. **预分词**。用一条正则表达式把文本切成短片段，大致按"一个单词 / 一串数字 / 一串标点 / 一段空白"来切。这一步决定了 token 永远不会跨片段合并，比如 "hello world" 先切成 "hello" 和 " world"（注意空格归到后一个片段）。GPT-4 的规则里数字最多 3 位一组，所以 "2026" 会被切成 "202" 和 "6"。
3. **BPE 合并**。每个片段先拆成字节，然后按一张"合并表"反复把相邻的两个符号并成一个，优先级高的先并，直到并不动为止。合并表是训练时从语料里统计出来的：最常一起出现的字节对最先被合并。
4. **加特殊标记**。在序列前后加上模型要求的控制符（对话开始、角色、结束等），这些也是 token，但不来自文本。

**手算一个玩具例子。** 假设合并表只有三条：第 1 条 "l"+"o" → "lo"，第 2 条 "lo"+"w" → "low"，第 3 条 "e"+"r" → "er"。对片段 "lower"：先拆成 l o w e r；按优先级找：第 1 条能用，得到 lo w e r；第 2 条能用，得到 low e r；第 3 条能用，得到 low er；再没有可合并的，结束。结果是两个 token："low" 和 "er"，再查词表换成两个整数。真实的合并表有十几万条，过程完全一样。

**在推理服务里它处在哪。** 用户的对话（messages 数组）先套上模型的对话模板变成一整段文本，再 tokenize 成 ID 序列，再按块算哈希去查前缀缓存，然后交给推理引擎；生成侧每出一个 ID 就 detokenize 一次流式返回（要处理一个汉字被拆在两个 token 里、UTF-8 还没凑齐的情况）。

### A.3 各模型一样吗：不一样，而且差在三层

| 层 | 差异 | 例子 |
|---|---|---|
| **算法家族** | BPE（大模型主流）、WordPiece（BERT）、Unigram（T5 等 SentencePiece 模型）；BPE 又分字节级和字符级加字节回退 | GPT-2 到 GPT-5、Llama 3、Qwen、DeepSeek、Kimi、gpt-oss 都是字节级 BPE；Llama 2、Gemma 是 SentencePiece |
| **预分词规则** | 正则表达式不同：数字几位一组、中日韩文字怎么处理、标点和空格怎么归属、是否区分大小写缩写 | Qwen 把数字一位一位切；GPT-4、Llama 3、DeepSeek 最多 3 位一组。DeepSeek-V3 的 tokenizer.json 里预分词是三条规则依次套用：先切 1–3 位数字，再把连续的中日韩文字单独切出来，最后用一条 GPT 风格的正则处理其余〔从 HuggingFace 上的配置文件直接读到〕 |
| **词表与合并表（数据）** | 每个模型完全不同，编号完全不同 | GPT-4 约 10 万、GPT-4o 约 20 万、Llama 3 约 12.8 万、Qwen 约 15.2 万、DeepSeek-V3 12.8 万 + 818 个特殊 token、Gemma 约 25.6 万；Claude 的 tokenizer 不公开 |
| **特殊 token 与细节开关** | 对话控制符不同；有的模型规定"整个片段在词表里就直接用、不走合并"（ignore_merges，Llama 3、gpt-oss 有）；SentencePiece 的空格前缀、字节回退 | 这些开关错一个，输出的 ID 就和参考实现不一致 |

后果：同一句话在不同模型下 token 数不同（中文在 Llama 2 上大约一个字两三个 token，在 Qwen 上大约一个 token 一个多字），ID 完全不同；用错 tokenizer 等于给模型喂乱码，而且前缀缓存按 ID 序列查，错一个 ID 后面全部不命中。所以 tokenize 的第一要求是**和模型厂商的参考实现逐位一致**，速度是第二位。

### A.4 加速库该怎么做：一个通用引擎，按模型加载数据

答案是**不需要给每个模型写一个 tokenizer，但需要给每个模型做一次验证**。类比 zlib：一个解压引擎能解所有文件，因为格式是标准的、内容是数据。tokenizer 也是这样：算法只有两三种，模型之间的差别几乎全在配置文件里——HuggingFace 的 tokenizer.json（含词表、合并表、预分词正则、开关）、OpenAI 的 tiktoken 文件、Google 的 SentencePiece 模型文件。HuggingFace 的 Rust 库 tokenizers 就是这么做的：一个引擎，加载任意模型的 tokenizer.json。

引擎里哪些是通用的、哪些是按模型的：

| 部件 | 通用还是按模型 | 说明 |
|---|---|---|
| 配置加载器 | 通用（三种格式） | 读 tokenizer.json / tiktoken / SentencePiece，构建词表和合并表的哈希结构 |
| BPE 合并核心 | 通用 | 线性算法（GitHub 的 bpe 库那种），一次实现覆盖所有字节级 BPE 模型；Unigram/WordPiece 另做，优先级低（大模型服务几乎不用） |
| 预分词 | 引擎通用，**加速规则按家族** | 正则各家不同，但主流只有十来种模式（GPT-2 系、GPT-4 系、GPT-4o 系、Llama 3、Qwen、DeepSeek、Kimi、SentencePiece 空格规则等）。TokTier 的做法是把每种正则改写成"按字符类分段"的规则再用向量指令跑，这一步是按家族生成的；没见过的正则退回通用正则引擎，先保证对，再谈快 |
| 会话状态与增量修复 | 通用 | 保存每个会话的 token 序列，追加时只重切末尾一小段并校验边界（TokTier 的契约），与模型无关 |
| 验证 | **按模型** | 每个模型、每个版本的配置文件按内容哈希登记，和参考实现（HuggingFace / tiktoken）在多语言 + 代码语料上逐位对比；任何一个开关不一致都会在这里暴露。TokTier 之所以说"认证是按配置做的，不是按'HuggingFace tokenizers'笼统做的"，就是这个原因 |

对鲲鹏要覆盖的范围：本地和云上用 MindIE、vLLM、SGLang 部署的开源权重模型——Qwen、DeepSeek、GLM、Llama、Mistral、Gemma、Kimi、MiniMax、盘古、gpt-oss——它们的 tokenizer 配置全部公开。Claude、GPT 的私有 tokenizer 不公开，但它们只在厂商自己的服务里跑，本地部署碰不到，不影响这件事。

### A.5 为什么它慢，加速的空间在哪

预分词是一条允许回溯的正则从左到右扫，天然串行；合并阶段对每个片段反复找"优先级最高的相邻对"，每次都要查哈希表，内存访问随机、分支多；tiktoken 的写法在片段很长时是平方复杂度——代码里的长串（base64、压缩过的 JS、没有空格的日志）正是这种情况。所以同样的 480 KB 上下文，HuggingFace 实现要 228 毫秒核时，Rust 的 fastokens 13.4 毫秒，增量修复 2.3 毫秒 [68]。加速的空间按大小排：先换线性算法和增量（软件，10 到 100 倍），再用 SVE2 加速预分词的字符分类（第二位），最后才是把整段切分搬到 NPU/GPU（TokTier 的 GPU 路径 0.15 毫秒，但要占一块加速器）。

### A.6 有标准的库实现吗

没有正式标准（没有 ISO 那种规范），但有三个事实上的参考实现和一种事实上的交换格式。模型厂商发布模型时附带的 tokenizer 配置文件，配上这三个库之一，就是"正确答案"的定义。

| 库 | 维护者 | 语言 | 配置格式 | 谁在用 | 许可证 | 实现特点 |
|---|---|---|---|---|---|---|
| **tokenizers** | HuggingFace | Rust 核心 + Python/Node 绑定 | tokenizer.json（含规范化、预分词、模型、后处理、解码、特殊 token 六段） | 几乎所有开源权重模型的参考实现：Qwen、DeepSeek、GLM、Llama、Mistral、Gemma、MiniMax…；vLLM、SGLang、TGI、TensorRT-LLM、transformers 都用它 | Apache-2.0 | 支持 BPE、WordPiece、Unigram；正则后端默认 oniguruma（C 库），可切换 fancy-regex；批处理用 rayon 多线程（就是 [69] 里和推理引擎抢核的那个开关） |
| **tiktoken** | OpenAI | Rust 核心 + Python | .tiktoken 文件（每行一个 base64 的 token 和它的优先级） | OpenAI 模型；Llama 3、Kimi、gpt-oss 也用这种格式发布 | MIT | 只做字节级 BPE；正则用 fancy-regex；片段很长时最坏平方复杂度 |
| **sentencepiece** | Google | C++ + Python | .model（protobuf） | Llama 2、Gemma、T5、Mistral 早期版本 | Apache-2.0 | BPE 和 Unigram 都支持，自带规范化，空格用特殊符号表示 |

在这三家之上，有一批"换核"的更快实现，思路都是保持格式和结果不变、换掉算法：

| 实现 | 来源 | 特点 |
|---|---|---|
| bpe / bpe-openai | GitHub（Rust crate，MIT） | 线性复杂度的 BPE，支持增量编码和子串计数；单线程比 tiktoken 快约 4 倍、比 HF 约 10 倍 |
| fastokens | Crusoe Cloud（Rust crate） | 同时读 tokenizer.json 和 .tiktoken；带前缀输入缓存；TokTier 表 8 里 13.4 毫秒那一档就是它 |
| quicktok、rs_bpe | 个人/社区 | 与 tiktoken 逐字节一致，快 3.5–11 倍 |
| dynamo-tokenizers | NVIDIA Dynamo | 推理前端的 Rust tokenizer，说明大厂已把 tokenize 当成前端组件单独做 |
| llama.cpp 内置 | ggml 社区（C++） | 自己实现了 BPE、SentencePiece、WordPiece 三种，不依赖上面任何库 |
| tokenizers-cpp | MLC | 把 HF 的 Rust 核和 sentencepiece 包成 C++ 接口，给 C++ 推理引擎用 |

推理框架用的是哪一个：vLLM、SGLang、TGI、TensorRT-LLM 走 HF tokenizers 的 Python 绑定（vLLM V1 把它挪到单独进程 [74]）；Dynamo 用自己的 Rust 前端；llama.cpp 用内置；MindIE 应当也是 HF tokenizers〔待核实〕。

**在 Arm 上的现状。** 以上全部是纯 Rust 或 C++，在 aarch64 上都能编译运行，但**没有任何一家有 NEON 或 SVE 的专门路径**，性能全靠编译器自动向量化；正则后端（oniguruma、fancy-regex）是标量回溯引擎。所以"鲲鹏上的 tokenizer"今天就等于直接跑 HF tokenizers，落在每核 2 MB/s 那一档。

**对 S1 的三条实现路径。**
1. **换核（drop-in）**：做一个和 HF tokenizers Rust crate 接口兼容的实现（或直接给 fastokens、bpe 这类库加 SVE2 预分词路径），vLLM、SGLang、MindIE 不改代码就能用。路径最短，收益马上能测。
2. **上游贡献**：给 HF tokenizers 提 aarch64 性能补丁。受益面最大，但合入节奏不受控，且增量/会话状态这类接口改动上游未必接受。
3. **独立服务**：TokTier 式的 tokenization 服务，放在网关和引擎之间，保存会话状态、做增量修复，需要框架改接入。收益最大（2.3 毫秒那一档），但要推动 MindIE/vLLM 前端改造。
建议 1 和 3 并行：1 先把每核吞吐从 2 MB/s 拉到 30 MB/s 以上，3 再把"全量重切"变成"只切追加"。两条路的正确性都用同一套办法保证——对每个模型的配置文件，和 HF/tiktoken 在多语言 + 代码语料上逐位比对。
