## 1. 要解决的问题（含 motivation 数据）

- 学术 benchmark（DeathStarBench、µSuite、Acme Air）规模 ≤40 个服务、调用图固定，不能代表生产环境。
- 目标：刻画微服务调用图的结构与动态性、微服务间的依赖类型、运行时性能（RT）与资源干扰的关系，并给出一个能生成大规模真实感 trace 的随机图模型。

## 2. 核心思路

纯测量 + 建模。数据来自阿里 ARMS（类 Dapper）：每分钟容器级系统指标（CPU/内存利用率、CPI、MPKI、JVM heap/GC）+ 按 TraceID 采样的调用记录（UM/DM、接口、RT、通信范式）+ 每微服务的聚合调用统计。

## 3. 系统设计 / 软硬件分工（阿里部署形态的关键事实，直接服务第 2 章）

- **运行载体（形态 B）**：Kubernetes 管理**裸金属**集群，软硬件混合的 virtio I/O；在线微服务跑在普通容器里，**与离线批处理作业（Fuxi 调度、安全容器）混部在同一台裸金属机上**以提高利用率。
- **有状态服务独立部署（形态 C）**：数据库和 Memcached 部署在**专用集群**，不与批处理或无状态服务共享。
- **三种通信范式**：RPC（双向同步）、MQ（单向、经第三方持久化）、IPC（进程间，通常在无状态服务与有状态服务之间）。**无状态服务之间：RPC 76%、MQ 23%、IPC 1%** —— MQ 占比远高于学术 benchmark 的假设。
- **语言**：指标里有 JVM heap/GC，说明 Java 是主流运行时（与 Meta 的 Hack/C++、Google 的 C++ 都不同）。→ 序列化/RPC 开销分析必须考虑托管语言的 GC 与对象模型。
- 每个微服务通常跑在**数百到上千个容器**中，所有容器同配置、均衡负载。

## 4. 关键定量结果

**A. 调用图结构**
- 图大小服从 Burr 重尾分布：**>10% 的调用图含 >40 个微服务**，最大的有数百到数千个；大图中 ~50% 的节点是 Memcached（比小图高 20 个百分点）。
- **常见深度为 3**（前端 → 业务微服务 → Memcached）；平均深度 4.27（σ=3.25）；>4% 的图深度 >10。
- 树状：大多数节点入度为 1；>10% 的无状态微服务出度 ≥5；深度 >2 的层有 >60% 概率只含一个微服务（深图多为长链）。
- 深度增加时 S2M（访问 Memcached）比例线性下降、S2D（访问 DB）亚线性上升、MQ 比例上升 → 缓存命中率随深度下降，MQ 用于把深层调用异步化以缩短端到端 RT。

**B. 热点与动态性**
- **>5% 的微服务聚合入度 ≥16，这些"超级微服务"出现在 ~90% 的调用图中、处理 95% 的调用**。
- 同一个在线服务可产生 >9 类拓扑不同的调用图；用 InfoGraph + K-means 可以聚类，类内 RT 稳定、类间差异大（>90% 服务的类内/类间方差比 <0.6）。

**C. 依赖类型（可用于优化服务拆分）**
- 环形依赖占 7.8%（几乎都经 RPC），其中 2.7% 是强环形依赖（UM 调 DM 后 DM 以 83% 概率经同一接口回调 UM）。
- 强耦合依赖（UM 每次被调都多次调同一个 DM、且 DM 不被别人共享）→ **合并这两个接口可以把远程调用变成本地调用**，直接减少 RPC 数。

**D. 运行时性能（对硬件最相关）**
- 微服务调用率（MCR）与 **CPU 利用率强相关**（>80% 的微服务 Spearman >0.6）、与 Young GC 强相关；与内存利用率不相关（>20% 为负相关；内存利用率方差 <10%）。
- **容器 CPU 利用率极低**：即使在 P95 调用率下，多数容器分钟级 CPU 利用率 <10%；RT 随调用率基本不变（无排队）→ 有很大的缩容空间。
- **主机 CPU 干扰**：以主机 CPU 利用率 10% 为基线，30% 时平均 RT 劣化 20%；>40% 劣化 >20%，>80% 劣化 >30%（75 分位）。**主机内存利用率 <60% 时干扰可忽略**。
- 各主机每分钟 CPU 利用率方差可达 20% → 批处理负载在主机间仍有很大的均衡空间。

## 5. 对芯片 & 服务器厂商的启示

1. **RPC 不是唯一的通信范式**：MQ 占无状态服务间通信的 23%。MQ 的开销形态（持久化写、拉取、序列化两次）与 RPC 不同，加速器设计若只盯 RPC 会漏掉这四分之一。
2. **微服务对 CPU 干扰的敏感度是混部的核心矛盾**：主机 CPU 利用率从 10% 到 30% 就让 RT 劣化 20%。这直接指向硬件隔离能力（核/LLC/内存带宽的 QoS、SMT 隔离）和"在线专用小核 + 离线大核"的异构 SKU 思路；同时说明**内存干扰不是瓶颈**——与 Kanev 2015"带宽过配"一致。
3. **利用率 <10% 是常态**：微服务的 CPU 大部分时间在等请求；这为"多实例高密度打包"和"低唤醒延迟"提出需求——能快速从空闲状态响应 RPC 的核（浅睡眠态、快速 C-state 退出）比峰值算力更重要。
4. **热点集中在超级微服务**：5% 的微服务处理 95% 的调用，且很多是 Memcached/DB 前端 → 针对少数高频服务做专用优化（类似 Google 的 method-specific accelerator）在阿里同样成立。
5. **Java 主导** → 硬件加速序列化时要面对 JVM 对象布局、GC 与堆外内存的问题，这与 C++ 世界的零拷贝方案（zBuffer/Cornflakes）的假设不同，是一个值得关注的空白。
6. **调用图深度 3 + 叶子是缓存**：和 Meta 一样，"每请求 RPC 数"的放大主要来自对缓存/存储层的扇出。

## 6. 局限 / 争议

- 只有 RT，没有 CPU cycles 分解，无法直接得到"每 RPC 成本"。
- 分钟级聚合指标，看不到 µs 级尾延迟。
- 只覆盖阿里的一部分集群；"微服务"定义与 Meta/Google 不同，Meta 论文明确指出无法严格横向比较。
- 论文对 MQ 减少 RT 的解释是推断，不是控制实验。
