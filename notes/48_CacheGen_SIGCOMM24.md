## 1. 要解决的问题（含 motivation 数据）

- 长上下文复用 KV 可避免重算，但 KV 很大（例：一个上下文的 KV 可达 19 GB，与模型同量级），且复用间隔可达数小时 → 必须从 GPU 卸到 CPU/存储甚至专用存储服务器，再经网络取回；取回延迟可与重算相当甚至更长。
- 现有 KV 量化面向 GPU 内存占用，不面向网络传输。

## 2. 核心思路

- 观察：同层相邻 token 的 K/V 差分（delta）熵比原值低 2.4–2.9×；浅层对量化更敏感；同一 layer/channel 的值分布相近 → 按组建模的算术编码。
- 编码：delta → 逐层量化 → 算术编码；生成多个压缩级别版本；流式传输时按带宽在块粒度切换级别，必要时回退到发文本重算。

## 3. 系统设计 / 软硬件分工

- 编码离线（每上下文 ~200 ms），解码 GPU 实现并与传输流水；存储总开销与量化基线相当。
- 测试床：Xeon Gold 6130 + 384 GB + GPU；模型 Mistral-7B、Llama-70B 等。

## 4. 关键定量结果

- KV 体积：比 8-bit 量化基线小 3.5–4.3×（即相对 fp16 约 7–8.6×，本笔记推算）；TTFT 比量化基线快 3.2–3.7×，比发文本重算快 3.1–4.7×；相对近无损量化仍快 1.67–1.81×。
- 解码计算量相对 prefill 可忽略；编码 200 ms。

## 5. 对芯片 & 服务器厂商的启示

1. **通用压缩对 KV 无效、专用变换有效**：有效成分是 delta + 量化 + 算术编码（视频编码思路），这三步都不是 zlib/zstd 引擎能做的——洞察第 3 节末的"压缩价值被高估"判断得到支持：KAE zip 不应用于 KV；若要做，是一个新的"张量压缩"引擎（delta/量化/熵编码）。
2. **价值条件**：只有 KV 需要跨网络（尤其 <100 Gbps）或落盘时才值得压缩；在 UB 内存池（TB/s 级、内存语义）场景，压缩的收益要重新评估——这正是洞察 4.2 表里"条件见 4.2"的含义。
3. 解码放在 GPU/NPU 而非 CPU——若做硬件引擎，位置应靠近 NPU 或在互连路径上，而不是 CPU 侧的 KAE。

## 6. 局限 / 争议

- 面向 2023–24 的 GQA/MHA 模型；MLA（每 token 70 KB）本身已压 4–5×，叠加收益未知。
- 有损（质量"几乎无损"依赖任务）。
