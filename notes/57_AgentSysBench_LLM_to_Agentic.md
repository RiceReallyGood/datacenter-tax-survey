## 1. 要解决的问题（含 motivation 数据）
- Agent 服务系统沿用单次推理的假设；没有研究在统一栈上插桩多类 Agent 并对照生产 trace。

## 2. 关键发现（数字）
- **时延构成**：GUIAgent 的容器化桌面沙箱占 >70% 执行时间，Pi-AutoR 的实验运行时占 90%；非 LLM 组件在 5/10 应用主导。
- **前缀复用**：迭代循环类应用命中率可达 99%；每轮重排/动态取上下文的 DeepResearch 降到 1%。
- **状态三类**：可驱逐的 KV 性能状态；持久正确性状态（DeepResearch 每会话向量库 7.4 MB，大会话 >49 MB；编码 Agent 的文件系统/依赖/进程元数据）；**活动工作集**（沙箱峰值 DRAM 中位 0.8 GB，编译/单测时峰值 28 GB）。建议在静止点做快照、把空闲会话的 KV 卸出 GPU。
- **数据搬移**：单次执行产生数十 MB：GUI 截图每步最大；DeepResearch 一次请求传 >20 MB 序列化 embedding（≈5,000 × 1,024 维 FP32）；GUIAgent 每会话累计 >10 MB 文本往返。"序列化/反序列化/传输消耗大量带宽与 CPU 周期，独立于算力配置地限制并发与时延"。
- **成本**：工具重的应用非 LLM 费用占主导（Pi-AutoR 沙箱 >99%）；根源是串行执行时沙箱/检索环境空转计费 → 需要沙箱多路复用、空闲时 pause/snapshot/resume。
- **异构 HOL**：同一应用内组件时延差 32×（Embed-Doc 比 … 慢 32×），单队列造成队头阻塞。
- **生产 trace**：中位会话执行占生命周期 20%，70% 会话执行不足一半（§7.1 "Long Idle-but-Live Intervals"、图 20(a)；分母是会话生命周期，分子是模型调用和工具执行的时间，35,037 个编码 Agent 会话、24 h；空闲指等人批准、等子 Agent 返回或等下一条指令，期间沙箱、终端上下文、KV、对话历史都保持可恢复）；空闲间隔从几秒到几小时（含过夜），多数在 1–10 min（图 20(b)），期间每会话的沙箱一直分配着；**5 min TTL 下 59.4% 会话至少一次驱逐，驱逐贡献 55.9% 的 cache-create token、31.5% 的总费用**（按 Claude Opus 4.6 定价估）；3,170 次压缩事件，99% 压掉 >70% 上下文，每次平均 156 s（p99 775 s，输入 176K、输出 5K）；辅助任务（安全护栏、循环检测）额外 2,684 次调用 / 6.5M 输入 token；搜索应用 373,678 条查询中 27% 唯一查询重复出现、占 67.3% 调用。

## 3. 对芯片 & 服务器厂商的启示
1. **"活着但空闲"（原文 idle-but-live，§7.1）是 Agent 状态层的主形态**（中位会话执行只占生命周期 20%，即中位 80% 时间空闲；"主形态"是本笔记的归纳，原文 §8.3 的说法是"production sessions spend the majority of their lifetime idle but holding expensive state"）：这为"把空闲会话的 KV 与沙箱状态放到 CPU DRAM / UB 内存池 / SSD"提供了直接依据；鲲鹏大内存节点 + UB 内存池的价值在这里，而不是在活跃计算。
   > **2026-09-30 更正。** 初稿写"状态卸载 4.6× 内存节省就是这么来的"，不对。原文 §8.3 的状态卸载实验是受控的 Mini-SWE 实验：在模型规划调用超过阈值时把闲着的沙箱卸出、下一步工具调用前恢复，所有并发沙箱进程的总驻留内存平均降 4.6×、峰值降 2.1×，延迟增加不到 0.5%。原文明确说它针对的是组件之间的空闲，"rather than an evaluation driven by the human-paced production pauses in §7.1"，而且不能和每会话 28 GB 的峰值比较。所以它只说明"卸载闲着的沙箱"可行，不是"卸载空闲会话"的收益证明，后者没有测过。
2. **沙箱工作集峰值 28 GB、中位 0.8 GB**：沙箱密度由峰值/中位的差决定，需要超分 + 静止点快照——硬件辅助快照/页拷贝（→960）与大内存容量（→950）都对上。
3. **序列化/搬移税被点名**：每会话数十 MB 的 embedding（FP32 向量）、截图、上下文往返 → 洞察税表 #2 的"JSON/tensor 序列化"与 #1 的搬移在 Agent 场景是实测存在的 CPU 消耗；embedding 用 FP32 JSON 传是最浪费的形态（零拷贝/二进制格式/fp16 立刻 2–4×）。
4. **控制面税**主要烧 NPU（上下文容量、辅助调用、重 prefill），不是 CPU；但它决定了 KV 池 TTL 的经济性：TTL 从 5 min 延长到覆盖 1–10 min 的人类空闲，需要的正是便宜的大容量 DRAM 层。
5. 组件时延差 32× + 队头阻塞 → 任务级分离部署（29–40%）：CPU 型沙箱、内存型检索、GPU 型推理分别放到各自的节点池——与 CloudMatrix 6.1.3 的 CPU 池化、TaiShan SuperPoD 方向一致。

## 4. 局限
- 受控实验的绝对数依赖其 benchmark 选型；生产 trace 只有三个应用、24 h；成本按公开定价估算。
