# Tokenizer 详解（给基础加速库团队的入门到设计手册）

> 2026-09-21 写，配合 `INSIGHT_AGENT_DEEPDIVE.md` 附录 A 与发力点 S1。数字来源：[68] TokTier、[81] 网络资料（GitHub bpe、tiktoken、HF tokenizers、GPUTOK）、本机读取的 DeepSeek-V3 tokenizer.json；经验值标〔经验〕。

## 1. 为什么需要 tokenizer

模型的输入层是一张"查表"：每个整数编号对应一行向量（embedding），输出层再把向量映射回编号的概率分布。所以文本必须先变成整数序列。三种最朴素的切法都不行：按字符切，序列太长（一个英文单词 5–6 个 token），模型每个位置能看到的信息太少；按单词切，词表无限大（新词、拼写错误、代码标识符、其它语言），而且模型参数里要给每个词一行向量；按字节切，序列更长。**子词切分**是折中：常见词整词一个 token，不常见的拆成几段，任何输入都能表示，词表固定在十万量级。

## 2. 三代方法、三种算法

| 算法 | 代表模型 | 训练时怎么得到词表 | 编码时怎么切 | 特点 |
|---|---|---|---|---|
| **BPE**（字节对编码；Gage 1994 用于压缩，Sennrich 2016 引入机器翻译） | GPT-2 到 GPT-5、Llama 3、Qwen、DeepSeek、Kimi、Mistral、gpt-oss（字节级）；Llama 2（SentencePiece BPE） | 从单字节（或单字符）开始，反复把语料里最常相邻出现的一对合并成新符号，直到词表到目标大小；合并的先后顺序就是"合并表"的优先级 | 按合并表优先级反复合并相邻对 | 确定性、实现简单、对代码和多语言友好 |
| **WordPiece** | BERT 系 | 类似 BPE，但合并时选"让语料似然提升最大"的对，而不是最频繁的对 | 贪心最长匹配：从左到右取词表里能匹配的最长前缀，续段带 `##` 前缀 | 只在编码器模型里常见 |
| **Unigram**（SentencePiece 实现） | T5、ALBERT、部分 SentencePiece 模型；Gemma 的 tokenizer 也是 SentencePiece（BPE 型） | 从一个很大的候选词表开始，反复删掉"删了之后似然损失最小"的条目 | 概率模型：用 Viterbi 找似然最大的切分；可采样得到多种切分（子词正则化） | 切分不唯一，可做数据增强 |

大模型推理今天几乎全是 **BPE**，且多为**字节级** BPE，所以后文以它为主。

## 3. 字节级 BPE 逐步拆解

### 3.1 为什么是"字节级"
早期 BPE 在字符上做，遇到词表没见过的字符（生僻汉字、表情、二进制垃圾）就只能输出"未知"。GPT-2 的做法是把文本先按 UTF-8 变成字节流，256 个字节值就是最底层的 256 个符号——任何输入都能表示。为了让词表文件仍是可读文本，GPT-2 把 256 个字节值映射到 256 个可打印的 Unicode 字符（空格显示成 `Ġ`、换行显示成 `Ċ`），这就是词表文件里那些怪字符的来历。SentencePiece 走的是另一条路：在字符上做，遇到词表外的字符再退回到字节（"byte fallback"），空格用 `▁` 表示。

### 3.2 四个阶段
1. **规范化**（可选）：Unicode 归一化（NFC/NFKC）、大小写。大模型多数不做或很少做，因为归一化会丢信息。
2. **预分词**：一条正则把文本切成短片段，合并永远不跨片段。GPT-2 的正则是
   `'s|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+`
   意思是：英文缩写后缀单独一段；"可选一个空格 + 一串字母"一段；"可选空格 + 一串数字"一段；"可选空格 + 一串标点符号"一段；空白按规则切。GPT-4 的 cl100k 改成数字最多 3 位一组（`\p{N}{1,3}`）、字母段允许前面带一个非字母非数字字符、换行单独处理。Qwen 把数字一位一位切（`\p{N}`）。DeepSeek-V3 是三条规则依次套：先切 1–3 位数字，再把连续中日韩文字单独切出，最后一条 GPT 风格正则处理其余（从它的 tokenizer.json 直接读到）。**预分词决定了 token 的上界**：一个 token 永远不会横跨两个片段，所以 "hello world" 永远是 "hello" 和 " world"（空格归后一个），"2026" 在 GPT-4 下是 "202" + "6"。
3. **BPE 合并**：每个片段拆成字节，查合并表，把优先级最高（rank 最小）的相邻对合成一个，重复到没有可合并的对为止。合并表十几万条，用哈希表存"字节对 → rank"。
4. **后处理**：加特殊 token（对话开始/结束、角色标记、BOS/EOS），这些 token 不来自文本，由对话模板插入。

### 3.3 手算一次
合并表假设只有三条：① `l`+`o`→`lo`，② `lo`+`w`→`low`，③ `e`+`r`→`er`。片段 "lower"：
```
l o w e r      能用的合并：①(l,o)
lo w e r       能用的合并：②(lo,w)
low e r        能用的合并：③(e,r)
low er         没有可合并的对 → 结束
```
输出两个 token："low"、"er"，再查词表换成两个整数。真实词表里 "lower" 很可能本身就是一个 token（合并表里有 `low`+`er`），那就是一个整数。

### 3.4 复杂度
- 朴素实现（tiktoken 的写法）：每轮扫一遍片段找 rank 最小的相邻对，片段长 n 时最坏 O(n²)。英文单词很短无所谓；**代码里的长串**（base64、压缩过的 JS、无空格的日志、长 URL）一个片段几百上千字节，就慢下来。
- 堆实现（HuggingFace）：把所有相邻对放进优先队列，O(n log n)。
- 线性实现（GitHub 2024 年的 bpe 库）：利用"BPE 结果可以从左到右增量确定"的性质，用回溯法做到 O(n)，还能 O(1) 数 token 个数。单线程比 tiktoken 快约 4 倍、比 HF 快约 10 倍 [81]。

## 4. 训练一个 tokenizer 怎么做
取一份有代表性的语料（几 GB 到几十 GB 文本，语言和代码比例决定词表偏向）→ 预分词 → 统计所有相邻符号对的频次 → 合并最频繁的一对、更新频次 → 重复到词表达到目标大小（10 万到 25 万）。HuggingFace tokenizers 能在分钟到小时级完成。厂商很少公开训练语料，但公开词表和合并表，所以复现编码不需要重新训练。

## 6. 词表大小的取舍与副作用
- **大词表**：同一段文本 token 更少 → 推理更便宜、同样的上下文窗口装更多内容、中文和代码效率更高；代价是输入输出层的矩阵更大（256K × 隐维度）、输出 softmax 更贵、稀有 token 训练不充分。
- **"故障 token"**：词表里有些条目在训练语料里几乎没出现（比如 GPT-2 的 "SolidGoldMagikarp"），模型对它们的行为异常。词表越大越容易有。
- **数字切法**影响算术能力（3 位一组便于对齐），**空格归属**影响代码（缩进）——这些都是厂商在预分词正则上的刻意选择，也是各家不一样的原因。

## 7. 在推理服务里的位置
```
用户 messages（JSON）
  → 套对话模板（Jinja 模板，把 role/content 拼成一段带特殊 token 的文本）
  → tokenize（文本 → ID 序列）
  → 按块算哈希查前缀缓存（块 = 16 或 512 个 token；缓存键是 ID 序列，不是文本）
  → 引擎：prefill 未命中的部分 → decode 逐 token
  → detokenize（ID → 文本，流式）→ JSON 回客户端
```
四个和 tokenizer 直接相关的细节：
1. **前缀缓存靠 ID 序列**：同一段文本切出不同 ID 就不命中；换 tokenizer 版本要清缓存；TokTier 把每个 tokenizer 配置按内容哈希登记，就是为了这个。
2. **token healing**：用户输入结尾可能正好落在一个 token 的中间（比如 "http" 是 "https" 的前缀），有的系统会退一个 token 再让模型接着生成，以免切分边界扭曲模型行为。
3. **流式 detokenize**：一个汉字 3 个字节可能被拆在两个 token 里，收到第一个 token 时 UTF-8 还不完整，要等凑齐再输出（否则出现乱码）；vLLM、SGLang 都有"增量 detokenizer"专门处理。
4. **特殊 token 的安全**：用户文本里出现 `<|im_start|>` 这类字符串时不能被当成控制符解析，tokenizer 有 `split_special_tokens` / `encode_ordinary` 之类的开关。

## 8. 性能：时间去哪、能不能并行

**串行部分是预分词。** 正则从左到右扫，允许回溯和前瞻（`\s+(?!\S)`），本质上是逐字符的状态机，每个字符要做 Unicode 类别判断（是字母吗？是数字吗？），用 oniguruma 或 fancy-regex 这类回溯引擎，每字节几十个周期。

**合并阶段是"片段内串行、片段间并行"。** 预分词之后每个片段独立编码，一个 480 KB 的上下文有十万级片段，可以分给多核（HuggingFace 用 rayon 做批内并行）。但每个片段内部是哈希表随机访问 + 分支：查 "这对能不能合并、rank 多少" 是对十几万条目的哈希表做随机读，L1/L2 经常不命中；每次合并要改链表或堆；每个片段还要分配小向量（GPUTOK 在 GPU 上测到 70–80% 的时间花在内存分配上，CPU 上同样的问题只是比例不同）。

**实测数字**（TokTier 表 8，117K token 上下文，"核时" = 单个核忙碌的时间）：HuggingFace fast 228 毫秒（约 2 MB/s）、Rust fastokens 13.4 毫秒（约 35 MB/s）、增量修复 2.3 毫秒、GPU 全量 0.15 毫秒。每 1,000 颗 GPU 需要的前端核：HF 114（每 GPU 每秒 0.5 请求）到 1,140（5 请求/秒）；Rust 6.7 到 67 [68]。

**为什么这在 Agent 场景里显眼**：Agent 每次调用只往十万 token 的上下文追加约 1.4K 字符，前端却全量重切；命中率越高 NPU 侧省得越多，CPU 侧这项不变，所以命中率趋近 0.99 时它在首 token 延迟里的占比从 10% 涨到 64% [68]（TokTier 摘要和引言的说法；引言称来自第 2 节的组件扫描，但正文没有给出这组扫描的图表和设置）。

## 9. 增量 / 有状态 tokenize：原理和难点

**为什么不能直接缓存上次的结果再往后拼。** 两个原因：(a) 预分词边界会移动——上次文本结尾是 "202"，这次追加了 "6"，`\p{N}{1,3}` 会把 "2026" 重新切成 "202"+"6" 或别的；末尾的空白在 `\s+(?!\S)` 规则下，追加了非空白字符之后归属会变。(b) 合并依赖右侧上下文——末尾几个字节和新来的字节可能合并成一个更长的 token。所以 tokenize(A) ‖ tokenize(B) ≠ tokenize(A ‖ B)，差异集中在拼接点附近。

**怎么做才既快又对。** 保留会话的 token 序列和每个 token 的字节区间；追加时从拼接点往左退一个窗口（几十字节到几百字节，由最长 token 和预分词规则决定），只重切这个窗口，然后检查"窗口左端是一个稳定的预分词边界、且左侧结果与旧结果相同"——检查通过就把窗口内的新结果拼上去，检查不通过就扩大窗口直到通过或退回全量。TokTier 的契约是：任何情况下输出都必须和参考实现全量切分的结果逐位一致，做不到就退回全量 [68]。上下文中间被编辑（Agent 压缩历史、删掉工具输出）的情况同理，只是修复点在中间。

**难点**：每个 tokenizer 家族的"稳定边界"判据不同（数字分组、前瞻规则、中日韩规则），要按家族推导；DeepSeek 家族的数字分组规则让某些位置永远不稳定，只能扩窗。

## 10. 正确性怎么保证
- **参考实现就是标准**：厂商发布的配置文件 + HuggingFace tokenizers / tiktoken / sentencepiece 之一，输出的 ID 序列是"正确答案"。
- **差分测试**：对每个模型、每个版本的配置，在多语言 + 代码 + 对抗样本（长数字串、混合空白、表情、无空格长串、特殊 token 字符串）语料上，逐位比对新实现与参考实现；任何一个开关（`ignore_merges`、`byte_fallback`、`add_prefix_space`、归一化）不一致都会在这里暴露。
- **版本固定**：按配置文件的内容哈希登记，前缀缓存键里带 tokenizer 版本。
- **历史教训**：HuggingFace 的"fast"与"slow"两套实现曾在 Llama 的空格处理上不一致，靠 `legacy` 开关兼容——说明"看起来一样"不够，必须逐位比。

## 11. 对鲲鹏加速库的设计建议（S1 的展开）
1. **一个引擎，三种加载器**：tokenizer.json（六段结构）、.tiktoken（base64 token + rank）、SentencePiece .model；先只做字节级 BPE，WordPiece/Unigram 后补。
2. **线性 BPE 合并核**：采用 GitHub bpe 那类回溯/增量算法，哈希表按 rank 紧凑布局减少缓存缺失，片段级并行分给多核。
3. **预分词的向量化**：把每个家族的正则改写成"按字符类分段"的规则（TokTier 的做法），字符类判定用 SVE2 的 `MATCH`/`HISTCNT`/`TBL` 一次处理 16–32 字节；没见过的正则退回通用引擎保证正确。
4. **会话状态 + 边界修复 API**：`append(session, text)`、`edit(session, range, text)`，内部做第 9 节的窗口修复，输出带"与参考实现逐位一致"的保证。
5. **接口兼容**：对外提供 HuggingFace tokenizers Rust crate 的兼容接口和 Python 绑定，vLLM/SGLang/MindIE 不改代码可替换；再提供独立服务形态（网关和引擎之间）承接会话状态。
6. **验证体系**：第 10 节的差分测试作为发布门槛；覆盖 Qwen、DeepSeek、GLM、Llama、Mistral、Gemma、Kimi、MiniMax、盘古、gpt-oss。
7. **目标数字**：每核吞吐 2 MB/s → 30 MB/s 以上（换核）；会话续写 2–3 毫秒/次（增量）；每千 GPU 前端核 114 → 1。

## 12. 常见误区
- "tokenizer 只是查表" —— 查表是最后一步，前面的切分是算法，且模型间不同。
- "JSON 都能 GB/s，tokenize 也差不多" —— 每字节差 100–2,000 倍，因为一个是结构扫描、一个是串行合并 + 哈希随机访问。
- "缓存上次的 token 序列往后拼就行" —— 拼接点附近的 token 会变，不校验就会给模型喂错 ID、前缀缓存也不命中。
- "多线程就能解决" —— 批内和片段间能并行，但预分词串行、单请求延迟仍受限，且和推理引擎抢核会适得其反 [69]。
- "做一个通用 tokenizer 覆盖所有模型" —— 引擎通用、数据按模型加载、验证按模型做，三件事缺一不可。

## 实测：词表和合并表的大小与一次上下文的热点（2026-09-23）
脚本和结果在 `notes/scripts_tokenizer_tables/`（measure.py → sizes.json，hotset.py → hotset.json；词表文件需重新下载）。
- 原始文件 / 加载后内存（HF tokenizers 0.23、tiktoken 0.14，RSS 增量，上界）/ 紧凑格式（MPH + 18 位 ID 打包，按公式算）：GPT-2 1.36 / 24 / 0.42+0.47 MB；cl100k 1.68 / 42 / 0.74+0.94；DeepSeek-V3 7.85 / 59 / 1.20+1.22；Llama 3 9.09 / 70 / 2.63+1.22（28 万条合并规则）；Qwen2.5 7.03 / 59 / 1.42+1.43；o200k 3.61 / 77 / 1.47+2.00。
- 449 KB 混合上下文（JS 280 KB、中英 Markdown 141 KB、JSON 28 KB）：o200k 用到 10,773 条合并规则（5.4%，74 KB@7 B），99% 查找落在 8,757 条，约 70% 查找 rank < 1 万；Qwen2.5 用到 11,342 条（7.5%，100 KB@9 B）。重放结果与原库逐 token 一致。
- 结论：整表压紧 1–3 MB > 950 每核 1 MB L2，但单次上下文热点 70–100 KB 放得下；现有库哈希表布局估算占 1 MB 以上缓存行 → 查表是软件问题，L2 容量不是 tokenizer 的硬件诉求。
- 已有案例：GitHub bpe 库（all_tokens + token_starts 字节块、u32 哈希键、pair_lookup、双数组 Aho-Corasick）；BlingFire（有限状态机编译模型，gpt2.bin、roberta.bin）；SentencePiece Unigram（双数组 trie）；Google Fast WordPiece（trie + 失败链接，flatbuffer）。HuggingFace tokenizers 主干 tk-encode（1.0.0-dev，未发布）已用 PtrHash MPHF 存合并表：ID 按 rank 重排；512×512 稠密网格（u16 索引 512 KB + 每条 u64 值）存 ID < 512 的热对；其余对 16 B 槽（键 u64 = 左<<32|右，值 u64 = rank<<32 | SAFE 位 | 30 位新 ID）；初始符号用 byte_internal[256] 和码点稀疏表。
