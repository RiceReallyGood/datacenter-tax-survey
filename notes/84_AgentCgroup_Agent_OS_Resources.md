## 1. 实验口径
- 单机：Intel Core Ultra 9 285K（24 核）、128 GB DDR5、Linux 6.15、cgroup v2；每个任务一个 Podman 容器，用 SWE-rebench 官方镜像（2.9–17.3 GB），**不设资源限制**；Claude Code 和依赖从宿主机 bind-mount 进容器。
- 两个模型后端：Claude Haiku 4.5（云 API，33 个任务）和 GLM-4.7-Flash（本地 GPU，111 个任务；Haiku 的 33 个是其子集）。
- 每秒采样一次 CPU 利用率和内存；记录每次工具调用的类型和起止时间。"工具执行时间"从模型发出工具请求算到结果返回，包括框架分发、进程执行、结果收集。
- 初始化时间不含镜像拉取，主要是 Podman 对镜像 overlay 层做用户命名空间 ID 重映射（随镜像大小增长），再加 Node.js 版 Claude Code 启动。

## 2. 关键数字
**时间构成。**
- 每个任务 5–11 分钟（GLM 均值 10.8、Haiku 均值 5.8，总体中位 8.1 分钟）。
- 整个生命周期：容器和 Agent 初始化 31–48%，工具执行 13–24%，模型推理 40–45%。OS 层（初始化 + 工具）合计 55–60%。
- 不算初始化时，工具执行占活跃时间均值 19.8%（Haiku）和 34.9%（GLM），单个任务从 0% 到 86% 不等。
- Bash 占工具时间的绝大部分（Haiku 80.6%，加上子 Agent 17.3%；GLM 98.8%）。Bash 内部按命令语义分：跑测试（pytest 等）占 Bash 时间 73.3%（Haiku）/ 44.5%（GLM），装包约 10%，Python 片段 27.0%（GLM）；文件浏览和 git 很轻。
- 工具调用的时间顺序是"理解—修改—验证"：Read 集中在前 30%，Bash 在 40–80%，Edit 均匀分布。

**资源。**
- **CPU 很闲**：平均 CPU 利用率 Haiku 13.2%、GLM 7.6%（以一个核为 100%）。
- **内存是密度瓶颈**：峰值内存 2–4 GB，按峰值分配时 128 GB 只能跑 32–64 个实例，而此时 CPU 用了不到总能力的 36%。
- **两层结构**：Agent 框架（Node.js 运行时）常驻约 185 MB（Haiku 183、GLM 188）；波动几乎全来自工具调用起的子进程——跑测试、装依赖时升到 500 MB–2 GB，然后回落。64 个并发实例光框架基线就要约 12 GB。
- **突发短而猛**：98.5% 的内存突发（超过 300 MB）发生在工具调用期间，而工具调用只占 28.5% 的采样时间（Haiku）；突发持续 1–2 秒；最极端的任务（pydicom#2022）峰值 4,060 MB、均值 264 MB，峰均比 15.4 倍，几秒内回落到 230 MB；1 秒内内存最多变化 2.9 GB，变化率最高 3 GB/s。
- **按命令分**：跑测试的内存突发 P95 是 518 MB（Haiku）/ 234 MB（GLM）；装包约 233 MB；文件浏览平均 4.5 MB，git 平均 13.5 MB。同样是 Bash，不同命令的峰值内存差 13.7 倍。
- **重试累积**：85%（Haiku）到 97%（GLM）的任务有重试循环（连续三次以上跑同一条测试命令），GLM 平均每任务 3.9 组、最多连续 56 次，占执行时间 7–21%；每轮重试都留下上一轮的内存，最多累积 502 MB 不释放。
- **镜像大**：平均 3.5 GB（中位）/ 4.1 GB（均值），是典型微服务镜像的 7 倍、serverless 函数的 70 倍。
- **不可预测**：任务间峰值内存 197 MB 到 4 GB（变异系数 147%）；同一任务三次运行 402/222/259 秒，解法完全不同；对话轮数与峰值内存几乎无关（r < 0.11），输出 token 数与峰值内存 r = −0.14。

## 3. 系统（AgentCgroup）
- 每次 `bash -c` 起一个临时子 cgroup，按工具调用粒度记账和限流；用 sched_ext（BPF 调度器）和 memcg_bpf_ops（内存控制器 BPF 钩子，2026-01 RFC）在内核里微秒级响应；内存紧张时先节流、再 cgroup.freeze 冻结，而不是 OOM 杀掉（杀掉就丢了上下文）；Agent 可以用环境变量声明"这条命令内存大/小"，被限流时把提示写回 stderr 让 Agent 改用省内存的办法。
- 初步评估（4 核、16 GB，回放真实内存轨迹加速 50 倍）：内存 1,100 MB 对 1,233 MB 需求时，基线 OOM 杀掉一个低优先级进程（存活 66%），AgentCgroup 全部存活；高优先级 P95 分配时延降 29%（71.0 → 50.1 ms）。

## 4. 对鲲鹏的启示
1. **"每兆瓦沙箱数"首先卡在内存容量，不在核数，也不在内存带宽。** 编码 Agent 的平均 CPU 只有十分之一个核，峰值内存却是基线的 15 倍。按这篇的数据，一台 128 GB 机器按峰值分配只能跑 32–64 个，按均值分配能跑几百个——差距全在**超卖**。这直接支撑纪要里"冷热分级 + KAE 解压提高超卖比"这条，也说明客户要的"大幅提升内存带宽"需要另找依据（见 [85]）。
2. **超卖需要"快速回收 + 快速归还"**：突发 1–2 秒、变化率 GB/s 级，用户态 PSI 守护进程（Meta oomd 那类，几十毫秒）来不及。硬件能帮的是：页状态由硬件维护（HAFT、HAFDBS）让冷页识别便宜；压缩与解压要低时延（KAE 的 KB 级时延是关键，见 [89] Sabre）。
3. **初始化占 31–48%**，大头是镜像 overlay 层的 ID 重映射——这是容器形态的问题，microVM + 快照克隆（CubeSandbox 的做法）绕开了它。
4. **跑测试是 Bash 时间的最大项**：与 `INSIGHT_AGENT_DEEPDIVE.md` 第 5.4 节"工具时间的 85% 在编译、安装、测试"一致，前端取指仍是核的第一诉求。
5. 这是**第一份公开的"命令级"分布**（跑测试 44.5–73.3%、装包约 10%、Python 片段 27%），补了深挖文档第 6 章列的缺口，但样本是 SWE-rebench 基准，不是生产日志。

## 5. 局限
- 单机、单框架（Claude Code）、单基准（SWE-rebench），两个模型；不设资源限制时测的，是"需求"而不是"在超卖下的表现"。
- 1 秒采样会漏掉亚秒级峰值。
- 控制器评估只有回放、4 核小机器。
