# Crab: A Semantics-Aware Checkpoint/Restore Runtime for Agent Sandboxes

| 项目 | 内容 |
|---|---|
| 出处 | arXiv 2604.28138v1，2026-04（`downloaded/F7_Crab_Agent_Sandbox_CR_arXiv26.pdf`） |
| 机构 | 香港科技大学（Wei Wang 组，与 AgentSysBench [57] 同组） |
| 链接 | https://arxiv.org/abs/2604.28138 |
| 一句话 | Agent 沙箱需要检查点恢复（容错、spot 实例被抢占、RL 树状 rollout 从中间状态分叉、危险动作后回滚），但每一轮都做全量检查点太贵、只存聊天记录又恢复不对。Crab 用 eBPF 观察每一轮工具调用在 OS 层留下的副作用，**超过 75% 的轮次没有需要恢复的状态**，只对有副作用的轮次做检查点，并与模型推理的等待时间重叠：恢复正确率从 8%（只存聊天）提到 100%，检查点流量最多减 87%，有一次崩溃时总时间只比无故障多 1.9% |
| 纪要对应 | "利用鲲鹏 DPA 加速器 offload cubesandbox 的 agent pause/resume"、"降低高并发高密度下 agent 操作语义尾延迟"；ISA 的 HDBSS（脏页跟踪） |
| 归属 | 沙箱团队、欧拉；硬件诉求（脏页跟踪、存储 I/O）归海思 |

## 1. 关键数据
- **现有方案的代价**：E2B（基于 Firecracker）做快照前必须暂停 microVM，开销超过 4 秒（DeltaBox [91] 给出的口径是约 4 秒每 GiB 内存）。ZFS 文件系统快照很便宜，高并发下也在 22 ms 以内；进程检查点（CRIU）的代价随内存增长。
- **主机级压力**：Terminal-Bench 轨迹的一轮中位 3.34 秒、每任务期望 117 轮；一台 128 核主机放 100 个沙箱，如果每轮都检查点，检查点请求中位 17 个/秒、p90 26 个/秒。
- **I/O 争用**：本地 NVMe（210 万/110 万随机读写 IOPS）上，16 个并发的 128 MB CRIU dump 就要 1.3 秒，64 个并发的 1 GB dump 要 47 秒；在 96 个沙箱的密度下，每轮全量检查点让 Terminal-Bench 变慢最多 3.78 倍。
- 引用 AgentCgroup [84]：框架基线约 185 MB，工具突发可超过 4 GB——检查点大小取决于在哪一刻做。
- Crab 的实现：内核的 soft-dirty 页跟踪（读 `/proc/PID/pagemap` 的脏位，做完检查点再清零）判断进程内存是否被写过；CRIU 存进程、OpenZFS 存文件；主机级调度器平滑多个沙箱的检查点突发；64 个沙箱时，检查点暴露在关键路径上的时延 p95 只占任务时间 0.44%。
- 测试平台：AWS c6id.32xlarge（128 核 Xeon 8375C、256 GB、4 块 NVMe）。

## 2. 对鲲鹏的启示
1. **暂停恢复的瓶颈在"数据量 × 并发"，最终落在内存带宽和存储 I/O 上**：100 个沙箱同时做检查点就能把 NVMe 打满。减少数据量有三层手段：只在有副作用的轮次做（Crab，软件）、只存脏页（需要便宜的脏页跟踪）、压缩（KAE，见 [89]）。
2. **脏页跟踪的软件代价**：soft-dirty 和 KVM 脏页日志都靠"写保护 + 缺页 + 清位后刷 TLB"。纪要里的 HDBSS（硬件把变脏的页记进缓冲区）和 HACDBS（硬件批量清脏位）正是把这一步硬件化；密度越高、检查点越频繁，收益越大。
3. 恢复语义的问题（哪些状态需要保存）是软件问题，硬件帮不上；硬件能帮的是"保存和恢复本身的字节搬运"。
