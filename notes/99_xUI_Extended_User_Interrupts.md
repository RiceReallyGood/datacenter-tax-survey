## 1. 用户态通知的现状（论文 §2）
- **信号**：每次约 2.4 µs 开销（论文在一个真实负载上测的），而且在任意位置打断控制流，精确 GC 的运行时（Java、.NET）无法利用。
- **轮询**：每次空检查很便宜（L1 命中的 load + 预测正确的分支），但没有通知时白白烧核；每轮询一个队列占一个缓存行；mwait 类的省电等待一次只能盯一个地址。Go 在循环里插抢占检查，几何平均慢 7%、最坏 96%；Wasmtime 靠轮询做抢占，紧循环里慢到 50%。
- **定时器**：OS 定时器贵；很多高性能运行时干脆用一个核忙等 rdtsc。
- 应用效果（模拟）：DPDK l3fwd 用 xUI 做 I/O 通知，响应性与忙等相同，40% 负载时省下 45% 的 CPU；对模拟的 DSA 加速器完成通知也有同样的收益。

## 2. ARM 上的对应物（本文调研）
- **ARM 没有用户态中断。** 能在用户态用的是"等事件"：LDAXR 读一个标志位后执行 WFE，其他核写这一行时本核被唤醒（深挖文档 5.7 节已写）；带超时的 WFET 属于 FEAT_WFxT（Armv8.7）。它只能盯一个地址，相当于 x86 的 umonitor/umwait，不是中断。
- **GICv5（FEAT_GCIE，Armv9.3 起可选）**：新一代中断控制器，所有中断类型都支持直接注入虚拟机，vCPU 之间收发 IPI 不再陷入 hypervisor——它解决的是**虚拟化**场景下的中断开销，不是用户态中断。
- RISC-V 有 N 扩展（用户态中断）的提案，另有 2026 年一篇给实时处理器加确定性用户态中断的工作（arXiv 2604.04015）。

## 3. 对鲲鹏的启示
1. 对客户"Intel UINT on ARM?"的直接回答：**ARM 架构目前没有 UINTR 的等价物**；用户态能用的是 WFE/WFET 监听一个缓存行，虚拟化场景下 GICv5 让 vCPU 间 IPI 免陷入。要不要做用户态中断，取决于客户想用它干什么：若是用户态调度器的抢占（Go、Wasm、Agent 运行时里大量协程），需要"内核旁路定时器 + 用户态中断"；若是 DPU/加速器完成通知，需要"设备中断直送用户态"——后者与 UB 的 JFCE 事件通道（REPORT 6.3）是同一类需求。
2. xUI 给出一个重要的设计教训：**中断的代价主要来自流水线冲刷和微码串行化**，而且乱序窗口越大越贵；ARM 如果要做，应当从一开始就采用"跟踪式"投递（不冲刷流水线，像分支预测失败那样只清掉受影响的部分）。
3. 与 Agent 沙箱的关系：数千个沙箱大部分时间空闲，唤醒快慢决定尾延迟；用户态通知是"密度"与"尾延迟"之间的调和手段之一。
