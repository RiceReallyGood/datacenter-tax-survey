## 1. 要解决的问题（含 motivation 数据）

综述性文章，目的是给出 hyperscale 基础设施端到端的"心智模型"，并点出与公有云的差异（不同约束导致不同优化）。

## 2. 核心思路（工程文化 → 架构选择）

- **Move fast**：持续部署到极致（97% 的服务全自动部署、55% 每次提交即部署；前端 FaaS 每 ~几小时全量发布一次；每天 >10 万次线上变更）。
- **单一代码库 + 主线编译**：RPC 库更新后，所有依赖它的应用下次发布自动用新版——这是 SRLib 形态可行的前提（对比 mRPC 论文引用的"Facebook 库变更要几个月上线"，两者角度不同：编译进去容易，全量部署完慢）。
- **共享基础设施与标准化**：所有产品共用服务器池；KV 存储收敛到 ZippyDB；组件复用链 Tectonic→ZippyDB→Shard Manager→ServiceRouter→Delos。
- **Research in production**：没有独立研究实验室，论文全部来自生产团队。

## 3. 系统设计 / 软硬件分工（对第 1、2 章有用的事实）

**硬件与 fleet**
- **非 AI 计算只有一种服务器类型**：单 CPU + 同样的 DRAM（以前 64 GB，现在 256 GB）；"公有云必须提供多种机型，Meta 则让应用去适配硬件，避免机型泛滥"。
- 存储：热数据在内存+SSD（社交图 TAO）；温数据 HDD（每台 1 CPU + 36 HDD + 2 SSD 元数据缓存）；冷数据高密度 HDD（1 CPU + 216 HDD，大部分时间断电）。
- 机架没有双电源、双 ToR；冗余只在 10,000–20,000 台服务器的 MSB 级别（每 6 个 MSB 一个备用）；容器用本地直连 SSD 做根盘（不支持热迁移）→ 用软件（容器/分片跨故障域分散、协作式生命周期协议、Global-DaaC）弥补低成本硬件。
- **Power 是最受约束的资源**（20–30 年寿命内固定），功率超订 + 自动化功率封顶。
- 自研数据中心、服务器、交换机、视频加速器、AI 芯片（MTIA，按负载优化 SRAM）；通过 OCP 开源。
- 数据中心网络：fabric 内任意两台服务器全 NIC 带宽互通、无超订；区域内跨数据中心通信不是瓶颈（除 ML 训练外服务可散布在区域内各数据中心）。

**请求处理路径（Figure 2）**
- 负载均衡器 → 数万台**前端 serverless 函数**服务器 → 调用许多后端服务 → 部分再调用 ML 推理（广告/信息流推荐）；前端函数可向事件队列投递事件给**事件驱动 serverless 函数**（XFaaS）异步处理。
- 前端函数：事件驱动函数的服务器比 ≈ **5:1**；XFaaS 负载尖峰，用延迟执行、跨区域全局均衡、配额限流来削峰。
- **FaaS 是主要编程范式**：>10,000 名工程师写 FaaS 代码，比写常规服务代码的多 50%；FrontFaaS 服务器 >50 万台常驻、无冷启动。
- **同一 Linux 进程内并发执行多个函数**（与公有云每函数一个 VM 的隔离模型不同）→ 更高硬件效率。
- FaaS 无状态，重度依赖外部缓存系统。

**Service mesh**
- 99% RPC 由链接进服务的路由库直接客户端→服务器路由，1% 走代理；省 O(100,000) 台服务器；代价是库编译进 O(10,000) 个服务、各自部署节奏不同。

**全局资源管理（Global-DaaC）**
- 全局容量管理 → 区域配额/虚拟集群 → 容器管理器（Twine）跨数据中心分散一个 job 的容器 → 内核机制做服务器内隔离；有状态服务由全局服务放置器（GSP）做约束优化；ML 训练按数据+GPU 共址调度；O(100,000) 服务器和 O(100,000) GPU 规模验证。

**控制平面哲学**：除 BGP 外几乎所有去中心化控制器都被集中式取代（WAN、分片、Owl 数据分发、元数据分发树）——"数据中心环境下集中控制器不仅够用，还更简单、决策质量更高"。

## 4. 关键定量结果

| 事实 | 数值 |
|---|---|
| 非 AI 服务器类型 | 1 种（1 CPU + 256 GB） |
| FrontFaaS 服务器 | >500,000 台 |
| 前端函数 : 事件驱动函数 服务器比 | ≈5:1 |
| 写 FaaS 的工程师 | >10,000，比写服务代码的多 50% |
| 服务数 | O(10,000) |
| RPC 走库 / 走代理 | 99% / 1%；代理若全量需 O(100,000) 台 |
| 自动部署 | 97% 服务全自动，55% 每次提交部署 |
| 每天线上变更 | >100,000 |
| MSB 故障域 | 10,000–20,000 台/MSB；6:1 备用 |
| 温存储服务器 | 1 CPU + 36 HDD + 2 SSD；冷存储 1 CPU + 216 HDD |

## 5. 对芯片 & 服务器厂商的启示

1. **hyperscaler 的通用服务器是"单一 SKU、单 CPU、大内存"**，靠软件适配硬件——这意味着 CPU 厂商面对 Meta 类客户时，**一颗 CPU 要同时服务 Web（PHP JIT，大代码）、缓存（内核/网络重）、排序（ML+序列化）、存储前端**，没有按负载分 SKU 的空间（SoftSKU 论文正是在这个约束下做"软配置"）。DCPerf 的多负载几何平均评分就是这个现实的反映。
2. **Meta 的"微服务"实际上是 FaaS 前端 + 后端服务**：前端是 50 万台服务器跑的 PHP/Hack 函数（HHVM），一个进程跑多个函数。因此 Meta 的"每请求 RPC 数"来自 FaaS 函数扇出到后端服务和缓存；RPC 客户端侧的序列化/I/O 开销落在 HHVM 进程里（Accelerometer 的 Web：I/O 21% + 前后处理 17% + 序列化 10%）。**Web 层的 RPC 客户端开销是 fleet 级最大的 RPC 成本池**（50 万台）。
3. **Power 是第一约束** → Perf/Watt 决定采购（与 DCPerf 一致）；功率封顶自动化意味着 CPU 需要好的功率管理接口。
4. **网络无超订、区域内跨 DC 无性能惩罚** → 服务放置（形态 C）主要考虑故障域而非网络距离；跨区域才有延迟问题（ServiceRouter 的 locality ring）。
5. **同进程多函数并发**是 hyperscaler 独有的效率手段；公有云每函数一 VM 的隔离是 serverless 形态 B 高成本的根源。硬件层面能缩小这一差距的是**廉价的进程/VM 级隔离**（快速 VM 切换、内存标签、CXL 池化的快速冷启动）。
6. **集中式控制 + 去中心化数据面**是 Meta 一贯的取舍——对 NIC/交换机可编程性的要求是"数据面快且可远程配置"，不需要在设备上做复杂的自治决策。
7. **服务器数量级**：O(10,000) 服务、>50 万台 FaaS、O(100,000) 台代理的节省量——给第 5 章估算"RPC 税值多少台服务器"提供了尺度。

## 6. 局限 / 争议

- 综述，无新的定量测量；tax/RPC 数据仍需引用 Accelerometer、ServiceRouter、DCPerf。
- 未涉及 CXL、DPU/SmartNIC 等新硬件在 Meta 的应用状况。
- 与公有云的差异被反复强调——本报告在推断公有云客户负载时不能直接套用 Meta 的形态占比（99% library）。
