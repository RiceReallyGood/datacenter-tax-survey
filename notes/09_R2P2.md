# R2P2: Making RPCs First-Class Datacenter Citizens

| 项目 | 内容 |
|---|---|
| 出处 | USENIX ATC 2019 |
| 机构 | EPFL（Kogias, Prekas, Ghosn, Fietz, Bugnion） |
| 链接 | https://www.usenix.org/conference/atc19/presentation/kogias-r2p2 ；代码 https://github.com/epfl-dcsl/r2p2 |
| 一句话 | 把"请求-响应对"而不是"字节流/连接"作为网络的一等抽象：基于 UDP、无连接、请求目标选择与消息传输分离，使**网络中间件（软件盒或 P4 交换机）可以按 RPC 做负载均衡/调度**。提出 JBSQ(n)（中心无界队列 + 每服务器有界队列 n），Tofino 上实现只加 <1 µs、软件盒 5 µs/2 核跑满 10 Gbps；Lucene 搜索 P99 比 NGINX 低 5.7×，Redis 在 200 µs SLO 下吞吐 +4.8–5.6× |
| 骨架公式定位 | 削减**每 RPC 通信成本中的服务器端排队项**（Google 九段模型的 Server Recv Queue）；部署形态：内核旁路（DPDK）端点 + 网内调度器（可编程交换机 = 把 L7 负载均衡从 sidecar/代理核搬进 ASIC） |

## 1. 要解决的问题（含 motivation 数据）

- OLDI 应用（搜索、电商、社交）是 root/leaf 两层结构，高扇入扇出，任务从几 µs（KV）到几 ms（搜索）。
- RPC 几乎都跑在 TCP 上（gRPC/Thrift/Memcached 协议），**字节流与消息语义不匹配**带来四个问题：(1) RPC 语义弱于 TCP 提供的可靠有序流（幂等、无序），多余的保证是开销；(2) 连接复用导致 HOL 阻塞；(3) 高扇入扇出的连接图导致 API 扩展性差；(4) POSIX socket 在两端造成 bufferbloat。
- 负载分配的两种现状都不好：随机选副本（直连或 L4）→ 负载不均和 HOL；L7 反向代理（NGINX 等，RR/JSQ）→ 仍有 HOL，且代理本身成瓶颈。
- 排队论：单队列模型远优于多随机队列；JSQ 在服务时间方差小时接近最优；**JBSQ(2) 在高负载、高方差下优于 JSQ**。

## 2. 核心思路

- **暴露 RPC 抽象给网络**：RPC 由 `<src_IP, src_port, req_id>` 唯一标识，客户端指定的目标地址与实际应答服务器解耦 → 网络中间件可以任意改路由；应答直接回客户端不经路由器。
- **请求目标选择与请求/响应流传输分离**：只有 REQ0（首包，含请求开头）经过路由器；REQn 和 REPLY 直接在客户端与被选服务器之间传 → 路由器容量只受包处理速率限制，不受消息大小限制。
- **JBSQ(n)**：路由器持有无界中心队列，每个服务器只允许 n 个 outstanding 请求（含正在处理的）；服务器完成后发 R2P2-FEEDBACK 回路由器。n=1 即单队列模型，n=∞ 即 JSQ。JBSQ 比 JSQ 更适合硬件：不需要"求最小值"，而且有内建的路由器→服务器流控。
- 失败与延迟暴露给应用（客户端按 SLO 设定时器、可实现对冲/早丢），不做透明可靠传输；无跨 RPC 顺序保证。

## 3. 系统设计 / 软硬件分工

- 协议：UDP 之上；消息类型 REQ0 / REQready / REQn / REPLY / R2P2-FEEDBACK；16 位 req_id + 16 位 packet id；Policy 字段告诉路由器用什么策略。
- 多包消息用 ms 级 RTO + SACK；拥塞控制不在范围内，声明可复用 Homa（消息语义天然匹配）或 DCTCP/DCQCN，且只需用于多包消息。
- 两级流控：客户端↔中间件（中间件可按优先级丢弃单个请求）、中间件↔服务器（JBSQ 的有界队列）。
- **非 POSIX 异步 API**（`r2p2_send_req`、`req_recv`、`req_success`、`req_timeout` 回调），只有整条消息到齐才通知应用。RPC 逻辑从应用层下沉到网络栈。
- 端点实现：DPDK 用户态库（r2p2-lib）；Linux 内核版可选。
- 路由器两种实现：**软件中间盒（DPDK）**：+5 µs 空载延迟，2 核跑满 10 Gbps；**Tofino P4 ASIC**：+<1 µs，消除软件盒 I/O 瓶颈。

## 4. 关键定量结果

- 微基准：64 个 worker、10 µs 任务、150 µs 尾延迟 SLO 下，JBSQ(3) 路由器在多种服务时间分布下**接近理论最优吞吐**。
- Lucene++ 网页搜索（ms 级任务，16 worker，50% 负载）：P99 比 NGINX 低 **5.7×**。
- Redis 主从复制 4 节点，200 µs SLO：吞吐比原生 Redis（TCP）高 **4.8–5.6×**（来自协议更精简 + 内核旁路 + 调度三者叠加）。
- 软件路由器 5 µs / 2 核；Tofino <1 µs。

## 5. 对芯片 & 服务器厂商的启示

1. **L7 负载均衡可以进交换机 ASIC**：只要协议把"选目标"和"传消息"分开、且策略不需要求最小值（JBSQ 而非 JSQ），P4 可编程交换机就能以 <1 µs 的代价替代软件代理。对比部署形态 A 里的 sidecar/代理形态（每个请求都要经过代理核做 L7 解析），这是把"每 RPC 的负载均衡成本"从 CPU 核转移到网络 ASIC 的具体路径。
2. **有界服务器队列 = 天然的过载保护**：JBSQ(n) 把排队集中到网络里，服务器端队列深度可控——这和 Breakwater/Aequitas 的准入控制是同一问题的不同切入点（网内 vs 端点）。
3. **消息语义再次胜出**：与 Homa 一样，R2P2 的收益很大一部分来自抛弃字节流（无 HOL、无连接状态、无多余可靠性）。对 NIC/DPU 厂商：面向 RPC 的卸载引擎应该以 request-response pair 为单位管理状态，而不是以连接为单位（RDMA QP 模型的连接状态爆炸是反例）。
4. **非 POSIX API 是前提**：要享受这些收益，应用必须改用消息式异步 API——这是所有内核旁路/新传输方案的共同门槛，也是 mRPC 后来试图用"RPC 系统服务"来绕过的问题。
5. **两核跑满 10 Gbps 的软件路由器**在 100–400 Gbps 时代不再成立（需要 20–80 核），这正是把它做进 ASIC/DPU 的理由。

## 6. 局限 / 争议

- 10 Gbps、Tofino 一代、EPFL 实验室集群；未在真实微服务调用图上评估，只有 KV/搜索两层结构。
- 不做拥塞控制、无跨 RPC 顺序、失败暴露给应用——生产环境要求（加密、认证、多租户、跨 DC）都未涉及。
- 中心路由器是单点（每个服务一个 JBSQ 队列），跨机架/跨集群扩展性未讨论。
- 后续 Google 论文指出真实 RPC 是 ms 级、CPU 成本才是主要问题；R2P2 这类 µs 级尾延迟优化的 fleet 级价值有限，主要适用于 KV/缓存这类"RPC 栈重"的服务。
