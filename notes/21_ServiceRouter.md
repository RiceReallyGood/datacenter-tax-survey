## 1. 要解决的问题（含 motivation 数据）

- 微服务需要 service mesh 做服务发现、负载均衡、故障转移、认证加密、可观测、过载保护、分布式追踪、容量归因、影子流量。
- 常见形态（Istio/Linkerd）= **每个服务进程旁一个 L7 sidecar 代理** + 中心控制面配置每个代理。两个问题：
  - **可扩展性**：中心控制面既生成全局路由元数据又管理每个路由器，撑不到百万级。
  - **硬件成本**：代理多一跳，要做序列化/反序列化。**Istio 官方基准：0.35 vCPU 处理 1,000 RPS → 路由 100 亿 RPS 需要 175 万台 AWS t4g.small**。
- 现有 mesh 不支持分片服务（Meta 68% 的 RPC 是分片服务，代理可能把请求路由到错误的分片）；跨地域路由缺乏"延迟 vs 负载"的显式权衡。

## 2. 核心思路

- **控制面只生成全局路由信息（RIB），不管理路由器**；RIB 大量复制；每个 L7 路由器自配置（按需拉取 miniRIB 并订阅更新）。
- **服务网格功能做成库（SRLib）链接进应用**，客户端直连服务器，无代理；miniRIB 由本机的 RIBDaemon 缓存（与应用隔离，避免 RIB 更新导致的 CPU 尖峰打进应用）。
- 允许多种 L7 路由器共存：SRLib（99%）、SRSidecarProxy（改不了源码或语言不支持，如 Erlang）、SRRemoteProxy（类 AWS ELB，多客户端共享代理以复用连接）、SRLookaside（gRPC 风格，已弃用——机器内存 ≥64 GB 后省内存没意义）。
- 分片抽象：mesh 与服务之间定义通用的分片接口，统一处理分片和复制。
- **Locality rings**：服务声明"本地负载 >70% 才允许流量去同大洲其他区域，>80% 才去其他大洲"；控制面据全局流量/负载算跨区域路由表。

## 3. 系统设计 / 软硬件分工

- 设计空间（Table 1）：两个维度——谁缓存 miniRIB（库/内核/本地守护进程/远程）× 谁路由流量（库/内核/本地代理/远程代理）。作者认为内核路由（eBPF，如 Cilium）只能做 L3/L4，L7 仍需 sidecar；库内缓存 RIB 会影响应用隔离。
- 连接管理：新建 TLS/TCP 连接 1.6 ms、每侧 14 KB 内存 → 连接复用 >99%；跨区域低流量客户端多时，共享远程代理能提高连接复用（E-Comm 案例：P90 从 ~325 ms 降到 ~150 ms，每台 SRProxy 处理 ~87K RPS）。
- 负载均衡信号：outstanding 请求数 + 服务器 CPU；轮询开销高时退化为二选一。
- 规模：数十个 region、数百万 L7 路由器、数百万容器、数亿分片；每天 ~2,500 个服务的路由配置变更。

## 4. 关键定量结果

**A. 形态占比（fleet）**
- **SRLib 路由 99% 的 RPC 请求**；SRProxy（数千台机器）路由 **1.1% 的请求、0.1% 的数据量**；若 100% 走代理需增加数十万台机器。
- 68% 的 RPC 请求面向分片服务，32% 面向非分片服务。

**B. CPU 开销微基准（Figure 10；10 台服务器、连接 100% 复用、同区域；生产平均载荷：请求 5.4 KB、响应 6 KB；Thrift 为下界基线）**

| 载荷 | SRLib 额外 CPU | SRProxy 额外 CPU | SRProxy 延迟 |
|---|---|---|---|
| 生产大小 | **+80%**（最坏微基准）；**生产聚合实测 +36%** | **+273%**（客户端与代理各半） | **+107%** |
| 大载荷（10×） | +25% | +190% | — |

- 微基准刻意最坏（载荷是简单字符串、无应用处理），因此比例偏高；生产环境聚合后 SRLib 只多 36%。
- **SRProxy 的指令 74% 在用户态、26% 在内核**——即使用零拷贝转发完全消除内核开销也不够，而且代理因为要处理加密和身份，根本做不了零拷贝。
- SRLib 与 Thrift 延迟几乎相同。

## 5. 对芯片 & 服务器厂商的启示

1. **给骨架公式的部署形态项赋值**（Meta 生产数据）：
   - library：每 RPC 成本 ≈ 1.36× 裸 RPC（生产聚合），流量占比 99%
   - sidecar/远程代理：≈ 3.7× 裸 RPC（+273%），流量占比 1%
   → Meta fleet 的 RPC 成本几乎完全由 library 形态决定；**mRPC 测的 sidecar "3×"与这里的 273% 高度一致**，可以作为公有云 service mesh 客户的系数。
2. **代理的成本在用户态（序列化、加密、身份）而不在内核**——所以"用 DPU/eBPF 卸载网络栈"对 sidecar 形态的收益有限，真正要卸的是 L7 处理（序列化 + TLS + 路由决策）。这与 Cerebros"整个 RPC 层一起下"的判断一致，也解释了为什么 Cilium 类 eBPF mesh 仍需 sidecar 处理 L7。
3. **hyperscaler 自己选择了"不要代理"**：Meta 用工程手段（库 + 分布式自配置）把 mesh 成本压到最低。对硬件厂商的含义：**公有云/企业客户（无法改应用、多语言、Envoy 普及）才是 sidecar 开销的主要承担者，也是 L7 卸载硬件最大的市场**；hyperscaler 内部需求则集中在 library 形态下的序列化/加密/内核栈。
4. **分片服务占 68% 的 RPC**：路由决策依赖应用层分片键 → 任何网内/NIC 上的 L7 负载均衡（R2P2/JBSQ 那类）必须理解分片，否则只能覆盖 32% 的流量。
5. **TLS 连接建立 1.6 ms / 14 KB**——认证加密是 mesh 的固有开销之一；Google 的 RPC tax 里 encryption 很小（<0.2%）是因为连接复用 >99%，但**代理形态下加密无法零拷贝**，是 sidecar 卸载到 NIC 时要处理的第一道关（TLS 卸载）。
6. **平均 RPC 载荷 5.4 KB / 6 KB**（比 Google 中位 1.5 KB 大，与 Meta 的 Thrift 二进制和信息流场景相符）→ 序列化/拷贝的绝对成本在 Meta 更高，零拷贝序列化（zBuffer）和 SG-DMA 的收益更明显。

## 6. 局限 / 争议

- 微基准是最坏情况；生产聚合的"36%"没有分解成序列化/路由/可观测等子项。
- 没有讨论 SRLib 自身在 CPU 上的分解（多少是 Thrift、多少是 SR 逻辑）——需要结合 Accelerometer。
- 论文立场偏向 library，对 eBPF/内核 L7 路由的判断（"只能 L3/L4"）在 2026 年已被 XLB 等工作挑战。
- 分片/跨区域路由部分与硬件关系不大，本报告只取形态与成本数据。
