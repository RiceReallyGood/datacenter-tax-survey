# Canal Mesh: A Cloud-Scale Sidecar-Free Multi-Tenant Service Mesh Architecture

| 项目 | 内容 |

## 1. 要解决的问题（含 motivation 数据）

阿里云四年 Istio 生产经验揭示的四个问题：
- **侵入**：sidecar 与应用同 pod，内存泄漏会拖垮应用，升级要重启 pod。
- **性能**：流量经 iptables 重定向到 sidecar，两端各多两次上下文切换、内存拷贝、协议栈处理；再加 CPU 密集的 TLS；吞吐/延迟劣化 3–7×。
- **资源**：**sidecar 占集群 10% CPU（1500 核）、10% 内存（5000 GB）**，极端 3× CPU / 5.54× 内存于应用；为保延迟必须让 sidecar CPU 利用率 <45%（>45% 延迟 2×，>75% 尖峰 100–1000×）→ 过度配置。
- **编排**：一个云服务 O(100k) pod，每个 pod 一个 sidecar，控制面推送配置的开销随集群规模线性增长，配置更新频率也随规模上升。
- 已有替代：Cilium/SPRIGHT 用 eBPF 省 CPU 但**L7 可编程性有限**，而 **80–95% 的用户需要 L7 功能（72–95% 用 L7 路由策略）**；Istio Ambient（2022）把 L7 拆到每服务可选代理、每节点共享 L4 代理，但代理仍在用户集群内、仍耗用户资源，且需要 L7 的用户仍要付 L7 代理成本。

## 2. 核心思路

- **激进解耦**：mesh 功能全部搬到云端集中式多租户网关（复用 SLB/NAT/云网关的运营经验与基础设施）；用户集群内只留每节点一个最小功能代理（功能等价性分析：证书/身份必须留本地，授权/流量控制/可观测可远程）。
- 多租户整合带来的新问题及解法：可用性（跨 AZ 分层故障恢复）、租户隔离（shuffle sharding）、噪声邻居（异常检测触发的快速干预：扩缩/迁移/限流）、弹性（根因分析定位快速增长的服务做精确扩容）、成本（LB 解聚合复用云基础设施、隧道会话聚合）。
- 性能手段：eBPF 替代 iptables 做重定向（发现 eBPF 缺少 Nagle 式小包聚合导致上下文切换过多，自己在 eBPF 里实现了聚合）；**mTLS 非对称加密卸到远程密钥服务器**（RPC 调用），对称加密留本地。

## 3. 系统设计 / 软硬件分工（对硬件最相关的发现）

- **本地加密加速的失败经验**：Intel QAT / AVX-512 只有 <10% 的 VM 机型（新 CPU）支持，且 g7 比 g6 贵 ~30%；批处理架构在新会话少时反而**增加延迟**（凑不满一批就等待）→ 改为远程密钥服务器集中做非对称加密，不依赖用户 VM 机型。
- **会话资源受 SmartNIC 内存限制**：整合后的代理要管理海量会话，而每个后端 VM 的会话资源来自底层服务器上 **SmartNIC 的有限内存**；会话用到 90% 时 CPU 只用 20% → 会话与 CPU 利用率失衡，用隧道会话聚合缓解。
- 可观测性有所牺牲：on-node 代理只做 L4 观测，L7 观测在远程网关。
- 健康检查探针在整合网关上成为显著负载，用多级聚合减少 99.6%。

## 4. 关键定量结果

| 指标 | Canal vs Istio | Canal vs Ambient |
|---|---|---|
| 吞吐 | **12.3×** | 2.3× |
| 延迟 | 1.7× 更低 | 1.3× 更低 |
| CPU 消耗 | **12–19× 更低** | 4.6–7.2× 更低 |
| 数百 pod 配置完成时间 | 1.5–2.1× 更快 | 1.2–1.5× 更快 |
| 南向控制面带宽 | 9.8× 更低 | 4.6× 更低 |
| 用户部署成本 | −55–70% | — |

- Ambient 相比 Istio 代理数从 O(pod) 降到 O(node+service)，按生产数据约少 43% 的代理。
- 生产 Istio：sidecar 1500 核 / 5000 GB（各 10%）；极端 3× / 5.54×。

## 5. 对芯片 & 服务器厂商的启示

1. **公有云 service mesh 的 RPC 税是真实且巨大的**：10% 的集群 CPU 花在 sidecar 上是保守值（配置复杂时 3× 于应用）。结合 MeshInsight（解析占 63–77%）和 ServiceRouter（+273%），可以给"公有云 sidecar 形态"一个经验系数：**每 RPC 成本 ≈ library 形态的 3–4×，占租户 CPU 的 10–30%**。
2. **架构演化方向与硬件卸载同向**：sidecar（每 pod）→ Ambient（每节点 L4 + 每服务 L7）→ Canal（集中多租户网关）。每一步都是把 L7 处理**集中到更少、更专业的位置**——这正是 DPU/网关加速器最适合的落点。Canal 的集中网关是"L7 处理专用基础设施"，天然是 SmartNIC/DPU/FPGA 加速 HTTP/gRPC 解析和 TLS 的用户。
3. **加密加速的部署教训直接对准芯片厂商**：(a) 加速功能只在少数新机型上有 → 客户不愿为此多付 30%；(b) 批处理型加速器在低并发时反而增加延迟。**结论：加密/压缩类加速要么是所有 SKU 标配（否则云厂商会绕过它），要么支持低延迟的小批量路径**。阿里最终用"远程集中加速"绕开了本地硬件——硬件厂商失去了这个市场。
4. **SmartNIC 内存限制会话数**成为多租户网关的扩展瓶颈——DPU 的片上/板载内存容量和会话表设计是云网关类客户的硬需求。
5. **eBPF 的小包问题**（缺 Nagle 聚合 → 上下文切换爆炸）说明内核旁路/eBPF 数据面对小消息 RPC 并不天然高效，与 Homa"小消息软件开销主导"、MeshInsight"零拷贝对小消息无效"一致：**小消息的批量/聚合能力**是 NIC/DPU 的关键特性。
6. **80–95% 用户需要 L7** → 任何只做 L3/L4 的硬件 mesh 加速（纯 eBPF、纯 NIC 流表）覆盖面不足；L7（HTTP/2、gRPC、mTLS）是必须啃下的硬骨头。

## 6. 局限 / 争议

- 集中网关引入远程一跳（延迟仍比 Istio 低是因为 sidecar 太慢），并牺牲了端到端 L7 观测；对延迟极敏感的服务未必接受。
- 多租户网关的故障爆炸半径更大，论文用大量工程手段缓解但仍是新的风险点。
- 评估对比的是 Istio 1.x 和 Ambient 早期版本；Cilium + Envoy 组合未直接对比。
- 阿里云特定（复用其云网关/LB），其他云厂商不一定能复用。
